# 研发计划 001：架构基线与决策记录

**状态：已确认基线**
**日期：2026-08-16**
**定位：记录 DramaBoard 工程启动时已确认的架构决策（轻量 ADR 合集）。设计愿景见 Design Note 001–003 与《基础设施.md》。本文档是所有开发会话的共同前提。**

每条决策记录：决定 / 理由 / 可逆性。修订时不删除旧决策，标注"已被 Dxx 取代"。

---

## D1：Simulation Kernel 是纯函数核，零外部依赖

**决定**：`DramaBoard.Kernel` 项目不依赖任何外部包与外部效应——无 IO、无 wall-clock 读取、无全局可变状态、无环境变量，不引用存储库（atelia）、游戏引擎、LLM SDK。核心形状为：

```text
(WorldState, Input) → (DomainEvent[], WorldState')
```

所有非确定性（随机、玩家决策、外部输入）必须显式作为输入进入 Kernel。

**理由**：可测试性（property test 需上万次快速迭代）、replay determinism、玩具模型轻量化。这是 Design Note 002 §4"Kernel 尽量纯、确定、可测试"的落实。

**可逆性**：难逆——它塑造所有领域类型的形状。这是有意为之的核心承诺。

---

## D2：事件链是 replay authority，WorldState 是投影

**决定**：世界历史的唯一真理源是 DomainEvent 序列（加初始状态与显式输入）。WorldState 快照只是加速缓存。Kernel 面向自定义的薄 Journal 接口记录事件；第一实现是 InMemory。

**理由**：Design Note 003 §16（`EventCandidate ≠ DomainEvent`；Forecast Queue 可失效，Journal 不可改写）。避免系统中出现两套版本化真理源竞争——世界线 Fork 语义必须按 `(ModelTime, Microstep)` 事件边界定义，而不是按任何对象图 commit 边界。

**可逆性**：难逆，与 D1 配套。

---

## D3：存储落盘是 adapter，后置实现

**决定**：
- 落盘采用 `Atelia.EventJournal` 作为 adapter（未来独立项目 `DramaBoard.Journal.Atelia`），DomainEvent 序列化为 opaque payload 追加，世界线 fork 对应 branch。
- `Atelia.StateJournal` 仅用于更远期的 checkpoint / AI Player lineage 快照（缓存与主体连续性角色），不进入 Kernel 领域模型。
- Kernel 与 Protocol 项目**永不**直接引用 atelia。

**理由**：EventJournal 的形状（parent chain / branch / opaque payload / 正序 replay）与需求几乎同构；StateJournal 是侵入式对象图编程模型（DurableObject / Durable* 容器 / Revision 绑定），本征耦合会污染领域模型纯度并引入确定性风险。原则："Journal-shaped, but not necessarily StateJournal"。

**可逆性**：中——adapter 边界使替换便宜。

---

## D4：repo 保持分离

**决定**：dream-board 与 atelia 是独立 repo。atelia 依赖只允许出现在 adapter 项目（WP11）。atelia 本地路径：`e:\repos\Atelia-org\atelia`（注意 `e:\repos\atelia` 是无关的旧 Python 项目）。

**理由**：第一阶段零依赖可行；探索期大量生成-丢弃的历史不污染 atelia；两边可并行开发。引用机制（local NuGet feed vs ProjectReference）推迟到 WP11 决定。

**可逆性**：半可逆，推迟是安全的。出现"频繁反向驱动 journal 库改 API"信号时再考虑 monorepo。

---

## D5：开发环境留在 Windows，跨平台正确性靠 CI

**决定**：日常开发 Windows + PowerShell；GitHub Actions 以 `{ubuntu-latest, windows-latest}` matrix 跑 `dotnet build + test`。

**理由**：.NET 工具链跨 shell 等价；跨平台正确性应由 CI 保证而非搬迁开发环境；WSL 有 /mnt 跨界 IO 性能坑，未来 Godot 调试也在 Windows。

**可逆性**：随时可换。

---

## D6：工具链基线

**决定**：
- TFM：`net10.0`（与 atelia 对齐，未来 adapter 零摩擦）。
- 测试：xUnit（优先 v3，配置困难则 v2，不阻塞）。
- Property testing：CsCheck，在 WP7 需要时引入。
- `Nullable` + `ImplicitUsings` enable，`TreatWarningsAsErrors`。
- Solution 格式优先 `.slnx`（diff 友好，利于多 agent 协作），工具链不支持则回退 `.sln`。

**可逆性**：高。

---

## D7：命名（2026-08-16 修订）

**决定**：正式名为 **DramaBoard**。代码命名空间/程序集/包名统一用 `DramaBoard.*`。repo 目录名 `dream-board` 是早期旧名，保留不改，不再有其他含义。

**理由**：用户确认 DramaBoard 为正式名（与设计文档概念名一致）；在 WP0 刚完成、代码量极小时执行 rename，成本最低。

**修订历史**：初版决定为 `DreamBoard.*`（与 repo 名一致），同日被本修订取代。

**可逆性**：已行使——此后视为低。

---

## D8：开发模式——主线规划 + subagent 执行

**决定**：
- 主线会话负责：方向、工作包定义、派发、验收、更新状态表。
- 具体实现由 `coder` subagent（`.github/agents/coder.md`）在一次性会话中完成。
- `docs/研发计划_002_工作包分解.md` 是跨会话共享状态：subagent 的输入 = 该文档对应 WP 章节 + 引用的设计文档章节；主线在 WP 完成后更新状态表。
- 每个 WP 的最低验收标准：`dotnet build` 与 `dotnet test` 全绿。

**理由**：应对上下文窗口限制；文档而非对话历史充当持久记忆；WP 边界即验收边界。

**可逆性**：高，纯流程约定。
