### 尚未选择的产品机制

计划具体表达；维护时世界是否继续；唤醒与中断条件；思考与其他活动能否同时进行；思考耗时公式；笔记生效/保留/中断处理；一般维护是否付费；空计划与保持原样后的节奏。审查可以指出选择的后果，不代替用户选择。

### 本轮允许的修改

新增和完善理念文档及审查记录，维护文档导航与 PROJECT-STATE。已有 PROJECT-STATE 修改来自前两轮设计讨论，应在其基础上更新。无实现、构建、测试、提交或推送任务。

## 2. 审查方法

使用用户指定的 `dialectical-simplification` 技能：三个独立角色分别审视需求膨胀（Demand skeptic）、最小模型（Minimal architect）与不可删语义（Semantic defender），再以具体反例交叉质询。审查期间代理只读；主会话对照用户要求与源码裁决后统一修订。

每项意见应给出位置、主张、来源、当前消费者、复杂度成本、最小替代、删除后的失败轨迹、裁决与置信度。多个文档源于同一提议时不计为独立证据。

## 3. 收敛结果

最小模型是：维护者编辑或保留未来安排；共享运行时保有信息与实际进度，按授权执行并在明确机会请求维护；“再想想”用一条可续用笔记和正的游戏时间换取继续维护的机会；实际结果仍由世界规则决定。

| 裁决 | 审视对象 | 证据与失败情境 | 最终处理 |
|---|---|---|---|
| keep | 规划、计划、执行进度的语义区别 | U3；把“到镇上再决定买什么”当作可直接执行指令会捏造采购；删除已出发的队列头不能使角色回到起点 | 保留区别，不预设三套容器或 Goal/Task/Activity/Command 多级框架 |
| merge / simplify | 初稿第 3、7 节重复的控制/结果权威说明 | U1、C1/C3；实际需要是计划修订不能与已开始移动的先后关系冲突，不依赖特定模块名称 | 合并为第 3 节的一处因果与生效边界；Kernel/Spatial 名称移入当前实现说明 |
| simplify | Human/LLM “查询能力一致” | U2；同形 API 无依据，但只有 Human 找得到笔记同样不满足共享方向 | 明确信息资格与可取用范围一致，呈现和取得方式可以不同 |
| keep / simplify | 注意力处理 | U4、C3；空计划 → 保持原样 → 同一时刻立即再次维护会形成无进展循环 | 约束维护后的推进/等待含义；新判断需要或约定时机都可触发，无需固定提醒生命周期 |
| keep | “再想想”的可选资格、必填笔记、正耗时与世界后果 | U5/U6；耗尽令牌便失去选项违反始终可用；按网络等待收费违背能力脱钩；直接跳时会漏掉先到期事件 | 保留全部产品语义，分开现实等待与游戏内行动 |
| simplify / keep | 笔记的续用保证 | U5；后台有记录但下次思考既不见文本也不知入口，仍无法继续；正式记录后因中断清空也破坏积累 | 正常完成后可发现、可取得；已纳入角色记录的内容不会仅因中断而消失 |
| defer / user-decision | 思考时笔记何时生效、如何中断，以及是否同时移动 | U1；[Submit](../../src/Server/FreePlay/FreePlaySession.cs)的 202 只代表输入获接收，说明“接受”不能含混代指所有阶段 | 分开请求接收、动作开始与笔记生效；具体时点、代价、恢复方式留机制设计 |
| defer | 通用认知、提醒状态机、异步规划、持久化兼容平台 | 无当前消费者要求这些工程结构；已确认产品语义可在具体场景中先验证 | 待真实机制及运行需求成立再选择；不据此删除用户明确要求的新能力 |

### 交叉质询中修正的主张

- 最小架构者撤回“必须有新原因才能再维护”的过强简写：空计划后也可按约定的等待、思考或时机继续维护。
- 三者都接受“笔记可查询”不足以支持无状态维护者，应补充可发现性；这不要求每次推送全部笔记或新增知识库。
- 语义捍卫者确认，其出发后改计划、中断后续思考的反例只要求行为边界，不要求保留独立权威章节、模块名称或提醒状态枚举。
- 需求怀疑者指出“已接受”可能混淆 HTTP 接收与正式积累。最终以“已纳入角色记录”为信息保证的边界，未把开始即保存写成已定机制。

不存在需要第三轮裁决的理念分歧。剩余选择改变产品机制，不能通过评审人数决定；继续作为正文末尾的开放问题。

## 4. 与现状的关系及下一步

- **理念变化**：当前单次 Intent 边界尚不表达 Plan-Maintainer，旧空间知识文档的当时限制也不覆盖本次方向。正文明确现状与目标，并在旧文入口增加新理念导航。
- **表面冲突已澄清**：当前等待驱动器零 ModelTime，与未来执行“再想想”消耗正 ModelTime，属于不同阶段；本轮没有改变 Kernel 并发合同。
- **保留的机制选择**：计划表达、思考耗时公式、活动并行、中断与笔记生效、一般编辑成本、空计划节奏及材料整理。无需为完成本轮理念文档而先裁决这些问题。
- **候选最小验证切片**：移动计划 → 自动推进 → 维护机会 → 修改或保持 → 带笔记再想想 → 正耗时与再次维护。先用该情境比较机制，再写施工工单；本轮不实现。

可观察的简化：合并一处重复章节；没有新增类型、API、状态枚举或依赖。审查证据来自用户要求和当前源码，不把三个评审者或派生文档算作三个独立产品需求来源。
