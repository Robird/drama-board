## 2. 审查方法

采用用户指定的 `dialectical-simplification`：三位独立审查者分别担任需求怀疑者、最小架构者、语义捍卫者。审查期间只读；先独立提出论点，再交换最强反例进行交叉质询。主会话核对证据并修订，必要时仅对未收敛事项进行第三轮。

每项论点包含位置、主张、需求来源、当前消费者、复杂度、最小替代、删除后的失败轨迹、裁决与置信度。共同阅读同一用户提案不算三个独立需求来源。

### Stay 补充审查边界

本轮独立评估了：以持续的 `Stay` 指令表达默认待机，用 `[Stay, ...原尾部]` 表达保留安排但不执行，并以有效程序提交统一表达执行授权，取消独立继续/停驻处置。审查将默认条件收敛为“合法维护结果中的完整程序为空”，没有将所有失败合并为空结果。结论见第 3 节。

需保持 U3/U5/U6/U7、World 唯一提交、当前动作与未开始尾部、未来指令入队与执行合法性的区分。需要明确：合法空响应、仍在等待响应、非法/迟到提交、驱动器最终失败分别如何处理；`Stay` 不能产生无限时间候选、永久占住一个 Kernel Step、覆盖在途动作或吞掉故障。首批不增加定时唤醒、主动恢复、循环脚本或 LLM 接入。已有“继续/停驻字段”是此前机制选择，允许有据地替换。

## 3. 裁决

最小模型：一个角色持续保存主观材料与未开始程序；领域规则维护当前执行；一个冻结的维护机会整体接受完整后续程序与主观修订。有效程序就是执行授权，合法空程序同次接受为 `[Stay]`；顺序执行到缺指令、受阻或 Think 完成时交回维护，当前 Stay 持续待机。

| 裁决 | 对象 | 证据、反例与最终处理 |
|---|---|---|
| keep / simplify | World VM 与 Player Process 隐喻 | U2/U3；VM 表示规则和状态所有权，Process 是其中的角色实例。没有第二个世界、独立角色时钟或 OS 线程的当前消费者；用术语表限定含义 |
| keep | 主观编辑与世界/设施状态的区别 | U3；“我已到 D”的文字若能覆盖位置或经历，就直接改变现实。允许改判断，系统事实与执行进度由所属规则维护 |
| keep / simplify | 当前执行与未开始尾部 | U4/U5 与现有出发/到达提交；最后一条移动出发后 Buffer 空，不等于到达。保留边界，执行进度复用 Spatial，避免 Process 再镜像一份运动状态 |
| simplify | 编辑操作族 | 无逐项远程补丁、多人或并发 Programmer 消费者。冻结机会整体替换尾部与主观区域即可表达追加/删改/重排，无须由此引入逐条身份和 patch 协议 |
| keep / simplify | 整体生效与程序授权 | 修改笔记“取消去 D”却未改成功 Buffer 会使行为矛盾，仍须整体接受。有效完整程序统一授权执行：重交原受阻程序表示重试，`[Stay, ...原尾部]` 表示保留不跑；删独立处置字段，不靠 diff 猜测 |
| simplify / keep | 多原因合并与一次需求处理 | 最强反例：Think 完成且 Buffer 空→保持空→马上再发缺指令。首批用一个主原因和可见的空状态，并让一次响应处理该边界需求；无需独立中断对象再合并 |
| keep / simplify | 默认 Stay 的安装时点 | 初始化和 Move 自然耗尽若直接填 Stay，会吞掉最基础缺指令中断。整份合法维护响应接受时才将 `[]` 规范为 `[Stay]`，与主观修订和机会处理一并提交，随后复用普通指令开始路径 |
| keep / defer | 空响应待机与恢复 | U7 允许片段终止，U8 允许按收益采纳 Stay。当前 Stay 不产生自然完成候选；全局无候选正常静止。主动解除、按钮与成本延期；其他世界事件继续 |
| keep / simplify | 执行受阻 | `Move(ac), Move(bd)` 到 C 后第二条不适用，保留原因与尾部并先维护。新合同下重交原序列表示再试，要保留不跑则加 Stay 前缀；同步替换旧“只改笔记就不重试”的描述 |
| keep / defer | 非法提交与驱动器失败 | 迟到/非法输入、未回答、应用取消或驱动器故障不是合法空程序。当前 HTTP/会话测试已有不同消费者语义；保留拒绝/待答/停止/故障，失败后自动待机须有真实外部驱动器需求再设计 |
| keep | Stay 的生命周期 | 永久 await 会阻塞其他事件；`long.MaxValue` 到期会被当前 Step 上界真正执行；零耗时完成会立即穿透尾部。开始提交有限完成，此后 active=Stay、不取下一条、不预测自然结束 |
| keep | Think 的耗时和交回时点 | U6；Think 后直接执行尾部会错过承诺的维护机会，直接加时会漏掉中间事件。固定正耗时与 2500 ms 测试事件足以验证；时间值仅是夹具 |
| simplify | 笔记的当前内容与历史来源 | 当前笔记 N 可显式改为 N2；历史事实不能随之改写，也不能自动把 N 恢复成当前文本。保留来源与续用保证，不要求多套笔记数据库或全历史永久保留 |
| defer | 目标树、脚本、中断平台、完整认知、持久化 | 没有当前消费者要求成为执行核心；按正文第 9 节的真实机制需求重开 |

### 交叉质询与立场修正

- 需求怀疑者初判停驻会迫使新增恢复 API；另外两位也指出静态场景没有恢复路径。U7 将片段终止明确为合法结果，三者撤回首批必须恢复的前提。
- 最小架构者与语义捍卫者接受单主原因；需求怀疑者接受“Think 完成后空状态不能再唤醒”的反例，保留一次边界需求处理，删去首批通用合并要求。
- 基础审查曾用独立执行意愿区分同值 Buffer 的重试/停驻；Stay 补充审查用两个明确程序值表达这一区别，三者同意撤回保留独立处置字段的要求。保留的是行为区别，不是其旧编码。
- 语义捍卫者确认笔记续用保证不禁止显式修改，避免把来源区别扩大成多仓库或不可变主观真相。

### Stay 交叉质询中的具体检验

- **只有空 Buffer 就补 Stay？** 初始化将不再请求 Programmer，最后一条 Move 后也失去维护机会；三者限定为合法响应接受时的规范化。
- **规范化后再普通开始，会否再次唤醒？** 正式接受状态已经有 `[Stay]`，本次机会也已处理；随后正常开始即可。无需强制接受与开始同提交，也无需独立默认指令阶段。
- **原值程序加一条笔记，是否还能表示不重试？** 新合同下它授权原程序执行。改为 `[Stay, ...原尾部]` 才表示保留不跑；必须同步更新 UI 含义、正文和验收，不能仅删字段。
- **Stay 能否删除所有控制状态？** 不能。当前指令、Buffer、维护机会及其关联、受阻原因仍有实际用途；停驻只从当前 Stay 派生，不再维护独立 `Parked` 权威。
- **“最终没合法程序”能否包含所有失败？** 自动待机可能有未来价值，但当前会混同输入拒绝、驱动错误和应用停止。明确结束却无法产出程序的受控降级延期；不引入超时/重试政策来支持 Stay。
- **将来怎样退出？** 没有自然完成不等于不可被世界事件结束。解除规则延期，不能通过改写未开始尾部消除当前 Stay；`[Stay, Think(note)]` 的 Think 在首批保持未开始。

基础模型与 Stay 补充均收敛于行为边界，没有需要第三轮的新失败类别。审查票数不作为需求依据；上述结论由用户授权、当前消费者与具体轨迹支持。

### 文档与现状的差异

现有 Server 在地点逐次请求单一移动，缺少 Buffer、主观修订、Think 与 Stay。`SimulationKernel.Exhausted` 表示全局无候选，`FreePlaySession.RunAsync` 却将非 `Committed` 一律判异常；新工程要允许 active Stay 下的正常无候选。`FreePlayScene.Forecast` 的 AtPlace→决策规则也需按新执行边界调整。保持 Kernel 同步等待、统一提交、查询只读及原输入/故障区别。

可观察的简化：原先已采用单主原因、整体替换和复用领域执行状态；Stay 补充新增一种简单指令，删去独立继续/停驻输入轴及独立 Parked 权威，避免程序与处置的交叉组合。停驻行为本身仍存在；没有新增代码类型、系统依赖或恢复设施。
