# DramaBoard documentation

Start with the repository's [current project state](../PROJECT-STATE.md). The active engine consists of Kernel, Spatial and Host. Hillside uses the ResourceCycle Console as the recommended entry; Microtown remains an economy migration reference; the earlier Player planning and presentation stack remains a frozen experiment.

The [Console layout contract](design/console-layouts.md) describes runtime layout switching, local meta commands and the survival decision layout; [playtest feedback and verification](experiments/console-layout-playtest.md) record the two routes and follow-up refinements.

## Current work

[Living world: town and mountains](codex-goals/living-world/README.md) defines the next phase: fuse Microtown and ResourceCycle into one continuous, resumable world for Human Console players (including Coding Agents) and LLM characters. The first Hillside slice provides continuous town/mountain travel and host controller bindings; see [foundation acceptance](experiments/living-world-foundation-acceptance.md). Production, money, limited daily markets and money gifts now share that world; see [economy acceptance](experiments/living-world-economy-acceptance.md). Resident offers now provide atomic exchange and lifecycle delivery; see [trade acceptance](experiments/living-world-trades-acceptance.md). Immutable saved content, canonical fingerprints and independent world variants are implemented; see [content acceptance](experiments/living-world-content-acceptance.md). Current work belongs in its [work plan](codex-goals/living-world/work-plan.md).

[Character following](design/character-following.md) is implemented: two or three survival characters can voluntarily follow one leader, travel through ordinary movement commands, split up to work, and regroup. Hillside `--characters 2|3` exposes the same rules to Console and LLM controllers, with atomic departure, personal reminders and recoverable per-character arrivals. See [implementation and playtest evidence](experiments/character-following-acceptance.md).

[Microtown and a shared multi-game codebase](codex-goals/microtown/README.md) is complete: a second independent environment now shares Goals, controller invocation and Gym with the survival game, while owning its production, market and resident-trade rules. See the [six-condition acceptance](experiments/microtown-acceptance.md), [Console usage](../src/Microtown.Cli/README.md) and [adding-a-game guide](implementation/adding-a-game.md). The [real-model playtest](experiments/microtown-playtest.md) covers three residents through a 30-hour economic day, market refresh, an exact feedback fork and a guided social trade; it distinguishes natural completion from budget-paused children and records memory limitations. The [design](codex-goals/microtown/design.md) retains implementation contracts, and the [work plan](codex-goals/microtown/work-plan.md) records closure and reopening conditions. `codex-goals/<topic>/` groups finite execution milestones; general architecture belongs under `design/`, evidence under `experiments/`, and project-wide current focus in PROJECT-STATE.

[Character Gym phase one](design/character-gym/README.md) provides readable per-character trajectories, context-linked controller feedback, and fork/continuation from a supported saved decision boundary. See the [usage guide](design/character-gym/usage.md), [engineering acceptance](experiments/character-gym-acceptance.md), [real-model playtest](experiments/character-gym-playtest.md), and [implementation status](implementation/character-gym-plan.md). Improvement experiments and comparative evaluation remain in phase two.

[Character goal management](design/goal-management/README.md) now connects a persistent actor-private goal graph, separate focus and lifecycle state, strict JSON operations, and automatic visibility of unfinished goals in each Context. See [engineering acceptance](experiments/goal-management-acceptance.md), [Console evidence](experiments/goal-management-console.md), and [real model experiments](experiments/goal-management-playtest.md). The [implementation entry](implementation/goal-management-plan.md) links the rules, persistence and frozen-material boundaries; the [LLM decision policy](design/goal-management/decision-policy.md) uses capability-aware fixed instructions without a multi-stage processing pipeline. Broad structured memory/recall is deferred, and the existing survival milestone's genuine Human/LLM cooperation acceptance remains separately outstanding.

The [Attribute threshold forecast design](design/attribute-threshold-forecasts.md) is implemented: each attribute carries frozen threshold/depletion times, while action hints only describe changed assumptions such as leaving shelter. Both layouts and delta rendering share these materials; see [engineering and four-session playtest acceptance](experiments/attribute-threshold-forecasts-acceptance.md).

The [Attribute rate explanation design](design/attribute-rate-explanations.md) is implemented with evaluated contributions and one derived total, shared by physical rates, frozen character observations and all layouts; see [engineering and independent playtest acceptance](experiments/attribute-rate-explanations-acceptance.md). Attribute-local explanations and source-grouped displays are projections of the same material, without a general Buff lifecycle framework.

The [Character context Model](design/character-context-model.md) persists per-character Opening and ordered Items, separating world facts, perception, context lifecycle and diagnostic output. Human Console and pure rendering now consume the same retained materials; see [implementation and playtest acceptance](experiments/character-context-model-acceptance.md). The original [context visibility feedback workset](archive/legacy/controller-context-visibility.md) is archived. The LLM adapter now reuses these retained materials; the longer retention window of incremental UI slice B remains deferred.

The [Human Console command boundary](design/console-command-boundary.md) separates game-action parsing and reusable game documents from human-only meta commands and Console prompts. A single immutable `HumanDefault` / `None` directory controls both prompts and dispatch at session construction. This does not implement an LLM adapter.

The [Incremental UI milestone](design/incremental-ui-milestone.md) records the confirmed rules: preserve event/effect sequences, summarize each affected current value once, report actual effects, and reuse the events in recent history. [Slice A](design/incremental-ui-slice-a.md) implements recorded effect materials, output after commit, semantic state selection, and full/delta session modes for survival; see [acceptance evidence](experiments/incremental-ui-slice-a-acceptance.md). Next is slice B design: the retained history window, capacity, first-observed semantics and durable source identity binding. The original `--play` gathering mode remains full-only; survival and `--duo` share the full/delta presentation.

The [Survival escape milestone](design/survival-demo-milestone.md) defines two phases: a single-character Human Console game, then a two-character experience with an LLM companion, dialogue and gifts. Phase one is complete; see the [implementation contracts](implementation/survival-demo-plan.md) and [final acceptance](experiments/survival-demo-acceptance.md), including two independent successful routes, explained failures and post-fix checks. Spatial exploration, [survival needs](design/survival-needs.md) and [weather risks](design/survival-weather.md) share a single durable game root. Phase two's revised target proceeds through 2A single-character Completion integration, 2B two-character survival and controller routing, and 2C dialogue, gifts and real cooperation; 2A has an implementation and two real model journeys; 2B has [dual-character rules and routing](implementation/survival-duo.md) with [recovery, privacy and real mixed-host evidence](experiments/survival-duo-acceptance.md). [2C communication and gifts](implementation/survival-communication-plan.md) are implemented with [engineering and model preflight evidence](experiments/survival-communication-acceptance.md); genuine Human/LLM cooperative escape remains pending. See [2A configuration and recovery](implementation/survival-llm-controller.md) and [its acceptance evidence](experiments/survival-llm-acceptance.md).

The [gradual modularization plan](implementation/modularization-plan.md) A–D is implemented: application boundaries, the total-unit capacity probe, and an independent Inventory assembly with explicit model registration and local tests; see [acceptance evidence](experiments/modularization-acceptance.md). Further extraction follows concrete gameplay needs. The default demo remains unlimited; saves containing Backpack schema v1/v2 are not supported by the v3 model.

The application-layer ResourceCycle example implements shared resource stock, day/night regeneration and three characters with independent timed gathering through one Console, using Mud as a reference rather than migrating it in place. See [the multiplayer rules](design/resource-cycle-multiplayer-gathering.md) and [acceptance evidence](experiments/resource-cycle-multiplayer-acceptance.md). The original [resource cycle design](design/resource-cycle-demo.md), [prototype scope](implementation/resource-cycle-prototype.md), [batch acceptance](experiments/resource-cycle-acceptance.md) and [single-character slice](design/resource-cycle-play.md) describe preceding experiments.

Spatial implements passage-scoped discovery, one transition-completion seam and time-aware validation. [Runtime derived predictions](design/runtime-derived-predictions.md) keep immutable Contacts in memory, persist business truth and recorded decisions, and rebuild on load; see [current acceptance evidence](experiments/runtime-derived-predictions-acceptance.md). The preceding [persisted-contact acceptance](experiments/local-prediction-acceptance.md) is historical. The [dialectical review](research/local-prediction-design-review.md) and [new-combination discovery survey](research/prediction-discovery/README.md) explain the discovery choices.

ResourceCycle separates durable business state from runtime predictions and fixed bindings; see [the original cache migration evidence](experiments/resource-cycle-runtime-cache-acceptance.md). Multiplayer preserves that boundary: activity deadlines and attention requests are independent, while joining/depletion perceptions and inventory transfers are recorded atomically in business facts. Balance changes to saved movement/growth parameters require separate explicit semantics.

The previous [Spacetime engine TODO / task brief](implementation/spacetime-engine-todo.md) is complete; see the [executed evidence](build-log/0027-spacetime-extraction.md).

This is an investigation, not an approved implementation plan.
