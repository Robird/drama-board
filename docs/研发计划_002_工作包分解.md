## 自主循环协议（2026-08-16 起生效）

用户以极简循环提示词驱动开发，主线会话自主规划与推进。用户标准提示词：

> **继续 DramaBoard 自主开发。按 docs/研发计划_002 的状态表、"下一轮建议"与 repo memory 恢复上下文，自主规划本轮目标并推进；结束时更新状态表与"下一轮建议"并汇报。遇到方向级决策点列出选项与你的倾向，可先按倾向推进不阻塞。**

主线每轮流程（OODA 映射）：
1. **Observe**：读 `agent-checkpoint/memory-notebook.md`（跨会话/跨 agent 交接快照，接手入口）+ 状态表 + 下一轮建议 + `git log`；跑 `dotnet test` 确认基线。（若运行在有 memory 设施的 Copilot 环境可另读 repo memory；其内容已并入 memory-notebook，无此设施的 agent 跳过即可。）
2. **Orient**：对照相关 Design Note 与研发计划_001，评估价值最高的推进方向。
3. **Decide**：定本轮目标（工作包 / 架构决策 / 重构），必要时先写决策再动工。
4. **Act**：细化派发 coder → 独立验收（跑测试 + 审关键接口）→ 逐包 commit → 更新状态表。
5. **Report**：汇报产出、涌现的设计发现、更新"下一轮建议"与 checkpoint（上下文将满时），方向级问题显式列出供用户异步纠偏。

授权边界：
- **自主**：WP 推进与细化、接口探索、Kernel 内决策（记入文档）、测试策略、本地 commit、文档更新、用不同模型 subagent 做异构评审。
- **停下来问**：游戏设计层面的取舍（001 愿景级）、大规模返工（>1 个 WP 的推翻）、引入重量级依赖、修改 atelia repo、任何 push / 历史改写。
- 防漂移机制：设计文档 001–003 是方向宪法；每轮汇报必含"下轮打算"，用户可异步否决；方向级决策在状态表留档可回溯。

### 第一阶段结论（2026-08-16，WP0–WP7 完成后）

Kernel 原型目标达成：确定性循环、同刻语义、坐标寻址 RNG、Activity/中断、replay/fork 均被测试锁定，Kernel 零依赖、零改动扛住五类玩具模型。

进入 WP8/WP9 前需先做的架构决策（候选 D9）：
1. **统一事件 envelope**：当前 DomainEvent.Kind 是 string、payload 是各模型自定义联合类型；多系统共存需要统一信封（含未来序列化/versioning 考虑，与 WP8 Protocol、WP11 落盘直接相关）。
2. **IEventReducer 正式契约**：独立于 ISimSystem，使状态投影在机制上由已提交事件产生，封闭"ResolveResult.World 可与事件描述不一致"的缺口（D2 的最后一公里）。
3. RNG 算法常量与派生规则自 WP7 起视为 replay 兼容契约，变更需显式版本化。

**D9 已裁决并落实（2026-08-16，同日）**：强制 event-sourcing（方案 a）+ EventKind(string Id, ushort Version) envelope + 空事件死循环防护 + 全局 reducer 路由。旧路径（ResolveResult 双轨）删除，五模型+全部 harness 迁移，Bouncing payload 经每球局部时间锚点瘦身（五球二球碰撞 40→13 标量）。87 测试绿。正式条目见研发计划_001 D9。落实过程 spike 实证：方案 b 的 property test 只能覆盖已测场景，方案 a 从类型上消除第二条状态写入通道。

分层依赖：

```text
WP0 骨架
 └─ WP1 时间 ── WP2 队列 ── WP3 循环+Timer
                              ├─ WP4 失效模型 ── WP6 Activity中断
                              ├─ WP5 RNG ────┐
                              │              ├─ WP7 Replay/Fork/属性测试
                              └─ WP8 Protocol ┴─ WP9 PlayerDriver ── WP10 FirstBoard
                                                        WP11 落盘 adapter（WP7 后任意时点）
```

WP0–WP3 为近期包，定义到可直接派发粒度；WP8 起为方向性描述，派发前由主线细化。**实现中发现设计文档与本文档冲突时，以实现中获得的新认知为准，但必须在完成报告中显式报告偏离。**

## WP1：时间语义 primitives

**目标**：实现 Design Note 003 §10–§11 的逻辑时间模型——这是整个 Kernel 最基础的地基。

**范围内**（目录 `src/Kernel/Time/`）：
1. `ModelTime`：世界逻辑时间。readonly struct，内部表示建议 `long` 计 tick（tick 粒度=1 秒或更细，需在 XML doc 中写死并说明理由），支持比较、加减 `ModelDuration`、`ToString` 人类可读（如 `D3 14:13:00`）。**不得**与 `DateTime`/`TimeSpan` 隐式互转。
2. `ModelDuration`：时长。readonly struct，同样基于 tick。
3. `Microstep`：同一 ModelTime 内的因果序，readonly struct 包 `int`。
4. `LogicalTimestamp`：`(ModelTime, Microstep)` 复合排序键，实现 `IComparable<LogicalTimestamp>`，全序。
5. 上述类型实现值相等语义（`IEquatable<T>`、`==`/`!=`、`GetHashCode`）。

**范围外**：wall-clock/presentation time（那是 Host/前端的事，Kernel 不知道它们存在）；日历系统（闰年月相之类，一律不做）。

**验收标准**：全序性质测试（自反、传递、与相等一致）；排序稳定性测试（同 ModelTime 不同 Microstep 按 Microstep 排）；加减运算测试含溢出边界行为（明确选择 checked 或饱和，测试锁定该选择）。

## WP2：确定性事件队列

**目标**：实现 Forecast 候选的存放与全局最早事件选择，语义严格确定：相同候选集合无论插入顺序如何，弹出顺序 bit 级一致。

**范围内**（目录 `src/Kernel/Scheduling/`）：
1. `EventCandidateId`：稳定标识（readonly struct 包 `long` 或 `Guid`——选 `long` 序列号，由队列所有者分配，保证确定性）。
2. `EventCandidate<TPayload>` 或非泛型 + object payload（倾向泛型，由实现权衡后在报告中说明）：含 `Id`、`Due`（LogicalTimestamp 或 ModelTime——见下方开放问题）、`SourceGeneration`、payload。
3. `ForecastQueue`：
   - `Enqueue` / `TryPeekEarliest` / `DequeueEarliest`；
   - **确定性 tie-break**：Due 相同时按稳定次序（如 `(Due, SourceSystemOrder, CandidateId)` 字典序），不依赖插入顺序或哈希序；
   - **staleness**：候选携带 `Generation`；提供按 source 失效（`InvalidateSource(sourceId, olderThanGeneration)`）或惰性失效（Dequeue 时校验 Generation 是否仍有效，无效则丢弃并记录）。第一版允许最简单实现：全量清空重建（003 §4 明确允许），但接口形状要为局部失效留位置。
4. 失效的候选可枚举（调试可观察性，003 §17）。

**范围外**：多线程安全（单线程运行是第一版明确假设）；性能优化。

**开放问题（实现时决策并报告）**：`EventCandidate.Due` 用 `ModelTime` 还是 `LogicalTimestamp`——候选只有时间、Microstep 是 Resolve 阶段才赋予的，还是候选就带 microstep？初步倾向：候选只带 `ModelTime`，Microstep 由 Kernel 在 Resolve 时按阶段规则分配（003 §11 的 μ0–μ4 是 resolve 阶段概念）。

**验收标准**：相同候选集不同插入顺序 → 相同弹出序列（穷举小集合的排列做测试）；Generation 失效语义测试；空队列/单元素/大量同时刻候选的边界测试。

## WP3：Kernel 主循环 MVP + Timer 玩具模型

**目标**：把 003 §3 的 Forecast → Advance → Resolve 循环跑起来，用《基础设施.md》Test Model A（Timer）验收。**本 WP 定义的接口是探索性的，预期在 WP4–WP6 中修订。**

**范围内**（目录 `src/Kernel/`）：
1. `ISimSystem`（名字可斟酌）：最小形状——
   ```csharp
   ForecastNext(worldView, now) → EventCandidate 集合
   Resolve(worldView, candidate) → DomainEvent 集合 + 状态变更描述
   ```
   具体签名由实现探索，但必须保持纯函数形状（D1）：不修改共享可变状态，变更以返回值表达。
2. `DomainEvent` 基础形状：`LogicalTimestamp` + 事件种类 + payload；进入 journal 后不可变。
3. `IJournalSink`（或 `IWorldJournal`）：`Append(DomainEvent)` + 可枚举已提交事件。第一实现 `InMemoryJournal`（就是个 List 包装）。
4. `SimulationLoop`：驱动循环——全量 Forecast → 选最早 → AdvanceTo → Resolve → Append → 重复，直到无候选或到达显式 `until` 时间。时间只能前进（`next.Due >= now` 违反即抛异常）。
5. Timer 玩具模型（放 `tests/Kernel.Tests/ToyModels/`）：三个独立 Timer 分别在 t=10、20、15 触发，断言 journal 顺序严格为 A(10)、C(15)、B(20)，且循环恰好推进三次时间跳跃（无逐 tick 空转）。

**范围外**：DecisionPoint / Player（WP9）；随机性（WP5）；Activity 中断（WP6）；superdense time 的完整 μ 阶段体系（本 WP 只需要"同一 ModelTime 的多个事件有确定 Microstep 序"这一最低保证）。

**验收标准**：Timer 模型测试通过；"时间不能倒退"不变量有专门测试（构造违规候选断言抛异常）；journal 中事件时间戳单调不减。
