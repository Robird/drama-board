# Design Note 002：整体软件架构与技术栈

**状态：概念设计草案**  
**日期：2026-08-09**  
**定位：在 Design Note 001 的项目定义基础上，固定软件边界、运行时分层与当前技术栈倾向。**

---

## 1. 设计目标

本项目的独特性不在渲染技术、物理引擎、动画系统或传统 RPG 基础设施，而在：

- AI Player 的持续主体性与角色化运行；
- Objective World 与 Subjective Belief 的分离；
- 信息、秘密、承诺、关系与记忆作为真正的游戏资源；
- 可回放、可 Fork、可比较的 Journal 世界历史；
- 面向未来 RL / imitation learning 的统一 Player 行动轨迹；
- 一个由少数 Human / AI Players 共同参与、能产生涌现剧情的 Drama Board。

因此技术架构的核心原则是：

> **把工作量集中到项目的个性部分；通用游戏能力尽量使用成熟引擎、成熟库和已有技术。**

同时保持另一个更重要的原则：

> **世界不能属于某个渲染引擎。**

Godot、MonoGame、命令行原型甚至未来其他客户端，都只能是世界的不同观察与交互方式。

---

# 2. 总体架构：Authoritative Host + Player Ports + Replaceable Frontends

目前不建议一开始就建立真实网络意义上的 Server / Client。

更合适的抽象是：

> **一个 authoritative DramaBoard Host，若干 Human / AI Player Driver，以及可替换的 Presentation Frontend。**

概念结构：

```text
                     ┌─────────────────────┐
                     │ HumanPlayerDriver   │
                     │        ↕            │
                     │ Godot Input / UI    │
                     └─────────┬───────────┘
                               │
                     ┌─────────▼───────────┐
                     │                     │
                     │   DramaBoard Host   │
                     │                     │
                     ├─────────────────────┤
                     │ Simulation Kernel   │
                     │ Scheduler / Time    │
                     │ Observation Builder │
                     │ Journal / Replay    │
                     │ Persistence         │
                     └─────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
     ┌────────▼───────┐ ┌──────▼───────┐ ┌──────▼────────┐
     │ AIPlayerDriver │ │ TestPlayer    │ │ RL / RPC      │
     │ Galatea Runtime│ │ Scripted      │ │ Player Adapter│
     └────────────────┘ └───────────────┘ └───────────────┘
```

这个边界应当先以普通进程内 C# interface 实现，而不是立即实体化为网络协议。

核心思想是：

> **RPC-shaped, but not necessarily RPC.**

接口的数据形状应天然可序列化、异步、可取消，但当前实现可以只是同步或异步的进程内调用。

等未来真的需要：

- AI Player 独立进程；
- Python / 外部模型运行时；
- 远程推理节点；
- 玩家编写第三方 AI Player；
- Tournament / batch simulation；

再将其中一个 Adapter 替换为 JSON-RPC / IPC / 网络协议即可。

---

# 3. 最重要的三个边界

第一阶段不应过早设计大量抽象。

真正值得提前认真固定的只有三个 seam。

## 3.1 Player Boundary

```text
DecisionRequest
      ↓
    Player
      ↓
PlayerDecision
```

Human Player、AI Player、脚本测试 Player、RL Policy 都必须共享同一个语义边界。

一个可能的最小接口：

```csharp
public interface IPlayerDriver
{
    ValueTask<PlayerDecision> DecideAsync(
        DecisionRequest request,
        CancellationToken cancellationToken);
}
```

需要强调：Player 永远不能获得完整 `WorldState`。

它只能获得角色合法可知的：

- Observation；
- 当前逻辑时间；
- DecisionPoint 原因；
- 可见 Actor / Object；
- 已知事实；
- 自己的记忆与 Belief；
- 当前允许表达的行动 affordance。

因此必须从架构上保证：

```text
Objective World
      ↓ Perception
Observation
      ↓ Memory / Belief
Player cognition
```

信息不对称不是 UI 技巧，而是 Core 规则。

---

## 3.2 World Boundary

```text
WorldCommand
      ↓
Simulation Kernel
      ↓
DomainEvent[]
```

Simulation Kernel 决定：

- 行动是否合法；
- 世界状态如何变化；
- 时间如何推进；
- 哪些事实客观发生；
- 哪些后续事件被触发。

Player 负责：

- 想做什么；
- 为什么这样做；
- 期待产生什么结果。

因此继续坚持：

> **系统决定“能不能”，角色决定“想不想”。**

LLM 输出应保持类似：

> 尝试做 X，并预期产生 Y。

Y 是角色预期，不是客观事实。

---

## 3.3 History Boundary

```text
External Input
+ PlayerDecision
+ WorldCommand
+ DomainEvent
      ↓
    Journal
      ↓
Replay / Fork / Evaluation
```

Journal 应当从原型第一天就存在。

即使原型代码最终被丢弃，第一批完整运行轨迹也不能丢弃。

> **Prototype code is disposable. Prototype history is not.**

这些轨迹未来可以成为：

- regression corpus；
- AI Player evaluation dataset；
- imitation learning 数据；
- counterfactual replay 输入；
- 世界行为调试样本；
- 自动剧情总结与世界史生成素材。

---

# 4. Simulation Kernel 与 Host 必须分离

建议区分：

## Simulation Kernel

尽量纯、确定、可测试。

概念上类似：

```text
(WorldState, WorldCommand)
          ↓
      Transition
          ↓
DomainEvent[] + NewState
```

Kernel 不知道：

- 当前 Player 是人还是 LLM；
- Godot 是否存在；
- LLM API 花了多久；
- 动画有没有播放完；
- UI 是否打开。

## DramaBoard Host

Host 是 orchestration layer。

负责：

- 逻辑时钟；
- DecisionPoint；
- Player 调度；
- LLM 等待；
- Observation 构造；
- Journal 写入；
- Persistence；
- cancellation；
- replay / fork；
- 必要的 RNG 生命周期管理。

这种区分非常重要，因为未来 RL / batch simulation 应当直接运行 Host + Kernel，而不加载任何图形引擎。

---

# 5. Player 与 Presentation 是正交维度

Godot Client 不应等同于 Human Player。

Godot Application 实际承担两个独立角色：

## Presentation Adapter

负责：

- 世界如何显示；
- Actor 如何移动；
- 动画如何播放；
- 对话框、立绘与 CG 如何呈现；
- 音效和视觉反馈。

## HumanPlayerDriver

负责：

- Human 在 DecisionPoint 选择什么；
- 将鼠标、键盘、菜单操作转为 `PlayerDecision`。

因此可以自然组合：

```text
Godot Presentation + HumanPlayerDriver
Godot Presentation + AIPlayerDriver
Text Presentation  + HumanPlayerDriver
Headless            + AIPlayerDriver
```

这意味着将来可以：

- 让 AI 自己玩，人只观看；
- 用极简 Debug UI 跑完整棋局；
- 用 headless 模式批量跑实验；
- 用统一轨迹格式比较 Human 与 AI 行为。

---

# 6. 当前技术栈倾向

## 6.1 Core / Host

倾向使用现代 .NET / C#。

原因：

- 已有 Galatea / Journal 相关基础设施可以继续复用；
- 领域模型、async orchestration、序列化与测试生态成熟；
- 方便未来做 Headless、CLI、服务化、工具链；
- 与 Godot .NET、Stride 等候选前端自然衔接。

建议核心工程大致拆分：

```text
DramaBoard.Core
DramaBoard.Host
DramaBoard.Protocol
DramaBoard.Journal
DramaBoard.Agents
DramaBoard.Persistence
DramaBoard.Headless
DramaBoard.Tools
```

这里的 `Protocol` 不代表网络协议，而代表：

- DecisionRequest；
- PlayerDecision；
- WorldCommand；
- DomainEvent；
- Observation；

这些稳定的跨边界数据契约。

---

## 6.2 产品表现层：当前首选 Godot .NET

目前更倾向：

> **Godot .NET + 轻量 3D 世界 + 2D 情感表现。**

原因不是追求 3D 画面升级，而是降低长期资产组合复杂度。

3D 适合承担：

- 人物身体；
- 通用 locomotion；
- 骨骼动画复用；
- 武器 / 盔甲 / 花束等附件挂点；
- 场景与空间关系；
- 简单导航；
- 风格化低模环境。

2D 继续承担：

- 角色半身立绘；
- 高情感密度表情；
- UI；
- 对话表现；
- 重要事件 CG。

即：

> **3D 负责身体与组合复用，2D 负责脸与情感。**

Godot 的价值在于已经提供成熟的：

- scene editor；
- skeleton / animation；
- navigation；
- physics；
- UI；
- glTF 资产管线；

这些都是项目不应该重新造轮子的共性部分。

---

## 6.3 Stride：值得保留为技术 Spike 候选

Stride 的优势：

- C# / .NET 原生感更强；
- 开源；
- 3D pipeline 与动画体系完整；
- 如果以后深度改造 Editor，技术气质非常合适。

风险是生态和社区规模明显小于 Godot。

因此更适合以一个小型 vertical slice 与 Godot 做比较，而不是现在直接押注。

---

## 6.4 MonoGame：原型与纯 2D 退路

MonoGame 仍然非常适合：

- 极简快速原型；
- code-first 的 Debug Visualizer；
- 如果最终产品退回纯 2D；
- 不需要复杂场景编辑、3D animation、NavMesh 时。

但如果产品确认采用 3D 人物、骨骼动画、附件复用，则不推荐用 MonoGame 自己补齐大量成熟引擎已经提供的基础设施。

---

# 7. 原型策略：先验证世界，不验证引擎

第一版 DramaBoard prototype 不应该以“做出一个 Godot 游戏”为目标。

它真正要回答的是：

> **这个世界会不会自己转起来？**

因此第一版 UI 可以极端简单：

- 方块表示地点；
- 圆点表示 Actor；
- 线表示连接 / 路径；
- 文字表示当前计划和事件；
- 一个事件列表；
- 一个时间轴；
- 必要的 Human Decision 输入。

例如：

```text
 ┌──────────────────────────────┐
 │            北塔 △            │
 │                              │
 │      Alice ●       Bob ●     │
 │                              │
 │ 酒馆 □──────────────□ 市场   │
 │                              │
 │            Leo ◎             │
 └──────────────────────────────┘

Day 3  18:42

Events:
18:39 Bob 离开市场
18:41 Alice 看见 Bob
18:42 Alice 停止原计划
```

第一原型需要完整跑完一局：

```text
开局
 ↓
形成目标
 ↓
自主活动
 ↓
相遇 / 获得信息
 ↓
改变计划
 ↓
合作 / 冲突
 ↓
产生终局
 ↓
完整 Journal
```

此时最重要的输出不是代码，而是：

- 行动粒度经验；
- Observation 粒度经验；
- DecisionPoint 经验；
- Scheduler 经验；
- 信息模型经验；
- 一批真实轨迹。

在这些经验基础上，再新开正式产品 Project，重新设计稳定接口，是合理的。

---

# 8. 现在不要做的事情

为了控制复杂度，第一阶段建议明确推迟：

- 真正网络 Server；
- 认证与远程连接；
- 动态 DLL 插件发现；
- AssemblyLoadContext 隔离；
- 完整 mod API；
- 通用 ECS 化 Domain Model；
- 自研场景编辑器；
- 自研骨骼动画系统；
- 自研通用物理引擎；
- 自研 NavMesh；
- 为“理论可扩展性”提前加入大量中间层。

先让接口具备未来跨进程的形状即可。

---

# 9. 一个重要实现细节：Decision 必须带版本语义

LLM 推理和 Human 思考都发生在 wall-clock 中，而 Simulation Kernel 使用自己的 model time。

因此 `DecisionRequest` 建议从第一版就包含：

```text
DecisionId
BasedOnWorldVersion
ModelTime
ActorId
Observation
```

`PlayerDecision` 返回同一组关联标识。

Host 可以判断：

- 世界是否仍然处于该决策成立的前提；
- Decision 是否过期；
- 是否需要重新生成 Observation；
- speculative AI response 是否仍然可提交。

这为未来：

- 并行 AI Player；
- speculative cognition；
- RPC；
- cancellation；

留下了非常廉价但关键的基础。

---

# 10. 当前软件架构判断

目前倾向的技术路线可以压缩成：

```text
                DramaBoard.Protocol
                       ▲
                       │
Human / AI Players ────┼──── DramaBoard.Host
                       │          │
                       │     Simulation Kernel
                       │          │
                       │       Journal
                       │
       ┌───────────────┼────────────────┐
       │               │                │
Debug Visualizer   Godot Client    Headless / RL
```

其中：

- **Protocol** 固定语义；
- **Kernel** 固定世界因果；
- **Host** 负责运行世界；
- **Player Driver** 负责能动性；
- **Presentation** 负责可视化；
- **Journal** 保存历史。

真正值得长期保护的是前四者。

Godot 是当前最合适的产品表现层候选，但不是世界本体。

---

## 结语

这个项目不需要先建一个“可扩展游戏平台”。

它需要先建一盘真正能自己运转的棋。

因此当前架构工作的核心不是增加抽象，而是寻找最少、最稳定的边界：

> **Player 只能提出选择。**  
> **Kernel 只负责世界因果。**  
> **Host 负责让时间和参与者运转起来。**  
> **Journal 负责让一切曾经发生过。**

只要这几个边界正确，进程内调用可以自然演化成 JSON-RPC，文字 Debug UI 可以自然演化成 Godot，单机实验也可以自然演化成 Headless Gym。

而项目真正昂贵的设计精力，仍然可以留给最值得的地方：

**AI Player、信息、记忆、关系与涌现剧情。**
