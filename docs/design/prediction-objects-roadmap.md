# 持久预测对象：核心演进草稿

> 2026-10-27。源码调查与后续切片建议；本文件没有对应的核心实现提交。单角色采集已完成，多角色应用片由另一会话并行推进，不由本草稿阻断。新增[发现算法综述](../research/prediction-discovery/README.md)补充局部发现、覆盖维护与时间语义约束；本次文档研究未运行产品构建、测试或性能实验。

## 方向与结论

用户已明确提出下一阶段方向：在继续构造更丰富的世界之前，将 Kernel/Spatial 的全量 Forecast 形状逐步改为子系统创建持久预测对象；对象响应事件，判断是否需要重新预测；事件处理完成后统一重算 dirty 集合。第一版允许所有对象的判断恒为 true，先统一生命周期和代码形状，再改善筛选效率。

这个方向有真实的早做收益。ResourceCycle 已经采用持久预测与订阅，而 Spatial 仍通过规则扫描世界产生临时候选。如果未来移动、施法、生产等分别复制两套机制，应用组合、恢复和诊断会各自增加适配。现在以两个已有消费者收敛一套小契约，比复杂世界建成后迁移更容易保持完整性。

“现在的小 Demo 无须此改造也能运行”只说明它不是当前采集片的技术阻塞，不能据此推断用户不希望优先演进核心。建议完成当前无移动体验片后，在扩大世界之前推进下面的核心切片。具体类型、命名、输出数量、事件载体和阶段边界仍是建议，尚未裁决。

第一版的目标应是统一持久生命周期、事件响应和调试入口。恒 true 的版本通常不会减少重算，新增持久记录还可能增加开销；不能把它宣传为已实现的性能优化。

## 先区分两种寿命

用户口中的“预测对象”适合表示一个可持久的预测过程，但不能只表示当前队列里那条有 Due 的记录。

| 概念 | 生命周期 | 举例 |
| --- | --- | --- |
| 预测者/过程对象 | 随业务过程创建、暂停、恢复、结束；可以暂时没有到期输出 | 太阳花生长过程，日落后仍关心日出；一条通道的接触预测者，暂时没有相交人对 |
| 预测输出/到期项 | 某预测者基于当前状态给出的未来 occurrence；可被替换、取消或消费 | “太阳花第 4 代在明天 09:00 成熟”；“实体 A 当前运动段于 t 到达” |

太阳花日落时取消成熟输出，但不能同时删除预测者及其光照关注条件，否则日出时没有对象负责恢复预测。真正移除资源点时才结束整个过程，并清理它的输出及关注条件。

实现不一定要求每个预测者再创建一个独立 DG 对象。已有持久业务对象加行为种类、稳定身份与订阅描述，也可以承载这个角色。应避免为了名字统一，把同一份业务过程状态复制成两份权威。

预测者不宜一律与业务实体一一对应。植物可以一个预测者输出零或一个到期项；空间接触可先按通道设置预测者，输出该通道的零到多个 contact。将来若证据支持细分为人对预测者，再改粒度。

## 建议最小契约

以下是语义草图，不是要求直接照抄的 C# 公共 API。

```text
持久过程描述：Id、Kind、目标/业务身份、关注条件
持久预测输出：OwnerId、SlotKey、CandidateKey、Due、行为数据

ShouldRecompute(process, committedBefore, businessAfter, noticeBatch) -> bool
Recompute(process, businessAfter, at) -> 完整的新输出集合
PlanSelected(prediction, committedWorld) -> 业务事实与过程生命周期变化
```

- `Kind` 与目标数据由加载后的代码注册表解释；不把 .NET Delegate、闭包、Task 或执行栈写入状态。
- `SlotKey` 只在一个 owner 的输出集合内唯一，便于批量替换、保留无变化输出。第一版可使用字符串或专用值类型，无需通用路径语言。
- `CandidateKey` 仍是调度身份。重算次数、dirty 次数、对象内存地址都不能进入此身份；语义相同的重算应保留相同输出。业务 generation 可用于区分新一轮生长、运动段和新的决策请求。
- `ShouldRecompute` 与 `Recompute` 都只读业务状态，不产生业务效果、不调用 Player、不发布事件、不修改其他预测者。先不允许预测者读取其他预测者的输出作为计算依赖，以避免同一 dirty 批次中的求值顺序和固定点问题。
- `Recompute` 返回零项很正常，表示暂时没有预计发生的 occurrence；不自动销毁过程。
- 第一个公共契约是否支持零到多个输出仍待裁决。建议允许完整输出集合：到达使用零/一项，通道接触使用多项，避免被迫提前建立人对对象及其发现/回收框架。

关注条件首版可以仅表达事件种类与主体/目标 ID；也可以先给所有过程同一批通知，让 `ShouldRecompute` 恒 true。只要事件响应接口和完整替换语义已固定，后续增加粗索引和细判断不改变业务作者的基本流程。

“恒 true 对照”必须绕过所有会漏掉对象的粗筛，使每个仍存活的预测者都进入 dirty；仅让已被错误路由命中的对象返回 true，不能验证遗漏依赖。

## 一个 occurrence 内的阶段

建议沿用 ResourceCycle 的完整转换边界，先只定义预测失效通知，不在此片建立通用业务广播框架：

1. 从已发布预测输出选择赢家；核对其 owner、业务 generation 与当前输出，拒绝失效到期项。
2. 业务规划产生完整业务变化，得到对应 scratch 业务状态，并确定过程创建/撤销与通知批次。通知要保留有意义的变化，不能仅凭前后净差异抹掉中间效果。
3. 撤销过程先移除其全部输出；新过程自动 dirty；被消费输出的存活 owner 自动 dirty，不依赖作者恰好声明了自身完成事件。
4. 对这一转换前后均存活的过程，按稳定身份顺序检查通知；dirty 按身份去重。新过程依据最终业务状态首次预测，不必补收它创建前的历史通知。
5. 所有 dirty 过程基于同一份最终 scratch 业务状态重算。以完整的新输出集合替换其旧输出，保留其他 owner 的输出；此阶段不再改变业务状态和过程集合。
6. 把业务事实、生命周期变化及预测结果装入同一个完整 draft，验证输出不过期、身份唯一等不变量，再由 Kernel 发布 E/S。
7. 下一步只读取已发布输出。恢复只 Fold 已记录结果，不再次通知、不重算、不请求 Player。

这里的“一批”是一笔完整业务转换，不是把同刻多个本来独立的 occurrence 合并。前一个 occurrence 结束后必须完成重算，再选择下一个；不能等一整天或一个 Player 回合结束才修正失效预测。

首版可以在应用/子系统组合规划层完成上述阶段，再把共同部分提取为 Kernel 的预测维护接缝。不能在任意 reducer 的逐条 Fold 内隐式广播和执行预测代码，否则 pending 恢复会改变行为，且同一批 facts 尚未完整时就可能重算。

业务 Fold 是否允许“业务事实已应用、预测表尚未替换”的临时 scratch，必须在实现时明确。完整世界的一致性校验应在整批完成后运行；若某现有子图 reducer 必须逐条保持其局部不变量，预测表可放在组合根，通过最后的预测变更事实更新，避免强迫逐条中间状态也满足跨子图不变量。

完成的 S 不保留 dirty。索引与 dirty 都可作为临时运行数据；注册、输出及业务状态共同持久化。若将来真的需要跨多个提交分摊重算，那是新的持久阶段机，本片不做。

## Spatial 的迁移必须覆盖“发现”

到达和入口日程可以先迁移，接触发现另作一片；不要求先重写空间数学。

| 过程 | 创建与失效依据 | 清理/完成边界 |
| --- | --- | --- |
| 实体到达 | 开始运动；掉头建立新运动段；移除实体取消。沿用已记录 ArrivalDue 与 MovementGeneration | 到达时消费；完成后无在途到达输出 |
| 计划入口变化 | 新建 schedule 时登记；到期行为仍读取当时有效 access 再应用 patch | 到期必须消费，即使最终 access 没变化 |
| 通道接触 | 该通道有人开始运动、掉头、到达、移除或 contact 被消费时重算本通道的人对集合 | 旧运动段的输出失效；已消费的当前段人对不得重新创建输出 |

如果系统只保存“已经预测到相遇”的对象，后来第三个人进入通道时，并没有那个新人相关的对象来监听事件。因此必须有一个持续存在的发现入口。推荐首版按通道保留接触预测者：它在没有接触输出时也存在；成员变化时全量重算本通道，先保持代码简单。也可以显式按新运动段发现人对并创建过程，但那会更早引入动态配对与回收复杂性。

当前 [GraphSpatialReducer](../../src/Spatial/Facts/GraphSpatialReducer.cs) 在掉头、到达、移除时清理旧段的 ConsumedContacts；新预测对象的清理须与同一业务事实协作，不能只删除队列项却留下永不回收的人对过程。

以下是现有语义的迁移对照基线，不能在换表示时无意改变。没有兼容性负担，若算法设计需要改变时间或仲裁语义，可以独立裁决并更新验收，不要求永久保留：

- arrival 使用 ceil；contact 使用 floor；掉头仅允许严格内部时间和位置。
- contact 身份为当前两个运动段及其 generation，消费后同一段对不再触发。
- 掉头和实体移除不会留下旧 arrival/contact 输出。
- 入口权限变化不自动终止已经开始的运动；掉头创建新段时才按当前入口规则检查。
- 计划入口 patch 在到期时针对有效 access 应用；无净变化的计划也必须消费。
- 同刻赢家仍遵循已选择的业务规则与 Kernel 稳定仲裁；不能因更换 candidate 编码而悄悄改变旧基线轨迹。

证据入口：[SpatialPlannerReducerTests](../../tests/Spatial.Tests/Planning/SpatialPlannerReducerTests.cs)、[SpatialKernelAcceptanceTests](../../tests/Spatial.Tests/Acceptance/SpatialKernelAcceptanceTests.cs)、[contact floor 说明](../worksets/passage-contact-floor.md)。

并行[发现算法综述](../research/prediction-discovery/README.md)进一步提出覆盖要求：任何可能成为下一次合法交互的关系，要么已有候选覆盖，要么保证在其可能被选中前完成发现。当前通道成员变化可作为首版充分触发；若以后采用较小邻域或时间窗，则须维护覆盖失效时刻。当前 floor 与同 tick 仲裁下，非几何邻接的人对也可能先胜出，不能直接用相邻换序替代全配对；见[可复现反例](../research/prediction-discovery/dramaboard-constraints.md#三邻接方案的可复现反例)。具体覆盖 API 和内部维护事件阶段仍待裁决。

## 统一形状与性能优化分开验收

改为持久预测对象不等于一步就变成高效增量时间引擎。至少存在四种不同成本：

1. 收到事件后查找可能受影响的预测者。
2. 判断是否失效以及真正计算新的输出。
3. 从所有当前输出中找最早 occurrence。
4. 不可变集合更新、验证和持久发布。

第一版恒 true 可以把第 1、2 项维持为全量；调度也可继续线性扫描第 3 项。获得的是统一对象生命周期与可观察性。后续可先按 kind/target 路由并细筛，再考虑堆或其他时间索引；运行时索引应可从单根恢复重建，不能成为第二份独立权威。

Spatial arrival 的数学 Due 已持久保存，迁移它主要减少重复装配并统一生命周期；contact 目前每次分组及两两求交，更可能从局部失效获益。收益大小需要测量，不可根据重算计数直接推断总时间加速。

也要注意“恒 true 先统一”会同时承担旧扫描成本和新增持久维护成本。这是可接受的阶段性实现选择，但应保留对照和范围，避免把过渡版本当作性能终点。

P1/P2 的具体代码归属需结合 API 验证：共同身份/维护约定可以落 Kernel；业务通知 payload、预测数学与效果仍留各子系统/应用。不要让 Kernel 引用植物、NPC、通道等具体领域类型。

可以先用一个薄 adapter 将持久输出接入现有 IOccurrenceRule，从而小步验证共同维护代码；随后把 Kernel 默认入口命名和职责改为读取预测。若最终仍保留 Forecast 这个名字，应明确它只是只读投影，不允许消费者继续把所有业务计算塞回其中。早期 adapter 是施工手段，不是永久保留两套权威的兼容目标。

无移动的 ResourceCycle 多角色片由另一会话独立推进，不必等待 P2/P3。本核心分支聚焦 P0–P3；更多地点和移动相关业务仍宜在发现契约明确后展开。

## 核心不变量与独立验收

- **完成状态一致**：每个输出有存活 owner；Due 不早于完成状态的模型时间；全局候选身份唯一；无 dirty 悬挂。
- **取消与唤醒分离**：暂停只撤销输出，结束才撤销过程；撤销过程后所有输出和订阅一起消失。
- **消费可见进展**：已选输出被消费或替换，新一轮请求/过程具有相应业务身份；不靠增加重算计数绕过 Kernel 的重复 cause 保护。
- **计算无副作用**：反复重算得到相同输出，不改业务 RNG、库存、角色状态或外部世界。
- **同批一致快照**：所有 dirty 过程读同一最终业务状态；过程生命周期与业务结果一起发布，观察不会看到“世界已变、旧预测还有效”的完成状态。
- **恢复不决策**：E 已保存后，中断再开只应用 facts；预测注册与输出不因重放重复添加。
- **可发现新组合**：不存在旧输出的关系也能在正确事件后产生新输出，尤其是暂停植物和新增运动人对。
- **有界生命周期**：结束的过程、旧段输出、消费记录与运行时索引可回收，不按运行时长无限积累。

验收不能只让“持久表读回后再选出的赢家”互相比较，因为一张遗漏预测的表也可能自洽。至少需要三个不同层次：

1. 手写边界轨迹：暂停/恢复、同刻完成、取消、第三人进入、新段与旧段区分。
2. 独立全量参考：从业务事实重建应有预测集合，比较身份、Due、payload 和赢家；随后比较完整轨迹。参考实现不得依赖增量 dirty 集或直接返回被测预测表。
3. 发布恢复：完成 S 冷开、关键 E-only 中断、连续与重开轨迹对照；普通恢复不调用预测代码，必要的重建检查属于显式诊断。

调度合规检查继续有价值，但“对保存的预测表正确选了赢家”不能替代“预测表没有漏项”。建议把预测完整性校验作为独立测试/诊断模式，避免冷开时为了验证而偷偷改写已发布事实。

## 替代方案与风险

**只在每个系统内部缓存 Forecast**：短期改动少，也可能减少 CPU，但取消、注册、冷开和诊断仍各自定义，不能满足统一形状的目标。可以作为性能局部技巧，不适合作为本方向的终点。

**只持久化有 Due 的输出，不保存过程**：到达日程较容易，但暂停植物和尚无接触的人对缺少唤醒/发现入口。若依靠全量业务扫描补回入口，其实把第二套生命周期藏了起来。

**先建完整通用事件总线**：会引入投递中增删订阅、重入、级联事件、持久队列和重放语义。当前目标只需要变化批次→失效判断，没必要一次承担这些机制。业务协作先由显式 transition 规划组织。

**运行时堆是唯一预测存储**：冷开必须重建全部业务预测，更新与世界发布又容易错位。若以后用堆，应将其视为持久输出的可重建索引，并定义失效项校验/清理，而非独立权威。

主要风险是遗漏创建/取消路径、误把暂停当结束、预测键因重算变化、contact 发现漏项，以及为了通用性让规则能在通知/重算阶段任意修改世界。这些风险可通过上述小契约与两种已有消费者暴露，不需要先搭完整 RPG。
