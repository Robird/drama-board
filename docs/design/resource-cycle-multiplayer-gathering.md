> 历史命名说明：本文保留当时的 ResourceCycle / Cycle 类型、命令与验证记录。当前应用已重命名为 Playground；现行入口与持久身份边界见[重命名说明](../../docs/implementation/playground-rename.md)。旧名称源码链接固定到重命名前的 Git 版本。

> 用户已授权按本文实施；库存再生、三角色有限采集及加入/耗尽感知已落地。实现范围与实际验证见[多人采集验收](../experiments/resource-cycle-multiplayer-acceptance.md)；题材扩展和规则包抽取仍为后续方向。

## 1. 目标、价值与范围

术语按[项目术语表](../glossary.md)：本文 Player 指角色控制器（CharacterController），当前代码入口为 `ICycleCharacterController.ChooseCommandAsync`；三个 Character 共用人类 Console，不表示已有三个独立控制器实例。唤醒控制器与角色的耗时活动是独立维度。

在现有 ResourceCycle 中做一个单地点、两种植物、三个角色共用 Console 的可玩原型。角色各有技能、背包和独立行动；资源共享，不预留，先完成采摘者取得资源。通过争夺同一存量自然产生选择与冲突，暂不实现战斗。

从玩法看，存量、补货和个人采集速度构成可解释的竞争：先到不等于先得，高技能者后来也可能先完成。从 Player 体验看，有限批次避免逐份唤醒，但外部竞争变化仍可以提前让玩家介入。从实现看，只预测下一个补货或行动完成时刻，无需逐 tick 更新，也无需同时征集各人的行动后再统一解算。

这套规则值得先做，但不能把“资源操作”“Player 获得控制权”“时间推进”混为一种状态。尤其是：**收到感知可以唤醒 Player，而角色当前活动继续存在；查看消息与选择继续不损失采集进度。**

首个实现不引入移动、LLM API、技能成长、战斗、装备增益、聊天/笔记系统或 RuleSuite 插件框架。无旧档兼容要求。应用内规则稳定后，再判断哪些应成为可复用规则包，哪些才是引擎能力。

## 2. 资源点与产出

| 内容 | 推荐语义 |
| --- | --- |
| 资源点 ID / 名称 | 独立于产出物品 ID；资源点不是一件物品 |
| 产出 | 一次成功采摘消耗库存 1 份，从产出表选择一种物品，获得该物品 1 件 |
| 采集技能及最低等级 | 如采药及等级门槛；门槛与速度分别计算 |
| 基础采集周期 | 无加速时完成一份所需的正数时间 |
| 再生周期 / 条件 | 累计符合条件的时间，每完成周期补充 1 份 |
| 最大容量 / 当前余量 | 正整数容量及 `[0, Capacity]` 内整数余量 |

首片两种植物均用单项产出表；先验证竞争，不强行加入随机掉落。多项权重表的语义已经明确：正整数权重、每次只选一项，不是每项各判定一次。将来实施时使用稳定确定性抽样，事实记录抽中的具体物品与数量；恢复不能重新抽样。不要仅为这个扩展先存一个尚未使用的 RNG 子系统。

再生与采集是两个独立过程：

- 未满容量时累积再生进度。采走一份不清零其他已累积的再生进度；否则高频采集会阻止补货。
- 满容量时停止再生，不暗中存储溢出进度。满仓后首次采走一份，才从零开始下一份再生。
- 昼夜切换只控制再生是否进行；暂停时保留不足一份的进度。已经存下的太阳花夜间仍可采，月光草白天亦然。
- 再生到期恰逢昼夜边界，先兑现刚结束的时间区间已长成的一份，再切换光照。
- 没有“倒计时每帧减一”。持久化进度锚点、有效累计量和过程参数，派生下一次完成预测。

建议试玩参数：D0 16:00 开始；两点容量各 5、初始库存各 3、初始再生进度 0；太阳花白天每 3 小时补 1，月光草夜间每 4 小时补 1；基础采集周期均为 1 小时。三个角色采药等级分别 0、1、2，门槛均为 0。这只是便于出现竞争的初始配置，不是平衡性结论。

## 3. 技能、活动与有限批次

每个角色只有一个耗时活动槽：空闲、等待或采集。空闲时可启动活动，忙碌时不得直接覆盖原活动或同时启动第二个。读观察、帮助等查询不占活动槽；未来有状态效果的即时操作也不应因“忙碌”被一概禁止，但仍须检查各自条件并提交事实。

推荐原型速度公式：`speedPercent = 100 + 25 × skillLevel`，`durationTicks = ceil(baseTicks × 100 / speedPercent)`。使用安全的整数运算，时长至少一个 tick；输入及计算溢出应明确拒绝。例：基础 60 分钟，等级 0/1/2 分别用 60/48/40 分钟。

每个采集周期开始时记录具体时长与截止时刻。首片技能固定；以后技能或增益变化默认作用于下一周期，不通过重建缓存追溯改变正在进行的周期。立即改变在途速度必须另行设计显式业务事件。

建议命令：`gather <resource-id> <1|n|all>`。`n` 为受支持的正整数；接受命令时统一转成有限整数目标：

- `1`：最多成功取得一份。
- `n`：最多成功取得 n 份，不要求当前库存已有 n 份。
- `all`：**命令实际接受时**该点当前余量的快照，例如当时有 3 份，则目标永远为 3。它不是资源预留，不是“追着未来再生一直采”，也不是保证原先的三份都归你。

开始条件：空闲、已知且可接触的资源点、技能达标、余量大于零、数量及时间计算有效。单地点首片所有资源点均可接触。查询阶段看到的余量不作承诺，接受动作时重新校验。

每次周期完成时，按已提交的最新状态处理：

1. 库存可用且能接收产出：扣库存 1、背包加产出 1、成功计数加 1，作为同一次转换提交。
2. 已达到目标：结束批次，通知 Player 完成。
3. 尚未达到目标：从本次完成时刻无缝安排下一周期，通常不逐份唤醒 Player；本次使库存降为零时，同时形成耗尽感知，推进时间前先让 Player 决定是否继续。
4. 本周期结算时无货：结束批次、保留先前成果，告知“目标 n，取得 k，本周期结算时资源已空”。不站在原地自动等再生。
5. 容量/数值边界导致无法收取时，结束并报告具体原因；不先扣资源再失败，不将预期业务阻塞变成异常退出。

能安排第一周期不代表任意长批次都能在时间表示范围内完成。成功收取后若下一周期的时间计算溢出，保留本次成果并以“无法继续安排时间”结束；不能回滚已经合法完成的这一份或崩溃退出。

**库存从正数降为零时，唤醒仍在该点采集的 Player，不自动取消或重置其活动。** 世界停在这一时刻，结算完同 tick 已到期事件后渲染界面、等待合法响应；选择 `continue` 才保留原周期继续推进，选择 `cancel` 则结束活动、随后可安排其他耗时操作。不再让玩家在不知道资源已空的情况下默默继续劳动。

成功后未达目标仍安排下一周期，即便此刻库存为零，但采空者本人也应收到这次耗尽感知；刚安排的周期尚未消耗时间，取消不会损失新周期的劳动。已有批次选择继续时，即使库存仍为零也合法：完成之前可能再生，代价是可能花完一个无收获的周期。初始新开仍要求库存非零；这是新开与明确知情的续采之间的规则差别，UI 必须说明。

因此成功 n 次即结束；若先失败，则 k 次成功后一次失败就结束，周期结算次数不超过 n。这个上界不包括主动介入的感知响应；它保证不会因持续再生而永不交还控制权，不保证现实墙钟时间或面对主动反复操作时的进展。

`cancel` 主动取消当前活动：保留已到手的物品，放弃当前尚未完成的一份，不退款、不发部分产出。以后若有施法/战斗打断，可复用相似结果形状，但本片不先建立通用效果系统。

## 4. 竞争、同刻顺序与控制台轮转

资源没有预约、占位或先到者优先权。各人的完成时刻独立；耗时短者可以后来先得。多人同 tick 完成时采用明确的确定性破平局，不能声称“先完成”已经解决完全同时的情况。

建议保持现有 Kernel 的固定 seed + 稳定 candidate key 仲裁，仅在应用筛选候选阶段规定：

1. 本 tick 的资源再生，再处理昼夜切换；原批处理销毁脚本仍在自然事件阶段，`--play` 不加载该脚本。
2. 本 tick 的所有采集/等待完成，包括成功、失败及自动续周期。
3. 本 tick 的 Player 请求。新接受的启动行动可以产生更多当前时刻的感知请求。

耗尽感知不会插入同 tick 尚未结算完的采集之间。若 A 与 B 同刻争最后一份，先结算 A 的成功及 B 的无货失败，再向 B 一次展示“被取走”和批次结束结果；B 此时已经空闲，没有可继续的旧活动。若 B 的 Due 在未来，则在耗尽时刻即可让 B 继续或取消，不推进到其 Due 才提醒。

同 tick 采集者逐个按最新库存结算，最后一份只发一次；前一人的结果先提交，再结算下一人。不要先把同刻所有人的“成功”预判出来。严格正数的下一周期时长保证本阶段不会自动形成零时间续采循环。

采集 candidate key 只依赖活动身份、周期序号、到期时间等过程身份，不包含注意力版本、UI 文本或世界全局修改序号。观察、通知确认、Console 服务次序不能暗中改变已经安排的抢资源平局。现有仲裁按每个候选独立计算排序值，加入无关候选不会改变原两者的相对顺序；新增真正竞争者当然可能成为赢家。

Player 服务采用应用层持久轮转游标，按固定角色顺序选择下一个有决策请求的人。每次合法修改/响应提交后交棒，查询、帮助和非法输入不交棒。游标影响后续选择，不能只是 Console 临时变量。只服务有请求的角色，忙碌且没有感知者跳过；只有一个人需要决策时可以再次轮到他。

**轮转保证服务机会，不保证资源平均分配。** 不用修改通用 Kernel 仲裁，也不把整个世界变成所有人一轮一次的锁步回合。

只要有人待决策，世界停在当前时刻；所有请求处理完毕后才继续推进到下一个事件。玩家在 Console 前思考多久都不消耗游戏时间。同 tick 已到期的采集先于输入结算，所以不能在其结束时刻的输入界面“抢先取消”已经完成的动作。

## 5. 唤醒不是打断

角色状态分为两个正交维度：

| 耗时活动 | 是否需要决策 | 交互含义 |
| --- | --- | --- |
| 空闲 | 是 | 选择下一活动 |
| 等待/采集 | 否 | 世界继续推进，暂不请求 Player |
| 等待/采集 | 是 | 因感知等原因介入；原活动与完成时刻仍在 |

当 B **真正开始一批**采集时，给当时同点正在采集的其他角色记录“B 加入”感知；B 自己的行动前观察已列出其他采集者。自动进入下一周期不算重新加入，`continue` 也不算。第一片选择每个新加入都可触发，而不是仅从独占变共享时触发。

当资源余量发生 **`oldStock > 0 && newStock == 0`** 的变化时，产生“资源耗尽”感知：

- 通知受影响、在该次转换后仍采集此点的角色，包含取走最后一份但批次尚未达标、已安排下一周期的采集者本人。已经达标结束者通过完成结果得知余量，不重复制造一次交互。
- 通知说明资源点、发生时刻、原因及可感知的行动者，例如“阿白取走最后一份太阳花”。不能从库存差值猜因果；由产生耗尽的业务事实记录。原因未知时明确未知，不捏造抢夺者。
- 仅正数到零的转换触发，不对持续为零逐次提醒；补货后再次被采空是新的真实事件。读取、预测重建、continue 和自动续周期都不重复触发。
- 取走资源、给采集者发放产出和记录受影响者的感知一起提交。感知与活动独立：只需重算相应 attention，不改变其他人的 activity Due。

感知是可恢复的业务状态：包含种类、相关资源、相关角色、来源事件/活动身份和发生时刻。多个尚未响应的加入、耗尽及结束结果在一次请求里合并展示，确认后消费；同一事件不能因恢复或重建再出现一次。资源点成员列表则从当前活动派生，不另存一份易失配的权威集合。

- `continue`：仅确认当前感知并让当前活动继续，保留当前周期截止时刻、时长、成功数、目标数及活动身份。
- `cancel`：终止活动并处理本次感知；角色转为空闲待决策，按轮转规则交棒。
- `:look` / `:help`：查询，不确认感知、不修改状态、不消耗时间。
- 批次自然完成/无货失败：形成结果并请求下一决定；中间成功份数通常只累计进状态与批次摘要，导致耗尽时按上述规则唤醒。
- 其他人离开、普通补货、昼夜切换：更新观察，首片不单独主动唤醒采集者。

决策需求由“活动为空，或存在待响应感知”派生。空闲者始终需要选择下一活动，不能用 `continue` 跳过；`continue` 只接受仍有活动且存在待确认感知的情况。启动新活动、continue、cancel 等合法决策提交，均原子消费本次已展示的待响应内容；之后产生的新感知不在此次确认范围内。空闲者开始下一活动后，不应被旧感知立刻再次唤醒。最近结果可保留为摘要，但不能单独持续制造请求。查询、非法输入及未提交的退出不消费请求。

感知描述过去发生的事，成员列表描述现在：若加入者在接收者回应前已经取消，应显示“曾加入，目前已离开”，而不是把旧通知渲染成仍在场的竞争者。

同理，耗尽通知记录一次已经发生的变化；若响应前同 tick 的其他业务使库存又增加，应同时展示“刚才被取空”和当前余量，不渲染成仍然无货。确认消息不撤销已经提交的资源归属。

可再生资源与唯一资源共用这个感知机制，但续采价值不同。对于不再生、容量为 1 的资源点，取空后应明确显示“资源已被取走，不会再生；继续当前周期不会取得产出”，由玩家选择继续或取消，不再无提示地缓慢开箱。首片仍只配置可再生植物；未来加入宝箱/唯一草药时，需要显式的“不再生”定义，不能仅用一个很长周期冒充。若目标对象被移除，活动本身已不可能继续，则应由该玩法产生“目标失效”的终止结果并唤醒，不能用空库存通知代替终止；本片不扩展对象销毁的通用生命周期。

多个请求合并不等于等待同 tick 所有人先输入。比如 B 加入后 A 已被服务，随后 C 才加入，A 仍可能在同 tick 再次收到感知。不要为凑成一次提醒另造输入阶段屏障。

首片不实现敌意的无限“取消—重新加入”防骚扰机制；一次真实的新活动可再次触发感知。按同一个开始事件去重只防重复交付，不能宣称已解决反复新活动的刷屏。试玩记录唤醒频率，必要时再选择“独占→共享”过滤或每批次每对手提醒一次；不要暗中吞掉尚未表达给玩家的真实变化。Kernel 同 tick 转换上限保留为故障护栏，不能作为正常玩法结束方式。

“即时操作不受活动槽限制”也不等于首片存在后台随时插话线程。Console 只在已获得决策/感知机会时接收输入；独立手动打断 Host、实时聊天、LLM 自主定时唤醒另行设计。未来说话、用物品等即时副作用仍通过同一 writer 规划/提交，不得在输入 provider 内直接修改世界。笔记若被纳入单根 Player 状态，也需要自己的提交语义。此类操作不应隐含 `continue`：例如记录“阿白抢走了最后一份”后仍保持当前交互机会和原活动，直到显式继续或取消；查询不提交，有状态的即时操作单独提交，但不因此确认掉待响应感知。首片只提供现有查询及 continue/cancel，不把尚未实现的笔记工具列成可用命令。

## 6. 面向 Player 的完整观察

优先减少恢复上下文的猜测，而不是只显示命令清单。每次唤醒应同时呈现原因、当前活动、批次目标与成果、下一份到期时刻、自己的技能/速率、资源余量与再生条件、同点采集者、个人背包和合法命令及阻塞原因。

默认玩家视图不展示其他人的技能、采集周期、下一次完成时刻或背包；只显示其身份、正在采集哪个点。一个 Human 轮流控制三人必然可能记住先前见过的信息，首片只约束每个角色视图，不声称实现信息隔离。独立调试输出可显示所有预测，但不要透传给 LLM Player。

示例（展示格式，非运行产物）：

```markdown
# 林间苗圃 · 阿青（a） · D0 16:10

## 本次介入
阿白（b）刚开始采集太阳花。你的采集没有中断，下一份仍于 17:00 结算。

## 你的活动
采集太阳花；开始时选择 all，目标已固定为 3 份；已取得 0/3。
本周期 16:00–17:00；采药等级 0，每份 60 分钟。
每周期结算无货则结束；有货且未达目标则继续，不逐份询问。

## 资源点
| 资源点 | 余量/容量 | 再生 | 正在采集的其他人 |
| --- | --- | --- | --- |
| 太阳花 sunflower | 3/5 | 白天每 3 小时补 1，进度 10/180 分钟 | 阿白（b），共 1 人 |
| 月光草 moongrass | 3/5 | 夜间每 4 小时补 1，当前暂停 | 无 |

空。

## 可用操作
- continue：确认感知并交还控制权，当前活动保持不变。
- cancel：放弃本周期，保留已经获得的物品，随后可选择新活动。
- :look / :help：不消耗时间，也不结束本次介入。

```

空闲视图直接列出 `gather sunflower 1`、`gather sunflower all` 的含义、当前可采数量和阻塞原因，无需枚举所有数量组合。数量不是工具探索后才发现的隐藏参数。资源再生及竞争使整批结束时间不一定等于成功目标 × 周期；可显示“无竞争且可持续取到时预计……”，不要把它写成保证。

耗尽时的介入文本例如：“16:40，阿白取走最后一份太阳花，当前余量 0/5。你的本周期仍于 17:00 结算；若届时仍无货，本批结束。可以 continue 保留本周期，或 cancel 取消后改做其他活动。”同一画面仍展示再生条件和当前进度，帮助玩家判断继续是否值得；不需要先调用工具才能发现关键变化。

## 7. 持久业务、事实与派生预测

继续遵循[运行时派生预测设计](runtime-derived-predictions.md)：业务状态与游标单根发布，缓存冷开重建；正常与 pending 恢复均 Fold → Complete → Validate，恢复不调用 Player 或重新规划。

以下是建议模型职责，类型名在实施中可调整：

| 子图/字段 | 权威内容 |
| --- | --- |
| 世界 | 资源集合、角色集合、固定角色顺序、上次服务角色、昼夜与时间 |
| 资源 | 定义参数及当前库存、再生进度锚点、过程代次 |
| 角色 | 身份、技能、背包、可空活动、待响应感知/结果、请求版本 |
| 采集活动 | 活动 ID、资源 ID、固定目标、成功数、当前周期序号、当前时长与 Due |
| 等待活动 | 活动 ID 与 Due |
| 感知 | 结构化原因及相关身份，确认后移除；不积累无限待办或逐份消息 |

固定三个角色的未响应信息可按感知种类、资源与相关角色聚合成有界记录，保留次数、最近时刻及最新来源身份，不保存无限原始消息列表；没有行动者的耗尽原因使用明确的环境/未知分类。已经完成的批次只留当前结果摘要；完整历史如有需要使用 E 历史，另设有界观察窗口，不复制到每个角色中。

活动代次与注意力/请求版本必须分开：确认感知只消费请求，不能更改当前采集 candidate key。取消再启动才是新活动，自动下一份只推进周期序号。业务中保存的 Due 与时长是已做出的周期安排，不是应该删掉的缓存冗余。

现有每个 owner 只能输出一个预测，建议拆为：

- `resource:{id}:regen`：下一份再生；满仓或光照不符时没有输出，但仍有订阅。
- `actor:{id}:activity`：采集/等待完成。
- `actor:{id}:attention`：当前待决策；与 activity 可以同时存在。
- `light` 与批处理 `script`：沿用原职责。

不需要持久化 .NET delegate。首片可使用固定身份的粗订阅和细检查；成员列表、索引及预测从业务派生。不要为了三个角色先实现通用动态订阅语言。

建议业务事件包括启动、成功采摘、批次结束（达标/无货/主动取消/无法收取）、等待开始/完成、资源再生、光照变化、感知确认。一个 occurrence 可以包含多个事实；结束可以与最后一次采摘同批记录。事实显式分开 ActorId 和 ResourceId，并支持一次替换多个角色子图。

关键原子边界：

- 启动 B 的采集和向同点 A/C 写入感知，在同一组业务事实中提交。
- 扣资源、增加产出、推进/结束当前批次、向受影响采集者记录耗尽感知及形成决策请求，在同一次转换中提交。
- 确认感知、消费请求、更新 Console 服务游标一起提交，S 成功才安装新 wrapper。

**不能在 Complete 中制造感知、发物品、推进批次或抽产出。** 这些都由 Plan 决定并记录进事实，Fold 应用；Complete 只能重算派生缓存。UI 渲染也不能充当通知消费或状态迁移入口。

| 已提交变化 | 需要检查/重算的 owner |
| --- | --- |
| 采集启动 | 本人 activity/attention、收到感知者 attention |
| 采摘成功 | 本资源 regen、本人 activity/attention |
| 库存从正数降至零 | 在上述业务影响之外，收到耗尽感知的角色 attention；保留其 activity 预测 |
| 资源补货 | 本资源 regen；不改变别人的固定采集 Due |
| 昼夜变化 | 受光照影响的资源 regen |
| 感知确认 | 本人 attention；activity 应保持原预测 |
| 取消或完成 | 本人 activity/attention；成员列表由新活动态投影 |

此表列业务影响，不替代“已消费 producer 必须重新预测”的规则：光照变化还必须推进 light 自己的下一输出，批处理脚本也必须推进 script；消耗掉的完成候选不得继续留在缓存中。

服务游标影响 attention 候选选择，在应用的只读 Forecast 筛选中使用；不要因为游标改变就改写全部活动预测。库存改变不需要重排在途采集，因为是否取到是在周期结束时校验。

复用 [CycleDurableHistory](https://github.com/Robird/drama-board/blob/8401bf0e781007a403d3382e4e5e3fa76fd18cc2/src/ResourceCycle/Persistence/CycleDurableHistory.cs) 的单根 E/S 与 S 成功后安装，以及 [OccurrenceScheduler](../../src/Kernel/Scheduling/OccurrenceScheduler.cs) 的同 Due 确定性仲裁；没有修改 Kernel/Spatial 或 DurableGraph。技能首片只支持 herbalism，产出为单一物品；资源 ID 与物品 ID 分离。默认参数使用第 2 节配置。

实施按以下职责分片，实际验收另记，不以这份分工代替运行证据：

1. **库存与有限采集**：替换单株成熟模型为资源点库存/再生；加入活动槽、技能周期、有限目标、完成时库存检查及取消。先用单角色验证语义，原批处理仍用于增量/全量对照；销毁定义为清空库存、重置再生进度，不创建第二套遗留业务模型。
2. **三角色竞争**：集合与身份查找、多角色事实、独立活动 owner、同刻完成与服务轮转；角色/背包各自子图，但仍单根事务发布。
3. **感知与 Console**：attention owner、加入/耗尽感知、continue、聚合、完整角色视图；不输出他人内部速度。到这里才达到本设计的最小可玩闭环。
4. **独立验收与打磨**：代码审查、真实 Console 多角色试玩、冷开恢复、文本校验；记录批次/感知造成的激活次数及是否容易理解竞争结果。

模型与事件契约先由主线程定稿；实现、独立测试和 UI 可以在文件责任清楚后委派。共享 solution/upstream 的构建与 schema 生成串行协调，不并行争用输出目录。

## 9. 验收场景与反例

以下为验收合同；各项的自动测试、真实 Console 证据及未实现边界见[验收记录](../experiments/resource-cycle-multiplayer-acceptance.md)：

1. 目标 `1`、`n`、`all`，后者在命令接受时冻结；高频再生也不能提高目标。普通中间成功不请求输入，耗尽按感知规则唤醒，达标请求一次。
2. 两人同 Due 抢最后一份，仅一人获得；另一个本周期失败结束；不同 Due 时较早完成者取得。无库存负数或重复发放。
3. A 周期中被 B 抢空，在耗尽时刻唤醒 A，时钟不提前跳到 A 的 Due；A continue 后到期前补货则仍成功，未补货则失败；A cancel 则可另选活动。A 自己取空且未达标时也收到感知，已安排的新周期保持零已用时间。
4. stock 为零初始命令受阻，all=0 不生成空活动；技能不足、数量非法、时间/数量溢出均不提交。
5. 不满容量时采集不重置再生；满仓不囤进度、收走后重启；昼夜保留部分进度；补货、切光和采集同 tick 顺序符合规则。
6. B 加入唤醒 A；continue 前后 A 的 Due、活动身份、周期序号及平局 key 不变。自动续份不产生加入通知。
7. 连续加入者聚合不漏身份；确认后不重现同一次加入；真正取消再加入按新活动处理。完成结果与已有感知共存时只服务一个合并请求；空闲者接受新活动时消费已展示的旧感知，不立即重复唤醒。
8. cancel 保留成果、取消未成一份；忙碌启动另一个活动受阻。只读/非法输入不推进；continue 无待处理感知时不能无意义反复提交。
9. 三人不同活动长度自然异步完成，忙碌角色可有 attention；所有自然/活动完成先于本 tick 输入。轮转及感知确认不改变采摘平局。
10. 逐提交边界比较 Incremental、Full、Rebuild 与独立业务公式 oracle；注意力变更不重算无关活动，空输出 owner 能被昼夜/采集事件重新激活。
11. 从 S 冷开继续同轨迹；采摘、加入/耗尽感知、感知确认的 E-only 恢复不重复扣资源、发物品、加通知或调用 Player；已提交确认后的请求不会复活。
12. E/S 发布失败不安装新世界；旧快照及各独立子图不被原位修改；实际存档无预测缓存/委托/Console 对象。
13. 真实 Console 至少试玩一次竞争失败、一次加入感知后继续、一次耗尽唤醒后取消换目标及一次昼夜跨界续局；玩家视图无他人内部速度，清楚区分库存与固定目标。
14. 正数变零触发一次耗尽感知，持续为零、continue 和重建不重复；再生后再次耗尽是新事件。同 Due 的失败结果与耗尽感知合并，不提供已经结束活动的 continue。
15. 加入与耗尽通知可合并且保留种类及原因；读取/非法命令不消费。未来接入笔记等即时操作时，另验收其提交不推进游戏时间、不隐含继续、不丢待响应感知。

## 10. 抽取规则层的条件

当前适合提炼职责，不适合立即承诺一个通用 RuleSuite API。先在应用内分清资源再生、活动执行、感知策略和观察渲染，避免它们全都知道彼此细节。

后续已采纳的[分层与组合设计](layering-and-composition.md)明确：先整理职责，独立测试或复用收益充分时即可提取模块，不强制等待第二个完整游戏。单耗时活动槽、有限重复策略、结果/感知请求、资源余额交易是否进入基础规则包，仍需逐项用例验证；采药、挖矿、钓鱼及题材的中断/产出规则属于领域包。Kernel 继续负责时间、仲裁、事实发布和完成接缝，不内置“太阳花”“背包”“玩家被通知”等规则。

后续重开条件：需要多项概率产出时补确定性抽样；真实唤醒次数过高时比较提醒策略；需要技能增益时裁决在途变化；需要主动插话时设计 Host 输入调度。模块整理按[渐进重构方案](../implementation/modularization-plan.md)推进；当前没有证明通用插件注册、通用事件总线或复杂活动继承体系有必要。
