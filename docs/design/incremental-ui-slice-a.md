## 1. 本片交付与边界

`--survival` 的两个布局都能在同回合输出有序事件、缩进效果与一次最终状态汇总；首次、新回合和冷开全量。提供 `:mode [full|delta]` 与 `:look` 重同步，模式不改变结算。`--play` 本片保留全量作为明确回退，不把多人经历分发夹带进来；帮助应列明当前模式能力，不静默忽略 delta 请求。通用呈现会话仍须隔离角色基线。

本片记录事件的结构化效果到 E，供提交后呈现；不建立角色的最近 n 回合历史集合，不在启动时重放旧屏幕。B 再把同一事件内容保留到角色历史窗口，不从增量 Markdown 解析历史，也不保存一份份旧的当前值汇总。

## 3. 最小数据模型

采用不可变值模型，不做可扩展注册框架、通用事件总线或任意对象树。类型职责如下；非持久呈现类型当前位于 CLI：

| 类型 | 内容与职责 | 所属层 |
| --- | --- | --- |
| `CycleStateKey` | 状态类别、对象 ID、字段；如角色水分、某物品数量、某活动期限 | 游戏观察/事件共用的语义身份 |
| `CycleVisibleValue` | 数值及单位、布尔、文本/标识值，以及显式 `KnownAbsent` / `Unobserved`；有限封闭值类型，不用 `object` 或 Markdown 承载结构 | 游戏值类型 |
| `CycleObservedEffect` | `Key, Before, After`；数字差值由两端计算，不另存一份可漂移的 Delta | 游戏记录 |
| `CycleObservedEvent` | 事实内稳定序号、观察角色、事件种类、发生时刻/区间、必要对象参数、有序 Effects | 游戏记录，存入 E |
| `CycleViewSnapshot` | 从角色观察投影的键值索引，以及全量布局所需的可见信息 | 非持久的呈现输入 |
| `CycleViewUpdate` | 本批有序事件、尾部最新状态条目、必要上下文条目、交付阶段、是否用全量尾部 | 非持久的呈现输入 |
| `PlayPresentationSession` | 当前布局/模式、角色/回合身份、推进中/已进入控制器输入的交付阶段、上次成功写出的完整快照 | CLI 会话 |

`CycleObservedEvent` 不保存尾部当前值汇总，不保存完整观察；事件拥有的只有当时事实及效果。显示名称如需脱离当前背包存在，应在可见事件参数中冻结，不能在输出时重新查询隐藏世界。事件种类和参数使用显式字段/有限记录，不能从 `Result` 或交接文字反向解析。

事件不需要父子树：本片是一条有序事件列表，每条下挂效果。比如“一份采集产出”和“采集目标完成”可成为两条有序事件，库存转移只归第一条，活动结束只归第二条；不要在两个事件中重复记同一效果。

### 三类身份互不代替

- 状态键不依赖章节、行号、中文名称；命令状态按命令种类与规范参数标识，不用显示出来的命令文本做键。
- 已提交事件可用 `(LineageId, TransitionCount, FactOrdinal, EventOrdinal)` 定位；角色投影保留来源身份，不因过滤或重绘重新编号。本片无需把完整提交地址预先塞入 Plan：事实内保存 EventOrdinal，发布后由 completion 补齐来源地址。
- 控制器动作沿用 `OperationRecordId / ToolCallId`，作为来源关联；自然过程不生成工具调用 ID。观察帧和事件 ID 均不代替 ToolCallId。

将来 B 在规划时保存历史需要确定提交地址如何绑定到领域记录，这是 B 的接点问题；本片不为此给 Kernel 新增 ID 服务，也不假定现有 Plan 已收到提交游标。

## 4. 事件和效果怎样形成

`CycleFact` 增加有序的事件材料集合，并在其复制方法、模型注册、Schema 和事实校验中贯通。数据是业务替换值的解释性记录，不是第二套执行指令；Fold 仍只按既有业务字段替换状态，不把 Effects 再应用一次。

由各业务规划函数提供直接事件的语义；由一个应用层收尾函数补齐已知持续过程、观察过滤和结构校验。收尾在最终事实返回前执行一次，不能通过 UI 快照差分生成全部原因。一个事实可以对应零条、一条或多条呈现事件。

### 时间与直接效果的分离

对有身体状态的观察角色，保留三个端点：

1. `before` 在旧世界时刻的投影值。
2. 同一旧状态在 `fact.At` 的投影值，表示此次瞬时结算之前的状态。
3. 最终已计划状态在 `fact.At` 的投影值。

`1 → 2` 属于“这段时间内的身体变化”；`2 → 3` 再由明确的结算分支归属给饮食、天气等事件。例：水分从 80 自然消耗到 72，再补到 100，效果分别为 `-8` 和 `+28`，不能将补给记作 `+20` 或配置收益 `+45`。

本片利用现有昼夜/抵达发生项分段：跨过速率变化前先结清旧区间，再记录新速率。若一个规划分支内部有多个直接效果阶段，应在该分支保存中间端点；仅有最终净差时不能伪造中间过程。没有发生时间推进的 handoff/查询不产生身体变化。

首次先按已提交边界形成过程记录；不增加定时刷新、逐 tick 事件或后台输出。无可感知变化时不输出事件；隐蔽资源的再生不借用公共 `Result` 泄漏远处库存。若连续过程输出过密，试玩后再决定首次呈现前的区间聚合，不事后合并已经展示过的事件。

### 首批映射

| 业务来源 | 事件及效果边界 |
| --- | --- |
| `ItemUsed` | 吃/喝事件；实际身体收益、物品减少。既有警告不在此确认 |
| `WaitStarted / GatherStarted / MoveStarted` | 活动/移动启动；期限、状态、必要的庇护或速率变化，以及该动作实际确认的通知/警告；不能声称已完成 |
| `GatherYielded / GatherFinished / WaitCompleted` | 得到物品、可见库存扣除、进度；如结束，单独表达停止原因与活动结束，效果不重复 |
| `AttentionAcknowledged / ActivityCancelled` | 警告/通知确认，或取消活动；保留已获物品与未改变的期限事实 |
| `LightChanged / WeatherResolved / MoveArrived` | 先期间变化，再昼夜/寒风/抵达；天气使用记录的实际扣除；进入视野是观察范围变化，不记成物体生成 |
| `SurvivalWarning / SurvivalFailed` 及结算中产生的终局 | 期间损失归过程，警告增加/结局状态归通知或终局事件；同一结局只记录一次 |
| `HandoffEdited` | 角色编辑记录与草稿效果，文字内容是意图，不是世界断言 |
| `DecisionContextOpened` | 内部交接边界，不追加“世界发生了新事件”；呈现会话据此全量换页 |

局部可见的资源再生、资源清空按真实事件记录；其他角色的私有身体/背包不进入当前角色事件。对象前值不可见时标记未知，不通过效果端点泄漏；已知持有物品用尽可明确记为数量 0。纯查询、非法输入及布局切换只产生操作答复，不进入游戏事件列表。

确认效果以最终事实为准：`wait/gather/go/cancel` 也会清理通知并确认已展示的警告，不能只为 `continue` 记录确认。将实际清除的通知/警告作为所属动作的效果；没有变化就不生成，已有 `AttentionAcknowledged` 事件承载了确认时不再重复记一条。`use` 与 `handoff` 均不确认警告。效果收尾须检查 Survival 等组合完成后的值，不能在最早的动作规划阶段提前封存效果。

### 校验与恢复

校验至少覆盖：事实内序号唯一有序、观察者合法、键和值种类匹配、直接效果与对应结算端点一致、作用范围符合事件种类；一个键在相邻效果中的已知端点应衔接。持续变化、直接效果与最终业务状态应可核对，不能只验证 Effects 字段不为空。

E 保存明确材料，pending E 恢复不调用规划函数、不重新掷天气、不从当前规则重建效果。冷开本片直接全量展示恢复后的状态，不重放已输出的增量，也不承诺恢复 UI 交付位置。新增 E 字段需要 Schema/GameRevision 调整；具体修订号实施时确定，不兼容旧开发存档。

## 5. 尾部当前状态怎样选择

游戏提供与布局无关的可见状态索引；数值、单位和缺失语义保留结构。范围包括身体与速率/庇护、背包与容量、活动/行程、感知与待确认警告、当前资源/通路、命令可执行性及风险、位置/时间、历史行动结果与草稿等。必要的静态解释可以保留在全量画面；`LastResult` 不再作为一条“当前状态”反复重印事件文本。

设上一份成功写出的完整语义快照为 `P`，此次最新快照为 `C`：

```text
E = 本批事件效果涉及的状态键集合
D = P 与 C 的语义差异键（新增、变化、移除）
R = 理解这些变化必需的少量关联信息
尾部键 = E ∪ D ∪ R
每个键依据 C 的当前观察语义解析一次最新值；缺项须区分已知不存在与不可见。
```

`E` 确保净零过程的状态也进入尾部；`D` 补齐效果之外的派生风险、操作可用性、可见范围等变化；`R` 只放有直接用途的上下文，例如补给后仍待确认的历史警告、当前活动未改变的期限。不把所有身体字段和全部命令都机械加入 R。

直接效果不覆盖“预计耗尽时刻变化”等派生结论；这些只在尾部出现。离开视野用“不再可见”，消耗至零用“0 份”，不能统一显示成“已删除”。`KnownAbsent`、`Unobserved` 与被当前文档省略是不同语义。

当前索引允许稀疏保存，尾部不能仅作字典查找：自有物品缺项按当前背包 `Count(id)` 得到 0；无当前活动或已清空草稿解释为 `KnownAbsent`；原来可见、现在已离开视野的资源字段解释为 `Unobserved`。当前命令条目退出观察仅表示不再是当前可见操作，不能据此推断对象已销毁。缺失分类属于共用投影逻辑，布局不猜测，也不回查完整 World。

这些缺项只为本次选中的键补齐，不要求后续快照永久保留“已删除键”集合。安装基线与重建验收都使用同一规范化语义：物品归零应明确显示一次，后续无关更新不再重复；离开后再返回地点，则重新显示当前可见值。

试玩补充：撤回条目仍须保留原对象与历史/当前的归属标签。新的推进接受后，旧 Incoming 摘要整体退出当前继承区，显示层可以汇总成一条明确的历史摘要撤回说明；语义更新仍包含各键的缺失值。不能把旧摘要中的“食物/活动已不存在”打印成当前身体或活动的“无”。通路离开视野时也必须注明是哪条通路，不能只打印字段名称。

全量与增量共用上述状态身份和值格式化器。结构性验收以语义状态可重建为准；某个值在全量页面的位置、具体分组方式不固定。需要修改字段映射时同时核对完整观察的覆盖，不能因为某个字段没进入索引而把漏显示误判为“未变化”。

## 6. 布局接口与输出会话

建议保留布局注册/切换方式，将输入改为明确的全量快照和更新消息：

```csharp
// 设计草图；不是已存在的 API。
interface IPlayLayout {
    string Id { get; }
    string Name { get; }
    string RenderFull(CycleViewSnapshot snapshot);
    string RenderUpdate(CycleViewUpdate update);
    string RenderActionHelp(CycleObservation observation);
}
```

两个布局复用事件与缩进效果的基本渲染器，以及最新状态的选择结果；布局只决定分组、名称与文字组织，不决定哪些效果属于哪个事件。用户可调的排版和可验证的语义消息结构分离。

`PlayPresentationSession` 拥有输出 writer、回合分隔策略和完整基线；不持有可写 World。主循环把已提交的角色投影交给它。`Prepare → Write/Flush → InstallBaseline` 在同一个串行 owner 内完成，无并发发布和通用 ACK 框架。失败后停止当前交付或使基线失效；后续恢复只能重新全量，不能从未交付的中间帧继续差分。

| 入口 | 输出及基线处理 |
| --- | --- |
| 首次/新角色/新 ContextSequence | 输出回合分隔线（终端青色、重定向纯文本），输出一次完整画面，建立基线 |
| 同回合提交完成 | delta：事件/效果＋尾部选择；full：相同事件/效果＋完整当前状态；成功后安装 C |
| 下一次 `ChooseCommandAsync`，同身份 | 进入可输入阶段；如交互可用性的说明变化，先补一小段必要更新，再显示 prompt；状态与交付阶段都未变时只提示输入 |
| `:look` | 当前布局全量，不新增回合分隔线，替换基线 |
| `:layout <名称> once` / `:help` / 拒绝 | 独立答复，不改变当前布局基线，不确认警告 |
| `:mode full\|delta` / `:layout <id>` | 显式切换后全量重同步；同回合不新增回合分隔线；帮助枚举合法参数 |
| 内部 `DecisionContextOpened` | 等下一次控制器入口全量换页，不先在旧屏打印一份同样的观察 |
| 终局 | 本批终局事件/效果之后展示一次冻结完整状态，代替本批普通尾部；主循环不再重复输出终局全文 |

prompt 收敛为角色/输入标记；[Human Console 边界重构](console-command-boundary.md)后由 `PlayPresentationSession` 统一生成，不属于布局接口。身体与可响应操作由正文表达。游戏推进中没有输入机会时不显示可输入提示；命令区以暂停交互的状态表达，不让暂时受阻的动作看起来立即可用。

交付阶段仅是宿主的非持久状态：返回合法操作后进入“推进中”，只有真正进入 `ChooseCommandAsync` 才进入“可输入”；本地查询/拒绝保持可输入。不能用 `NeedsDecision` 或某条命令 `Rejection == null` 代替这个阶段，因为同刻还可能先结算环境、抵达或其他完成事件。推进中可说明当前动作条件，但不能宣称现在已接受输入。阶段变化不制造领域事件、不改动作校验、不新设 Kernel 回调；界面表达会话是否接收输入即可，无需给每条命令复制一套临时受阻原因。

## 7. 从输入到输出的实际调用顺序

1. 控制器读取操作：按现有流程先记 Received 和 ToolCallId。查询/拒绝在本地完成并答复，合法操作返回 `CycleControllerOperation`。
2. 业务规划生成替换事实及事件效果，完成现有 Survival/Observe/Continuity 组合和事件校验。尚不输出成功事件。
3. Kernel 发布 E、发布 S、安装世界；失败时不展示未提交成功的事件或新状态。
4. CLI 收到 `StepStatus.Committed`，先保存该操作的结果记录，再将 completion 内的可见事件与当前观察交给输出会话。当前 `CompleteOperations` 取消直接 WriteLine，`PrintPublicChanges` 的职责合并到同一通道；提交完成本身不将会话标为可输入。
5. 输出会话生成本批更新；写出后安装完整语义基线。再次进入同角色控制器时，按交付阶段补必要提示并显示 prompt。自然事件走同一路径，但没有伪造的工具结果。

一次正常 completion 是本片的默认输出批次，包含该提交内按记录顺序排列的所有事件；不要一直等待到长活动结束。同一批的尾部取全部效果键并集，故一个键仅输出一次最终值。

操作日志仍是 receipt/result 审计，不在本片升级为可重放的完整 Console 会话。成功操作保存由事件结果材料产生的语义答复，避免沿用静态补给描述而记录错误收益；屏幕上的相关当前状态是额外观察，不能宣称日志已保存完整屏幕。查询答复仍先记结果后显示，既有 ToolCallId 配对和不重复执行恢复合同保持不变。

正常 `CompleteOperations` 与冷开 `ReadCommittedOperations` 是同一个“已提交事实 → 语义操作答复”投影的消费者；该投影放在 ResourceCycle 应用层，不依赖布局或 CLI。两条路径都使用原 E 中的事件材料，不从当前状态反算，不新增另一份持久结果文本。`ExactResult=false` 允许恢复答复不逐字复现旧界面，不允许实际收益或来源 ID 不同。比如水分 90 → 100 的补给，S 成功后若操作结果尚未写入，冷开补录仍应是实际 +10，不能退回静态 +45 的描述。未接入事件呈现的 `--play` 可保留原有结果路径，生存模式不能因漏接材料而静默回退。

## 8. 验收与施工顺序

自动验证以下合同，不固定屏幕布局：

- 实际补给收益与库存扣减；满值附近裁剪；保留警告；非法输入无事件。
- 已有待确认警告时，合法 `wait/gather/go/cancel` 将实际确认列为所属动作效果；`use/handoff` 保留警告，`continue` 不重复记录确认。
- 多事件同一键先减后增：事件过程完整，尾部只一个最终值；没有重复归因。
- 时间积分与寒风分离，庇护免损，昼夜与抵达改变速率；净零也能解释。
- 已提交事件顺序、可见端点、不泄漏远处当前状态；内部交接没有虚构世界事件。
- 语义基线加更新与当前快照一致；物品用尽、取消、命令移除、风险变化都覆盖。
- 最后一份物品消耗后效果为 -1、尾部为 0，随后无关更新不重复；离开地点显示“不再可见”，返回后重新显示当前值。
- 连续零耗时操作不重印完整画面；新回合、冷开和 `:look` 可独立理解；两个布局、两种模式一致。
- 输出写入失败不安装假基线；E/S 中断恢复不重新规划、不重复执行；终局不重复显示。
- 裁剪补给的 E/S 已提交但操作结果缺失，冷开补录仍保留同一实际收益和操作身份；同刻连续提交期间不产生虚假的输入机会。

施工建议分三个可复核步骤：先接通一个 `use` 的真实效果从 E 到呈现消息并验证裁剪，再覆盖自然过程与其他事件，最后统一两布局/输出会话并做完整流程验收。第一步是开发纵切，不能把只支持 `use` 宣称为切片 A 已完成。

工程通过后由不了解实现的 subagent 做独立 Console 与终端试玩，重点检查当前值、效果、历史警告的辨认，以及输出量是否被大量过程事件或 prompt 抵消。全量/增量输入轨迹应得到相同游戏状态；本片运行证据集中在[验收记录](../experiments/incremental-ui-slice-a-acceptance.md)。

## 9. 已采用的边界与留给 B 的工作

本片采用：事件材料写入事实 E；提交后统一输出；稳定状态键驱动最终值去重；布局共用语义消息；冷开全量。它修改 ResourceCycle 的事实 Schema，但不增加 Kernel 接口、CharacterController 回调或完整对话持久化。

B 再决定历史集合位置、回合归组与 n、首次获知记录、持久提交身份绑定、窗口裁剪与可选注号。A 不创建这些空框架。若本片事件材料的具体序列化形状在编码前有调整，应保持三个已确认规则和上述可观察合同，而不是维护未发布的 API 形状。
