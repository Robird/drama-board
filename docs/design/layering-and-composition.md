# 分层、领域模块与游戏组合

状态：已采纳的架构方向；逻辑边界现在建立，物理拆分按实现证据推进。本文不表示已有通用组件、RuleSuite 或 mod 运行时。当前事实与施工切片见[渐进重构方案](../implementation/modularization-plan.md)。

## 1. 目的与决策

让后续代码更容易写在合适的位置，并保留按玩法证据调整模型的空间。现在明确职责、依赖方向和协作合同；不预先为所有设想创建程序集或通用接口。

- 逻辑模块可以先用普通类型、文件和命名空间表达。它不是固定基类、ECS 组件或 DI 注册单元的同义词。
- 职责明确、依赖方向成立，且独立测试或复用有实际收益时，可以提取程序集；不强制等待第二个完整游戏。
- 多个独立用例是验证抽象的有力证据，但不为证明复用而制造空壳消费者。尚不清楚的共性先留在应用层。
- 这替代此前“必须出现第二个独立玩法才评估基础规则包”的机械门槛；广泛通用化仍需实际组合经验。

## 2. 四类逻辑职责

| 职责 | 拥有的决定 | 不应承担的决定 |
| --- | --- | --- |
| 执行核心 | 模型时间、发生项仲裁、转换与发布/恢复协议 | 物品种类、背包容量、伤害公式、NPC 行为、游戏修订政策 |
| 世界机制与规则模块 | 一项领域能力的状态、局部约束、查询、规划/应用规则及必要预测 | 硬编码某个游戏根、擅自发布整个世界、要求某种 UI |
| 具体游戏及组合逻辑 | 选择并连接模块、跨模块行为、世界根、初始化、内容与玩法、整体修订政策 | 另建一套与 Kernel 竞争的时钟或提交权威 |
| 交互与运行适配 | Console/Markdown/GUI、控制器运行设施、磁盘/API 适配与启动接线 | 因渲染而改变领域真相、在恢复时重新决定已记录事实 |

这是职责分类，不是四个必须一一对应的程序集，也不是要求每次调用逐层经过四个 facade 的流水线。游戏可以直接使用确有需要的 Kernel 类型和领域模块。适配器可以针对具体游戏实现，具体游戏向外声明所需契约；最终可执行入口完成接线。

当前对应关系：

- [Kernel](../../src/Kernel/Simulation/SimulationKernel.cs) 提供执行协议，保持不引用具体游戏。
- [Spatial](../../src/Spatial/Simulation/SpatialSimulation.cs) 是可选的空间能力，依赖 Kernel；不并入 Kernel，也不要求所有角色或所有 demo 使用空间。
- [Host](../../src/Host/SimulationHost.cs) 是通用驱动循环。它属于运行适配职责，但仍可保持现有独立核心项目地位；名称分类不要求搬迁。
- [Inventory](../../src/Inventory/ItemInventory.cs) 是独立领域模块，只依赖 DG，提供不可变数量快照、单份接纳和可选总件数上限；不拥有角色、资源点、时间或发布入口。
- [Goals](../../src/Goals/GoalRules.cs) 是独立目标图模块，提供局部纯编辑、校验与 DG 注册；角色所有权和原子发布由游戏负责。[CharacterControl.Completion](../../src/CharacterControl.Completion/LlmDecisionLoop.cs) 提供无跨角色语义记忆的调用/反馈循环，[CharacterGym](../../src/CharacterGym/GymJournal.cs) 提供宿主证据记录和导出；各游戏适配自己的强类型 Context、完成边界与操作结果。后续双游戏验收由[小镇目标](../codex-goals/microtown/README.md)驱动。
- ResourceCycle 同时包含领域状态/规则、具体场景与游戏持久化适配；[CLI](../../src/ResourceCycle.Cli/PlayConsole.cs) 提供当前展示与人类控制器。职责有待进一步梳理，不宣称已经完全物理隔离。

### 基础机制与规则不要混同

“基础设施”过于宽泛，不用它承诺所有常见玩法都是底层能力。商店、NPC、笔记本和语言交互要按具体职责拆看：库存与交易政策、角色状态与决策策略、笔记内容与编辑规则、LLM/API 传输分别处于不同位置。

效果也有两个层次：记录并应用已决定变化的协议属于核心机制；中毒、免疫、打断、叠加顺序和伤害公式属于领域规则。当前 `CycleFact` 是具体游戏的替换事实，不能仅因名字含“效果”就提升成所有游戏必用的通用 Effect 模型。

模块的尺度可以不同：库存是较小能力，一组战斗规则可能是较大的组合。仙侠或生存类规则包可在真实组合出现后提供成套默认规则；不要求它们拥有统一继承树。

## 3. 依赖与状态所有权

目标依赖方向如下，箭头表示使用关系，不是必须新增的项目引用：

```text
可执行入口 → 游戏组合 + 交互/存档适配 + Host
游戏组合   → 领域模块 + Kernel
领域模块   → 明确需要的底层能力（可含 Kernel、DurableGraph）
Spatial    → Kernel
Host       → Kernel
```

- 下层不能引用 `CycleWorld` 等具体游戏根来取得所有上下文。新提取模块接收完成工作所需的状态、参数或窄查询能力；不先创建一个通用 `IWorld` 取代根依赖。
- 模块之间可以存在明确、无环的语义依赖；无需强行做到彼此零引用。依赖多项能力的行为放在组合逻辑中，其复用程度决定留在具体游戏还是成为组合规则模块。
- 子图有明确所有者，变更通过业务 API/规划结果表达。共享只读定义和显式引用可以存在；“独立子图”不等于禁止一切引用，也不等于存档分库或独立事务。
- 已交付的业务快照不能因模块操作被原地修改。运行时 wrapper 与持久根可共享同一份业务状态；缓存不是另一份可独立修改的世界。
- 不为了逻辑纯度移除现有 DurableGraph 标注、另建同构 DTO 层。是否分离 Persistence 程序集由实际依赖收益决定。

## 4. 跨模块行为：显式组合，统一发布

以一次采集成功为例，资源模块决定可用份额，库存模块决定接纳结果，采集组合规则协调资源、背包、活动和感知。**应产生同一转换中的完整业务结果**，不能由资源模块先提交扣除，再由背包模块单独提交入库。

1. 在当前边界上规划完整结果，包括所需的业务通知；规划不修改已发布状态。
2. 正常 Step 先 Fold 应用草稿事实、Complete 准备派生缓存、Validate 检查候选最终边界，再依次发布 E、S；S 成功后安装运行状态。准备失败不留下新的 E。
3. pending 恢复应用已记录结果，不重新询问控制器，也不按新命令门槛重新判断该份战利品能否获得。

单根 S 保存相关子系统与游标的一致结果。**E 与 S 仍是两个发布边界**，允许 E 已发布而 S 尚未发布；这里的原子业务结算不等于一次不可分割的 E/S 磁盘事务。详细执行与恢复合同以[E/S 设计](durablegraph-occurrence-persistence.md)为准。

目前 [CyclePlanning](../../src/ResourceCycle/CyclePlanning.cs) 通过一个 `CycleFact` 的资源与角色替换表达多项变化。这是可继续使用的实现，不要求为了分层改成通用效果列表、事件总线或模块事务协调器。

依赖绑定与 dirty 集合主要用于筛选需要重新预测的单元。它们不能暗中产生业务收益、通知或额外提交。业务因果可以显式组合，不把一次交易拆成顺序隐含的监听回调链。未来若确需可扩展的规则反应链，应另行定义顺序、终止和恢复合同。

## 5. 变体与抽象的验证方式

“无限背包”和“有容量背包”先视为用例，不能直接推导继承设计：

- 若物品数量表示相同，仅接纳条件不同，可共享库存表示并组合容量政策。
- 若出现格子、重量、嵌套、自动整理等不同操作语义，可以采用独立实现；消费者只依赖自身确需的能力。
- 当前 `ItemInventory` 共享数量表示，支持无容量限制与总件数上限；默认 demo 未设置玩法容量，单项仍受整数范围限制，不能将“无限”解释为任意精度或保证永不拒绝。
- 已实施的容量探针保留开始/结算两时点检查，单份全收或全拒，拒收不扣资源；采集时序由游戏编排决定。完整合同及证据见[重构方案 C](../implementation/modularization-plan.md)。格子、重量、动态调容量等其他语义仍需独立用例，不能在提取库存时顺手决定。

优先用不依赖 `CycleWorld` 的模块测试与一个有明确规则的约束用例验证接口。通过后再决定是否独立程序集；若仍需大量可选参数、类型分支或游戏根回调，先缩小抽象。

## 6. 游戏初始化、修订与展示边界

具体游戏拥有总根与组合工厂。领域模块可以提供子图工厂、局部校验、重建和迁移辅助；总根身份、跨模块引用及最终就绪校验由游戏组合协调。工厂所有权合同见[初始化与修订设计](game-initialization-and-revision.md)。

当前继续采用游戏级 `GameRevision`，S/E 各自标注自身表示。模块拆分不自动引入多模块版本协调器。文件移动、CLR 标识符变更、DG Schema 改动、游戏语义修订是不同问题，逐项核查；不能通过搬程序集绕过旧表示解码要求，也不能把架构整理变成兼容性工程。

展示读取业务信息并决定如何表达，不成为规则执行的必需条件。但文字不一定都是可删除的 UI 杂质：当前 `CycleFact.Result`、`CycleCharacter.LastResult` 和 `CycleNotice.Reason` 已随业务历史保存。未来提取文案时须明确哪些是历史叙述、哪些是可重建显示，保持冷开与 pending 恢复的一致性。

角色可见上下文由游戏构造；控制器局部会话、共享运行设施和角色长期记忆的边界继续遵守[无状态控制器决策](stateless-character-controller.md)。当前控制器接收 `CycleDecisionContext` 的观察结果与纯命令校验，Console 不再直接读取完整世界；这不是同进程恶意代码的安全隔离。领域模块可以支持观察查询，但不必绑定 Markdown、GUI 或某个 LLM SDK。

## 7. Workshop / mod 是扩展来源

mod 不固定放在层次顶端，其内容在相应位置接入：

| mod 种类 | 初期可用的接入方式 | 需明确的责任 |
| --- | --- | --- |
| 内容 | 普通对象定义、子图工厂、程序化生成函数 | 稳定领域 ID、初始化所有权、被引用内容的完整性 |
| 规则 | 源码模块与显式组合代码 | 依赖、规划/事实/恢复语义，与其他规则的冲突处理 |
| 完整游戏 | 游戏根、组合工厂与可执行入口 | 总体玩法、存档/修订支持范围、适配选择 |

当前方向是源码引用、共同编译、显式注册/接线，不要求现在提供统一 mod API 或登记机制。规则替换由组合代码明确选择，不依赖程序集扫描顺序或“最后加载者胜出”。新增模块不得自行建立第二套世界发布权威。

Coding Agent 降低修改源码的门槛，但不消除理解与组合冲突。优先提供可阅读的示例、局部测试和恢复合同，而非提前冻结扩展接口。动态加载、热更新、第三方代码隔离和长期二进制兼容均待真实需求；程序集边界不是安全隔离。

## 8. 物理拆分与未决事项

建立新程序集前，回答：职责是否能独立说明？依赖是否无环且不倒向具体游戏？是否带来真实的测试、复用或变更隔离收益？生成器、Schema、注册入口和存档路径是否仍能验证？没有收益时保留逻辑模块即可。

保留 Kernel、Spatial、Host；ResourceCycle 内部职责与库存容量变体验证后，Inventory 已作为独立领域模块提取。项目/符号映射和验收只维护在[重构方案](../implementation/modularization-plan.md)。其他规则包装配 API 或通用角色模型仍未确定，不由这次局部提取推导。

重新设计的触发条件包括：第二种确需不同语义的库存/战斗用例、具体游戏之外的真实模块消费者、空间与采集接线、LLM 可见性约束，或需要支持独立内容包升级。触发后先补充该用例的合同，再调整抽象；不将这些条件本身当作本轮施工任务。
