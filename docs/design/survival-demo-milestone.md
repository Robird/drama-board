# 生存逃离 Demo 里程碑

状态：一期已完成并通过[工程与独立试玩验收](../experiments/survival-demo-acceptance.md)，一期组合合同见[实施方案](../implementation/survival-demo-plan.md)。二期目标于 2026-10-29 按当前 Context 与 Completion 能力修订；2A 已接入并完成真实模型通关与恢复验收（见[证据](../experiments/survival-llm-acceptance.md)），下一片为 §3.3 的 2B。

## 1. 目标与设计空间

让角色在信息有限的野外，通过补给、探索、规划和互助返回人类社会。时间流逝、地点差异、资源再生与身体需求共同产生选择；不依赖打怪升级、装备成长或复杂制造来支撑玩法。

- **一期：单角色、人类 Console 生存逃离。** 建立可完整游玩的世界，同时验证空间、采集、生存需求和持久化的组合。
- **二期：双角色、人类与 LLM 同伴。** 在一期世界中加入交流、赠与与合作决策，验证角色可见上下文和共享无状态控制器方向。

这是实验原型，不是冻结的产品规格。实施者可以依据电子游戏常识、源码证据和试玩结果，自主决定并调整地名、物品、命令、数值、地图规模、风险分布和局部实现。采用最小可玩的方案，重要语义和调整理由写入对应设计或验收文档。

范围弹性不取消完成标准：不能以“以后再补”为由省掉一期的空间接线、有限信息、生存取舍、随机环境事件、完整结局和恢复验证，也不把二期或通用框架扩张成一期前置条件。若发现核心目标确实互相冲突或依赖外部条件无法满足，应明确报告并提出替代范围。

## 2. 一期：一个人走出野外

### 2.1 推荐起点

默认采用山林迷途题材：溪流、山脊、废弃营地和道路遗迹提供可理解的线索。固定小地图即可，不要求程序化生成。初始建议约 6～8 个地点、分岔与回路、两个通向人类社会的出口；具体规模可调整，但至少形成两条有实质取舍且可完成的逃离路线。

一期只有一个可控角色，不把已有多角色状态模型改回全局单例。资源位于具体地点；移动有时间代价，途中仍受世界事件和生存需求影响。胜利是抵达明确的安全出口，失败是身体状态恶化至明确终点；结局有原因说明，不能继续推进普通活动。

### 2.2 必需玩法

| 能力 | 最小要求 | 可自主决定的细节 |
| --- | --- | --- |
| 探索与移动 | 使用现有 Spatial 能力连接地点、通路和耗时移动；位置只有一个权威来源 | 地图、通路代价、线索文案、途中可用操作 |
| 资源与采集 | 保留资源余量、再生、耗时采集和有限目标数量；只能使用角色可达的资源 | 资源种类、昼夜条件、再生与采集数值 |
| 食物与水 | 消费库存影响身体状态，缺乏补给会影响后续生存 | 指标范围、消耗速率、警告阈值、食物饮水是否耗时 |
| 保暖 | 夜间或暴露地点带来寒冷压力，至少有一种有效应对手段 | 庇护地点、休息、简单消耗材料；不要求制造树 |
| 活动与响应 | 移动、采集、休息/等待；危险阈值能唤醒角色并提供合法响应 | 取消、继续、掉头或就地应对的具体规则 |
| 背包 | 使用现有 Inventory，并补充消费所需的扣除语义 | 是否启用总件数上限；启用后须有合理处置物品的方式 |
| 环境风险 | 至少一种有实际玩法效果的随机环境事件 | 野兽驱赶、天气或其他风险；无需完整战斗系统 |
| 结局 | 可获胜、可失败，原因与关键经历可解释 | 结局文案、初始补给和难度 |

不要求每种活动都允许随时取消。必须在 UI 中说明可用响应，并按现有空间语义处理途中位置，不能以“取消移动”瞬移回起点或复制另一套位置。唤醒与取消活动是不同操作；继续不能偷偷重置已完成进度或活动期限。

危险提示应在玩家仍有机会应对的边界出现。显示已知的持续时间和生存趋势；若某行动可能跨过致命阈值，应给出合理警告。无需精确预告所有隐藏风险，但不能把基础操作代价藏成猜谜。

### 2.3 信息与 Console 体验

每次决策展示当前位置、时间/昼夜、身体状态、库存、当前活动、近期关键事件、可用操作与相关限制。玩家无需读源码即可理解命令和行动结果；非法输入、查看、帮助等不耗游戏时间，也不改变随机结果。

明确区分：

1. 当前直接观察到的事实。
2. 曾观察到的事实，附必要的时间或过期提示；离开地点后不能继续无条件获知其实时库存。
3. 尚未证实的线索或推测，不写成世界真相。

未探索地点、远处实时资源、隐藏风险和出口身份不能因为渲染方便而全部泄漏。可以展示可感知的方向、路标和地形线索。已探索地图与必要经历由游戏按角色维护，先用小而明确的数据结构，不构造通用知识图谱或记忆检索框架。

形成面向控制器的角色观察结果，Console 使用该结果渲染。观察构造读取世界真相；控制器输入不再以整个世界对象作为常规决策上下文。此边界用于体验与 API 约束，不宣称隔离同进程恶意代码。

### 2.4 时间、随机和持久化合同

- 生存变化优先采用“基准时刻的状态＋变化规律＋下一阈值预测”；昼夜、地点、活动、消费改变相关条件时再检查重新预测。避免为了扣数值建立每分钟全世界轮询。
- 由游戏组合空间、资源、角色、生存与观察记忆，统一使用一个 Kernel、一个模型时间和单根发布。模块不能各自跑独立模拟循环或提交部分业务结果。
- 预测和渲染不抽取随机结果。明确风险发生机会，只有选中发生项的规划才决定实际结果；可恢复的随机状态纳入业务状态，结果与随机状态推进一同记入事实。取消、查看和重新预测不得无意重抽。
- 正常执行保持准备/校验后发布 E、S；pending 恢复只应用已记录事实，不重做控制器决定、随机抽样或消费门槛判断。运行时预测冷开重建。
- 同刻到达、需求阈值、风险、完成和输入的顺序在实现切片中明确，并验证组合边界；不由模块注册的偶然顺序决定生死。
- 新游戏、保存、还原、运行就绪继续使用既有工厂与 S/E GameRevision 分界。无旧开发存档兼容要求；格式或规则变化须有明确版本处理，不能静默误读。

### 2.5 代码落点与推进切片

默认就地演进 ResourceCycle 和现有 Console，增加生存场景工厂及职责明确的规则文件。保留原采集场景和批处理作为轻量回归入口，不要求它们启用所有生存机制。若实际耦合证明新游戏程序集更合适，可以调整并记录收益；避免复制两套控制、持久化和规则代码后长期并行维护。

继续遵守[分层与组合设计](layering-and-composition.md)：新玩法先落在应用层，Inventory 的局部消费能力可在模块内增加；空间与生存的交互归游戏组合。不开工通用 Effect 总线、RuleSuite、动态 mod、通用存档框架或统一组件基类。必要的上游小改动以真实消费者与测试证明收益。

建议每片都交付可运行结果，实际顺序可以调整：

1. **走得出去。** 接线 Spatial 与游戏根，完成小地图、地点资源、移动、出口及保存恢复；同时建立最小可见性边界。
2. **路线有代价。** 加入消费、食物、水、寒冷、庇护和危险唤醒，让两条路线形成不同补给/时间取舍。
3. **世界有不确定性。** 加入少量随机环境事件，完善线索、历史观察和结局表达；先验证确定性基线，再调整风险。
4. **试玩收敛。** 独立试玩、修复不合理体验、补齐中断恢复和回归证据，完成运行说明。

每片先核对当前源码与既有验收，再决定局部设计；不要求预先写齐所有接口。适合并行的规则、观察和测试使用有界 subagent 工作包，主线程维护组合契约、复核实际产物并集成。

### 2.6 一期完成标准

一期完成须同时具备以下证据，不能仅以构建通过或一条脚本到达出口判定：

- **可交付：** 有明确的新游戏/续局启动命令、操作说明、胜负条件，普通用户从 Console 能走完整个循环。
- **可玩性：** 至少两次独立完整成功试玩，覆盖不同逃离路线及补给策略；至少一次可解释的失败试玩。试玩者只凭玩家可见信息行动，事后可以读源码诊断。记录关键选择、困惑、修复和剩余限制，避免只写“体验良好”。
- **机制覆盖：** 采集与再生、移动、消费、昼夜/寒冷、危险唤醒及随机风险均有实际运行证据；若两次通关未自然覆盖某机制，补充定向场景验证。
- **信息边界：** 未探索地点及离场资源的实时状态不会泄漏；旧观察与当前事实可辨，非法/只读操作不推进世界。
- **确定性与恢复：** 固定初始条件、随机状态及同一合法动作序列得到一致结果；覆盖移动中、生存阈值附近以及随机结果 E 已发布而 S 未发布的冷恢复，结果不重复、不丢失。正常 S-only 续局与连续运行等价。
- **回归与工程：** 按改动范围运行 Schema Verify、相关测试和既有 Console/采集回归；由主线程独立复核 subagent 报告。无需以此次目标重写无关历史代码。
- **文档收敛：** 将实际运行方法与验收证据存入文档，更新 PROJECT-STATE；明确尚未实现的二期内容与剩余局限，不保留虚假的施工完成状态。

随机测试采用受控种子或明确风险场景，不能依靠偶然遇到事件而使验收不稳定。两次完整试玩用于检查体验；自动化测试用于保证边界，两者不能互相替代。

## 3. 二期：有智能的同伴

最终体验仍是同一世界中两个独立角色，一个由人类控制，另一个由 LLM CharacterController 控制，通过交流、补给与行动安排合作逃离。分三片推进，先验证模型能使用现有游戏，再扩展双角色生存与协作；不把模型接通视为整个二期完成。

### 3.1 复用基础与调查时的缺口

2026-10-29 调查基线：DramaBoard `036f6ef`、相邻 atelia-completion `b91e0aa`。这些是调查时的设计依据，不要求后续固定版本；以下缺口不是完成状态表，当前 2A 实现见[实施说明](../implementation/survival-llm-controller.md)。每片开工仍核对最新源码。

- [角色 Context](character-context-model.md) 已保存冻结 Opening、保留 Items、原始操作与结果、交接文字和待交付经历；复用现有按角色感知、共享 parser、校验和 E/S 恢复，不重造历史摘要或第二份角色知识权威。
- [控制器接口](../../src/ResourceCycle/CycleActions.cs) 每次返回一个 `CycleControllerOperation`，游戏随后解析、校验并提交。一次方法调用不是一个完整决策回合；即时操作和拒绝之后可以继续服务同一 Context。
- [纯 Context 渲染器](../../src/ResourceCycle.Cli/CharacterContextRenderer.cs) 已有，但仍是 CLI exe 内部类型。按适配消费者需要提取必要的共享呈现边界；模型输入不得由截取混合 Console 字节或反解析 Markdown 操作记录来恢复。
- atelia-completion 已提供 Completion 请求、JSON 工具、连接配置、客户端工厂与生命周期管理；二期围绕它做薄映射，不重新实现 provider 协议或通用 Agent 框架。
- 生存场景仍明确限制一个角色；天气效果保存单人结果，获救/死亡是全局终局。原 `--play` 的多人调度、各角色 Context 和背包可复用，但不能据此声称双角色生存已实现。

### 3.2 2A：单角色 LLM 接线

**目标：** 让真实模型通过现有单角色生存场景完成连续决策，独立验证调用、配置和恢复边界。

当前已由 ResourceCycle.Completion 与 CLI `--survival --llm` 实现；两次真实模型自主获救及自动化边界见[2A 验收](../experiments/survival-llm-acceptance.md)。下文继续保留合同与验收要求，不表示整期完成。

首版采用**游戏管理上下文的独立决策调用**：每次 `ChooseCommandAsync` 将当前持久 Context 的完整保留材料映射为新的 Completion 输入，不依赖控制器私藏历史，不续接上一请求的原生 assistant/tool 消息。历史操作反馈作为 Context 材料交付，不伪装成端点协议的 tool-result。同一决策回合仍可有多次调用；它不是“每调用一次就推进游戏时间”。

默认只暴露一个 JSON 行动工具，例如 `act({ command: string })`，包装共享行动字符串入口；名称可在实施时调整。完整响应须恰有一个该工具调用，保留 Completion 交付的 ToolCallId 原值，并分配独立操作记录身份。游戏仍权威解析、校验与提交：合法即时操作或游戏拒绝进入当前 Context，之后再次调用模型；接受放行模拟的行动则关闭旧 Context，经历在下次 Opening 交付。合法操作不一定放行模拟，不新增动作后收尾或 `:end`。

仅接受 Completed 响应中的完整调用。无调用、多调用、错误工具名和畸形工具参数在适配边界处理，不能执行半截结果或默默丢弃多余调用；可解析的行动字符串即使语法或游戏合法性错误，也交给已有持久拒绝流程。网络失败、取消、协议失败不得伪造为角色已执行的游戏操作。

宿主提供可配置的调用/连续失败上限、取消与暂停机制，耗尽后保留已提交游戏状态，不自动代选 wait/continue。具体限额与诊断格式在本片确定；同刻 1024 转换护栏不能代替调用预算。超大 Context 应显式报告或暂停，不能静默丢掉关键材料来凑输入长度。先复用已有保留策略和 handoff，依据真实运行证据决定是否扩展容量。

配置与接线职责：

- 复用 Completion 的连接目录、精确连接选择、客户端工厂及注册表；模型、端点、认证在宿主初始化，凭据与客户端对象不进入游戏图。
- 控制器可共享客户端与运行设施；角色跨决策记忆仍由游戏保存。角色到 Human/LLM 配置的绑定归应用，2A 可只有一个角色，2B 补混合路由；重开时明确绑定，不静默换角色或连接。
- 适配代码依赖 ResourceCycle 与 Completion，Kernel/Spatial 不依赖模型库。开发期优先相邻 Completion 源码引用，统一依赖身份；具体程序集拆分按最小可复用边界决定。
- 旁观输出区分实际模型输入、模型输出、已提交操作和宿主管理信息。模型自由文本不自动成为游戏对白、事实或角色记忆；需要延续的意图使用显式 handoff。

恢复承诺：未发布 E 的请求或响应允许中断后重新调用，结果和计费可能不同；已发布 E 则按既有恢复完成，不再调用模型或重复业务效果。S 已提交但输出未显示时从保存材料继续；不承诺外部调用恰好一次，也不承诺恢复原生推理/完整协议会话。ToolCallId 是关联身份，不是全局执行去重键。

**本片验收：** 至少一个实际配置的模型完成单角色完整旅程，保留输入、操作、反馈和可解释结局；实际使用即时补给及 handoff。协议夹具覆盖多调用、无调用、半截响应、取消和有界失败；合法字符串的游戏拒绝反馈可进入后续请求。覆盖响应完成但 E 未发布、E-only、S 已发布但未展示的中断窗口；已提交效果恰应用一次。模型在端点调用前未配置好属于外部条件，不能以 mock 宣称真实接线完成。

### 3.3 2B：双角色生存与控制器路由

**目标：** 在一个 Kernel、模型时间和发布根中容纳两名生存角色，先用同一 Human Console 或脚本验证规则，再接 Human/LLM 混合控制。角色各自拥有位置、背包、需求、活动、Context 与已知地图；共享一个控制器实例也不能串记忆。

采用最小个人终局政策：个人获救或死亡后停止该角色的普通活动、需求消耗和决策，其他未结束角色继续；全部角色结束后汇总结局。两人均获救为共同成功，否则区分部分获救与无人获救。允许从不同出口获救；已获救角色本期不返场，死亡不复活，不引入拖拽伤员或救援系统。对幸存角色的观察不能无条件泄漏远处同伴位置或个人终局，整局结束后的总结与角色在局内知道什么分开。

天气机会与各角色受到的效果分开：同一世界天气发生项按各角色当时暴露/庇护条件结算，实际损失及可感知记录按角色保存，同根提交；不因控制器调用顺序改变天气抽样。个人终局与世界终局、预测移除及 Context 关闭一起校验，不能只删除单人数量检查。

**本片验收：** 两人独立移动与采集、相同天气下不同庇护效果、同刻请求稳定服务；一人先获救/死亡后另一人继续并最终汇总。覆盖共享控制器交替服务、Human/LLM 绑定、角色可见性、双角色 S 冷开与关键 E-only 恢复。原多人采集和单人生存入口保持可运行。

### 3.4 2C：交流、赠与与合作试玩

**目标：** 提供同地点、不耗模型时间的说话和物品赠与，形成真实 Human＋LLM 合作。

- 说话以显式游戏行动提交，按接收者保存“谁说了什么”的经历。模型普通解释不自动广播；对方所述线索不自动变成亲眼观察或地图已探索事实，同处也不自动共享私有 Context/背包。
- 赠与校验当前同地、对象可交互、物品和数量；一个业务转换中完成双方库存与相关可见反馈，拒绝无部分扣除。受赠者按相同 Context 交付规则获知，不另建第二套聊天日志作为知识权威。
- 收到消息不必取消原活动或重置期限。实施本片时先确定有限的交流机会、轮转、合并通知与明确结束规则，再接唤醒；不能每句话无条件开启新轮、靠 1024 护栏结束正常聊天。不同角色之间要能及时获得回应机会，不因某个控制器持续零时间操作而饥饿。
- 服务决策期间模型时间暂停；控制器返回待校验的原始操作，游戏处理拒绝并继续服务，直至按规则放行模拟。不做后台自主插话、实时联机、远距通讯。默认不新增完整笔记编辑器，handoff 不足时再按证据选择小幅增强。

**本片验收：** 同地交谈和赠与有效，异地/未知对象拒绝不泄漏信息；赠与 E-only 恢复不重复扣取或增加物品；对话、告警与原活动共存且不重置期限。至少一次真实 Human＋LLM 完整共同逃离，记录交流或赠与实际改变了哪些行动和结果，不能以两个角色各走各的代替协作验收。模型、配置、输入材料、关键选择、困惑、调整与剩余限制写入实验文档。

### 3.5 二期完成标准与延期边界

2A → 2B → 2C 各片先交付可运行结果，再推进下一片；局部接口和数值可依据证据调整，真实模型、双角色规则、协作与恢复证据不能互相替代。完成须具备可复现的新游戏/续局/配置说明、上述三片验收、按影响范围的 Schema Verify 与自动化测试，以及原批处理/Console 回归。单片成功不宣称整个二期完成。

首版不前置原生 append-only 工具会话、完整 assistant/reasoning 历史恢复、并行工具批次、长期记忆检索、最近 n 个完整回合窗口、完整笔记编辑器或通用 Agent/RuleSuite 框架。若独立调用在真实玩法中暴露决策连续性或成本问题，再比较原生工具会话；届时明确持久 ActionMessage/结果配对和原生续接材料，不把本期关联 ID 与语义 Context 当作已实现该能力。

需要恢复的角色语义与已提交操作继续单根发布；模型原始输出审计和宿主运行日志不自动成为游戏状态。没有旧开发存档兼容负担，变化依实际 Schema 与 GameRevision 处理。实现完成后更新 PROJECT-STATE 与验收记录，后续内容不得隐含扩展为新的 Goal。
