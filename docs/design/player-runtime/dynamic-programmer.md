# World VM、Player Process 与 Dynamic-Programmer

> 层级：概念模型与最小机制设计。日期：2026-09-17。
> 状态：已完成三角色独立审视与交叉质询；核心语义与首个验证建议已整理，当前未实现。用户已明确选择空响应可停驻并结束运行片段，主动重新唤醒延期。
> 上位产品语义见[运行时理念](README.md)；来源与取舍见[本轮审查记录](../../worksets/dynamic-programmer-review.md)。

## 1. 最小模型

**世界按规则运行角色的已有指令；需要新安排时，唤起 Human/LLM，允许其改写未开始的指令和角色的主观状态。**

```text
合法环境观察 + Process 可读状态 + 本次中断原因
    → Dynamic-Programmer（Human / LLM）
    → 未开始指令的修订 + 主观状态的修订 + 继续/停驻意愿
    → 游戏规则校验并整体接受
    → 按顺序继续执行，或正常停驻
```

长期目标、信念、候选方案、目标树可先存在角色的主观状态中。执行核心只解释已定义的指令；以后可以在指令生成侧增加固定任务方法或规划器。主观文本不会自行成为可执行程序，未来目标也不会仅因写进笔记就自动产生提醒。

本模型延续 Plan-Maintainer 的产品角色，并将“编辑未来安排”明确为对后续程序和主观材料的动态维护。近期 Buffer 可以只有一步，也可以有多步；核心不要求先确定长期规划的数据结构。

## 2. 隐喻的含义与边界

| 用语 | 本文含义 | 不随隐喻自动引入的机制 |
|---|---|---|
| World VM | 游戏规则及其维护的世界、执行设施和合法状态变化 | 指令集模拟器、字节码、任意代码执行、特定脚本语言 |
| Player Process | 与角色关联、持续存在的运行实例；保存主观材料和执行所需状态 | OS 进程、独立线程、独立时钟、独立提交器 |
| 时间 Kernel | 调度世界中的 occurrence，其中一些推进 Process 或请求响应 | 按角色轮流发 CPU 时间片、每条指令固定耗时 |
| Instruction Buffer | 已授权、尚未开始执行的有限顺序指令 | 长期目标树、通用控制流、自动任务分解 |
| Dynamic-Programmer | 在响应机会中阅读材料、提出程序与主观状态修订的 Human/LLM | 对全部角色字段或世界状态的直接写权限 |
| 中断 | 有待交给 Programmer 的响应原因 | 必须立即抢占、停止动作、嵌套中断处理或中断优先级系统 |

“Player”在这里指运行中的角色主体；Human/LLM 是其 Programmer。既有 `Player` 程序集名和 `IPlayerDriver` 不因概念用词自动变更，命名映射交给工程方案处理。

角色 Process 属于世界中的运行实例。对客观属性和执行设施的所有权仍在 World VM；“与某个角色关联”不等于“该角色可以任意赋值”。World VM 是范围性用语，不是新增第二个拥有同一世界的组件。

## 3. 状态的写入边界

| 材料 | 谁决定变化 | Programmer 的权限 |
|---|---|---|
| 目标、信念、猜测、笔记、经历的个人解释 | Programmer 提出，游戏系统按允许的格式接受 | 自由编辑允许区域；猜测可以有误 |
| 实际经历、合法披露的原始信息与来源 | 世界规则与记录规则 | 阅读有资格取得的内容，修改自己的理解 |
| 位置、物资、身体状况、角色能力等游戏属性 | 所属领域规则 | 通过允许的行动影响，不能直接赋值 |
| 当前动作、执行进度、完成结果、已处理的响应机会 | World VM 的执行规则 | 查看合法投影，提出允许的控制请求，不能伪造进度 |
| 尚未开始的指令 | Programmer 提出，运行时接受并推进 | 在维护机会中追加、删除、重排或整体替换 |

角色设定中哪些部分可编辑，由各自领域定义；不能因某个字段被放进 `PlayerState` 就扩大写权限。“我已经饱了”的主观文字不会恢复饥饿属性，“我走到 D 了”不会改变位置。

主观内容的真伪不由通用正确性校验器判定。系统保证它的来源与用途，不将主观断言升级为事实或行动资格。主观状态的具体字段可以先很少，不要求现在建立完整人格与认知模型。

Human/LLM 共用可读范围、可写范围与指令语义。显示格式和输入方式可不同；响应所需的已有笔记、Buffer、实际进度和中断原因应可发现、可取得。

## 4. 顺序指令与执行边界

逻辑上区分**未开始的尾部**和**正在执行的指令**。已完成结果由正式记录说明，不把它们混入待执行 Buffer；是否使用游标、列表或单独字段是工程选择。

客观执行进度复用所属领域的正式状态，例如移动进度来自 Spatial；Process 只需保存额外必要的指令关联与控制信息，不再镜像一份位置或运动进度。

一条指令具有游戏定义的参数、开始条件和结果语义。接受到 Buffer 表示安排获准保存；开始表示世界接受了本次实际行动；完成由实际结果确定。三者不等价。

例如 `Move(ac), Move(cd)`：开始 A→C 后，后续 `Move(cd)` 仍可在允许的维护机会被替换。删除后续指令不撤销正在进行的 A→C。停止、掉头等行为只有在游戏另行提供其语义时才可提出。

Buffer 入队时检查指令种类、参数形状、引用资格等可判定事项；执行时再检查当时的地点、出口与资源条件。未来的 `Move(cd)` 可以先保存，不能因角色此刻仍在 A 就判作不可安排，也不能因此提前承诺 C→D 会成功。

下一条开始前，应先处理此执行边界必须交付的中断。当前动作完成后，依据新结果继续；失败不被当作成功而悄悄越过。已开始或完成的事实不会被程序改写撤销。

MVP 的顺序语义可以只要求每个 Process 同时执行一条指令。长期导航以后可以成为一个具有确定规则的复合指令，条件和循环也可后续扩展；当前无需建立通用脚本执行栈。

## 5. 中断与 Programmer 激活

### 5.1 缺指令是最基础的原因

**Process 需要取得下一条指令、当前无正在执行的指令、也无未开始指令，而且该边界尚无维护机会时，产生缺指令响应需求。** 初始化也可以使用这个原因。已经选择停驻的 Process 不会自动重新进入取指令过程。

最后一条长动作已经开始、Buffer 暂为空时，不代表动作结束；第一版可等其完成后再响应缺指令。提前补充 Buffer 是后续可选能力。

中断表示待处理需求，激活表示在允许的边界请求一次响应。它们与暂停后续执行、停止当前动作分别有含义。首批一个主要原因加当前材料即可解释一次维护，不要求通用中断队列、优先级、注册中心或独立唤醒调度器。

“再想想”完成时，即使 Buffer 也为空，完成所提供的这次维护就同时处理了后续缺指令问题。空 Buffer 在材料中可见，无需再创建一个独立中断并进行合并；本次响应后不因同一空状态追加一次激活。

未来的外部信息、里程碑、意外等可提供更多中断来源。初期用明确领域事件触发；Programmer 自己写进笔记的“危险”字样不会直接触发世界中断。

### 5.2 一次响应的生效

Programmer 读取同一次冻结响应材料，返回对未开始指令与允许主观区域的修改，也可以保持原样；同时明确接受后继续执行还是停驻。修改与本次需求的处理结果经校验后整体生效；HTTP 收到请求不等于正式生效。

无效或迟到响应不能部分改写主观状态、消费响应机会或启动动作。世界只能按照已经正式接受的 Buffer 执行。具体关联标识、版本字段和接口形状属于工程设计。

### 5.3 防止无进展重入

缺指令是响应需求，不是“每次观察到空列表就重新调用 Programmer”。相同条件保持成立时，不能自动形成零模型时间的无限激活。

用户已选择：**允许响应后保留空 Buffer 并停驻，以此结束角色的本次运行片段；主动重新唤醒留待后续。** 不自动插入移动或收费思考，不靠刷新页面制造新的响应机会。仅修改信念不能被当作新的缺指令事件反复触发。

指令受阻也需要相同原则：保留失败位置与原因，停止自动重试；后续是否重试、替换或等待，应由明确响应决定。非法输入、可解释的领域失败和程序内部故障分别处理，不能把实现异常伪装成普通游戏中断。

| 响应内容与意愿 | 后续行为 |
|---|---|
| 提供非空 Buffer 并明确继续 | 尝试下一条指令；受阻后的继续也表示明确授权再次尝试 |
| Think 完成后保留非空 Buffer 并继续 | 从现有尾部继续，不要求为了“保持计划”制造内容差异 |
| 保留受阻安排，仅修改笔记或选择停驻 | 保存安排和原因，不自动重试 |
| 保留空 Buffer | 结束本次需求并停驻，不紧接着再次触发缺指令 |

协议如何表达上述意愿由工程方案选择；不能从列表内容相同/不同、对象引用或指令身份推断重试。角色停驻不阻止其他世界事件；全部候选耗尽时，世界正常结束本次推进，服务仍可展示最后状态。

## 6. “再想想”与两种时间

“再想想”是具有非空白笔记参数的指令。在每次允许维护的机会都可选择；活动执行边界仍受第 4 节约束。

它正常执行消耗规则确定的正模型时间，期间所有到期世界事件照常参加 Kernel 仲裁。正常完成后产生响应机会，即使 Buffer 仍有后续指令，也应先交回 Programmer；本次笔记在这次响应中可发现、可取得。

指令在 Buffer 中、动作开始、笔记正式纳入记录、动作完成是不同语义。已经正式记录的笔记不因中断自动消失；Programmer 后续显式修订主观笔记，与系统丢失已积累材料不是同一件事。实际提交过什么仍由系统事实记录说明。

当前笔记可以从 N 显式改为 N2；系统不把历史中的 N 自动恢复为当前笔记，也不把 N2 说成当时原本提交的文字。这只要求区分当前主观内容与事实来源，不要求多套笔记仓库或永久保留全部历史全文。

等待 Human 操作或 LLM 网络返回消耗的墙钟时间，不直接换算成角色思考耗时。首个验证配置可保留当前 Kernel 合同：一次选中事件等待 Programmer 时，同一时间线停止推进；正式执行“再想想”后再按世界事件推进时间。

不从这个模型推导所有程序编辑免费或收费，也不从“中断”推导边移动边思考。它们是独立产品选择。

## 7. 建议采用的首个验证配置

本节是**供后续工程工单采纳的具体建议**，当前未实现。空响应停驻并结束片段是本轮用户明确裁决；其余配置是审查后保留的最小验证建议，不能倒写成用户已逐项批准的产品定律。工程工单应明确采用或替换建议部分，并保持已确认语义。

| 项目 | 建议配置与目的 |
|---|---|
| 运行范围 | 沿用单角色、单进程内存、四点全图已知场景；Human WebUI，测试可用脚本 Programmer |
| 指令 | 只支持相邻移动和带笔记的“再想想”；有限顺序 Buffer，无分支与循环 |
| 可编辑主观状态 | 一个主观工作区先承载目标/判断文字；思考笔记可续用，当前文本与提交来源按第 6 节区分 |
| 修订表达 | 整体提交新的未开始序列和主观工作区，加上继续/停驻意愿；追加、删除、重排是编辑效果，不需要独立补丁操作族 |
| Programmer 时机 | 同步冻结响应；只在指令边界激活，不实现途中接管 |
| 中断来源 | 缺指令、指令受阻、“再想想”完成；一次维护有一个主要原因，Think 完成与 Buffer 空按第 5 节只响应一次 |
| 思考耗时 | 测试先用一个固定正值，例如 1000 ms；不是角色属性公式或正式数值平衡 |
| 笔记纳入时点 | 建议动作开始正式提交时记录；此前仅是 Buffer 参数，删掉未开始指令不伪造“已经思考” |
| 空响应 | 用户已选择允许停驻并结束本运行片段；首批不提供主动重新唤醒 |
| 受阻后的继续 | 明确继续才重新尝试；可以提交相同 Buffer，也可以改写尾部；仅保留安排不等于授权重试 |
| 修改成本 | 首批只对“再想想”的正耗时作承诺；一般编辑沿用同步响应机会，不新增独立计费机制 |

“停驻”表示角色不再自动产生执行或维护需求，当前安排和状态仍可查看。其他世界事件继续仲裁；无候选时正常静止，不伪造时间流逝，也不关闭服务或重置角色。主动恢复入口、时机与成本不进入首批。

### 7.1 最小可观察闭环

1. 初始化在 A、0 ms、没有指令，以缺指令原因激活 Programmer；页面显示真实位置、主观工作区与响应原因。
2. 写入一条主观目标，安排 `Move(ac), Think(note), Move(cd)`。
3. 规则自动开始并完成 A→C，时间到 2000 ms；普通到达不要求 Programmer 再决定一次移动。
4. 在 C 开始“再想想”，将笔记纳入记录。以 1000 ms 思考为例，完成时到 3000 ms；测试在 2500 ms 放一个独立世界事件，证明期间没有跳过它。
5. 完成思考触发响应；材料含该笔记、当前判断、剩余 `Move(cd)` 与真实进度。Programmer 将后续改为 `Move(ac)`，同时修订主观判断。
6. 角色从 C 返回 A，时间到 5000 ms；后续空 Buffer 产生缺指令需求。允许提交空响应，正常停驻并结束本运行片段。另一条独立验收轨迹可保持原 Buffer，确认 C→D 在 4000 ms 到达。

`Move` 的字面写法仅为说明；最终标识、目标映射和协议由工程方案选择。2500 ms 事件是测试夹具，不要求给正常场景新增无意义的游戏机制。

### 7.2 行为验收

| 验收 | 可观察证据 |
|---|---|
| 自动执行 | 单次提供 `Move(ac), Move(cd)` 后于 3000 ms 抵达 D；C 不调用 Programmer；无逐步 HTTP 驱动 |
| 改写未来 | 思考完成时同时改写 Buffer 与主观判断；已完成移动和模型时间不被修改 |
| 写权限 | 伪造位置、进度或系统经历的修订不生效；主观猜测可保存但不扩张行动资格 |
| 三个边界 | 接收、开始、完成可区分；正在执行的尾指令不会因 Buffer 已空而被误判完成 |
| 中断消费 | Think 完成且 Buffer 空时只有一次维护；保持空、仅改主观文字或保留受阻指令时，不出现同一需求的自动忙循环 |
| 正常停驻 | 空响应结束运行片段，状态仍可读、不报故障；如仍有其他世界事件则继续处理，不增加恢复入口 |
| 失败解释 | 格式非法保留当前响应；执行 `Move(ac), Move(bd)` 时第二条已知通路在 C 不适用，保留受阻条目及尾部并请求响应；明确继续才重试。实现故障独立诊断 |
| 思考与因果 | 正耗时、中间世界事件、笔记续用均成立；真实响应快慢不改变规定模型耗时 |
| 信息连续性 | 刷新页面不会重新执行或丢失 Buffer/笔记；Human 与脚本 Programmer 使用同一材料来源与修订规则 |

## 8. 与当前源码的关系及工程边界

当前 [IPlayerDriver](../../../src/Player/IPlayerDriver.cs)与[PlayerDecision](../../../src/Protocol/PlayerDecision.cs)只表达单次动作意图；[FreePlayScene](../../../src/Server/FreePlay/FreePlayScene.cs)在地点请求移动决定。现有 [FreePlaySession](../../../src/Server/FreePlay/FreePlaySession.cs)提供内存会话、冻结视图与 Human 输入关联。这些证明当前行为，不证明本文能力已经存在。

具体差距：`FreePlaySession.RunAsync` 当前把所有非 `Committed` 结果视为故障，而 Kernel 的 `Exhausted` 只表示全局没有候选。首批工程必须把合法停驻后的无候选处理为正常静止；其他本应推进却缺少候选的规则错误仍应暴露，不能一概吞掉异常。

后续工程需要表达 Buffer、主观工作区、执行与响应进展，并将合法修订及行动纳入同一因果顺序。核心合同至少包括：

- [SimulationKernel](../../../src/Kernel/Simulation/SimulationKernel.cs)仍统一调度与提交；世界规则拥有状态变化，Programmer 返回提议。
- [TransitionDraft](../../../src/Kernel/Simulation/TransitionDraft.cs)要求非空事实。处理响应、修改主观状态等可以是正式领域进展，不需要伪造一次移动。
- candidate 在 Programmer 回答之前确定；仅更换 key 而没有领域进展不能用于规避无进展保护。
- 不能把影响后续调度的 Buffer/执行状态只藏在 UI 或 driver 的可变队列里；存放类型与依赖由工程方案选择。
- GET、刷新与诊断查询只读；Human HTTP 与后续 LLM 输入均不直接修改 World。

首批不需要恢复归档、接入 LLM、引入新 Script VM 或存档格式。角色私有状态的完整续局闭包，等真实持久化任务出现后再设计。

## 9. 后续选择与重开条件

| 待选事项 | 何时需要 |
|---|---|
| 停驻后的主动唤醒入口与成本 | 用户需要继续已经结束的运行片段时再设计；首批正常停驻无需恢复功能 |
| 途中中断、暂停与停止指令 | 某个具体活动需要中途修订或反应时 |
| 思考与移动并行、思考中断 | 有明确场景要求两个活动重叠时；届时明确笔记与未完成动作的结果 |
| 更丰富的指令、循环、选择、脚本 | 顺序指令与已有领域方法无法表达实际所需行为时 |
| 目标树、任务分解、共享子目标 | 指令生成侧有真实需求时；不先作为执行核心的前置依赖 |
| 中断优先级与累积机制 | 已有多个来源产生具体的延迟、丢失或顺序问题时 |
| 人格/信念的结构化模型 | 实际 Programmer 或游戏规则需要读取明确字段时 |

工程方案应从第 7 节的小闭环确定改动、接口与验收，不以 VM 隐喻为理由扩展为通用操作系统或认知平台。
