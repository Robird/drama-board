# Player 运行时与 Plan-Maintainer：关键设计理念

**Human 或 LLM 维护角色的未来计划与规划；共享运行时保留信息、执行已授权的安排，并在需要判断时唤起维护者；游戏规则决定实际发生的结果。**

## 1. 设计目的与层级

先用 Human 可玩的有限虚拟世界验证共同的角色运行时，再接入 LLM。Human 可以尽量依靠系统提供的信息做决策，以发现系统应保存和提供哪些材料；系统不假定 Human 或 LLM 总能自行记住上次经历。

Human 与 LLM 具有不同的判断能力和呈现方式，但应共用信息资格、计划语义、执行规则和注意力机制。固定领域规则可以承担记录、召回、导航和日常执行；这些能力不以通用认知系统为前提。

后续设计分为三个层级：

| 层级 | 回答的问题 | 产出边界 |
|---|---|---|
| 关键设计理念（本文） | 想要怎样的角色与游玩方式，哪些语义应保持？ | 原则、例子、待决问题 |
| 系统机制设计 | 计划怎样推进、何时唤醒、思考怎样付费、意外怎样处理？ | 比较具体候选机制，确定状态与行为规则 |
| 软件工程设计 | 类型、接口、依赖、提交与验证如何实现这些机制？ | 仓库内可执行的施工方案 |

同一理念可以有多个机制，同一机制也可以有多个工程实现。下层方案不得把候选选择倒写成已经确认的理念；若需要改变本文的产品语义，应明确提出裁决。

## 2. 主意识维护未来安排

**Plan-Maintainer（计划维护者）** 是 Human 或 LLM 作为 Player Character 驱动器的主要角色。它读取信息、判断形势，并修改或保留未来安排。

- **规划**：有意图或约束，但尚未确定实施办法。例如“进山前准备好补给”。
- **计划**：已有运行时能够解释的执行办法。例如“去镇上，购买三份食物，再去山口”。可执行不保证成功。
- **执行进度**：实际开始了什么、完成了什么、在哪里受阻。

这是语义区分，不要求三套容器或一种通用计划语言。近期安排通常更具体，远期意向可以暂不展开。缺少必要实施办法时，应请求维护者细化，不擅自补全意图或跳过必要环节。

维护包括追加、细化、重排、替换、撤销未来安排，也包括判断“现有计划仍合适”。单步动作是只有一步的安排；快捷操作应能解释为同一控制语义。

**修改未来必须尊重已经发生和已经开始的事情。** 删除后续目的地不会撤销已经出发的移动。取消未来安排、停止当前活动、让角色掉头，需要各自明确的游戏含义。

## 3. 共享运行时兑现已授权的安排

运行时在授权范围内逐步执行计划，满足完成条件后再推进。指令被接受、动作被尝试和活动已完成，是不同的结果。

每一步仍须符合实际执行时的游戏规则。可以提前安排尚不满足当前地点条件的活动，例如抵达旅店后住宿；计划可接受性与当前动作可执行性分别判断。

“不出意外就继续”必须由游戏能判断的条件表达。例如下一段路可走、必要资源足够、没有出现指定危险。条件不满足时，应保留剩余安排和原因，按已约定的行为暂停、修订或请求维护；扩大花费、绕路等自由度需要属于先前授权。

运行时只能根据角色合法拥有的信息作选择。世界掌握完整地图，不等于角色的导航可以利用未知道路或远方未被获知的动态变化。

计划、进度与注意力由游戏系统持续维护；已授权部分的自动执行和信息记录不依赖界面刷新或反复调用驱动器。角色私有状态也可以是系统正式维护的状态。组件划分和具体存放位置留给工程设计。

**世界规则决定实际结果。** 计划修订与实际行动须处于一致的因果顺序中；修改有明确的生效边界，只能影响届时仍可修改的未来，不能把预期直接当成结果，也不能悄悄撤销已开始的动作。

## 4. 信息可以记录、关联并按规则召回

运行时维护角色已获知的地图、经历、情报及对后续判断有用的笔记。自动执行期间仍应记录合法获得的信息；主意识尚未被调用不意味着这些信息丢失。

有限游戏世界可以直接提供结构化情报。例如某段 NPC 发言使角色获得“樵夫说后山小树林有怪响”的条目；进入后山时，地点规则将这条材料召回。实现这一行为不要求从自然语言中推断全部语义。

信息应保留必要的来源和语义区别：

- 亲眼观察的内容也可能已经过时。
- 听过一个说法，不代表该说法为真。
- 维护者写下的判断、候选或排除理由，可以被后续证据修订。
- 系统曾提供某条材料，不保证 Human 或 LLM 已经相信或正确理解它。

**记录、召回、要求重新判断各有含义。** 一条材料可以长期保留、在相关场景中出现，却不必每次出现都打断执行。同等角色状态下，Human/LLM 的信息取得资格与可取用范围应一致；呈现、取用方式可以不同，也不要求每次展示全部材料。需要续用的材料应有可发现的入口，不能让一方可查、另一方无从得知其存在。

## 5. 注意力负责把问题交给维护者

里程碑、计划用尽、执行受阻、意外、取得思考机会以及收到外部信息，都可以成为唤醒原因。具体触发条件、合并方式和优先次序由机制设计确定。

一次维护应让维护者理解：当前形势、相关材料、计划与进度、这次为什么需要判断、可以如何处理。维护者可以只改变较远的安排，也可以保持现状。

**唤醒主意识、暂停计划、停止当前动作是三个不同的效果。** 例如坐船途中收到目的地商店关门的消息，可能只需修订抵达后的安排；船是否继续前进，取决于世界与活动机制。

本次维护结束后，即使保持原计划或计划为空，也应有明确的后续推进或等待含义。同一条件仍成立，不能在没有进展的情况下自动造成反复唤醒。下一次维护可以来自新的判断需要或事先约定的时机；具体规则留待机制设计，无需据此规定独立提醒对象或固定状态枚举。

## 6. “再想想”：用游戏内时间继续思考

### 6.1 始终保留这个选择

在每次能够维护计划、选择下一步的机会中，**“再想想”始终可选**。没有可行路线、暂时不知如何细化目标或尚未作出决定，都不应使维护者失去这个选择。另设的思考机会或资源规则不得将它隐藏或耗尽。

“始终可选”表达维护者的行动资格；它不承诺随时发生一次新的维护机会，也不承诺越过正在执行的动作立即生效。何时可以接管和怎样安排执行，属于下一层机制。

### 6.2 必须带一条有助于继续思考的文本

选择“再想想”必须填写非空白的文本参数。其语义是**积累一条供下一次思考使用的信息**，例如一个子问题、已经排除的方案及理由、值得进一步考察的候选或待验证假设。

例如：“桥已确认关闭；下一步比较渡船和绕山路线，先查渡船的时间。”

这条文本是可复用的思考笔记，不要求记录完整思考过程，也不承诺结论正确。正常完成“再想想”后，下一次思考必须能发现并取得该笔记；只存于请求日志或不可发现的查询入口不算兑现积累。已纳入角色记录的笔记，也不能仅因思考被打断而悄然丢失。

请求被接收、动作开始和笔记纳入角色记录，不自动表示同一个时点。具体纳入时点及此前被打断时文本如何处理，由机制设计明确。这里要求连续游戏中的信息可续用，不预设跨进程持久化。系统不把笔记里的猜测升级成世界事实，也不自动把自然语言笔记变成可执行指令。

“有帮助”规定该动作的用途；本理念不要求系统拥有判定推理质量的通用能力。输入限制与笔记整理方式由后续设计决定。

### 6.3 消耗正的游戏内时间

执行“再想想”必须消耗正的游戏内时间。耗时由游戏规则确定，可以由角色的思维敏捷等属性影响；具体属性、公式与取值范围尚未选择。

Human 实际思考多久、LLM 推理或网络用了多久，不直接决定角色付出的模型时间。系统衡量的是游戏中明确执行的思考行动，而不是尝试测量驱动器的真实思考速度。

这段时间属于同一个游戏世界。期间其他到期事件仍须按世界规则发生，思考可能使角色错过机会；不能通过一次“加时间”跳过中间的世界后果。正常完成后，应有继续维护的机会，并能利用先前积累的笔记及届时合法可知的信息。

能否边移动边想、思考如何被打断，以及开始、完成或中断时分别保存什么，均是机制层待决事项。“再想想”不预先决定所有计划编辑都收费，也不建立无限次免费重新唤醒的通道。

## 7. 用具体情境检验理念

以下是对后续方案的语义检验，不是已实现功能或本批施工范围。

1. **受托执行**：维护者安排前往一个已知地点。沿途按授权继续，到里程碑或目的地才请求维护；刷新界面不丢失计划和进度。
2. **意外与未来修改**：得知后续道路关闭。维护者能看见原计划、受影响部分与原因；修改未来不伪造已经完成的移动。
3. **带笔记继续思考**：维护者选择“再想想”并留下一条候选线索。执行消耗正的模型时间，期间到期事件照常处理；正常完成后的下次维护能发现并取得该线索。已正式记录的笔记不因中断消失；中断发生在记录前的结果必须由机制明确。Human/LLM 的实际响应快慢不改变这次规定耗时。
4. **不完整规划**：维护者留下“到镇上后再确定补给来源”。运行时可以先完成已有办法的部分；必要的未决环节应交回维护者，不凭空完成采购。
5. **信息不等于事实**：角色记录一条传闻，在相关地点召回。传闻未被证实也可辅助思考，但不会因此生成对应世界事实。

## 8. 当前实现与待裁决边界

当前 [0025 场景](../../build-log/0025-verification.md)只有四点全图已知、相邻真实移动和双页面。源码中的 [IPlayerDriver](../../../src/Player/IPlayerDriver.cs)仍是单次请求返回一个意图；[FreePlayScene](../../../src/Server/FreePlay/FreePlayScene.cs)在地点上请求移动决定；[Player.Agency](../../../src/Player.Agency/Spatial/IPlayerSpatialKnowledgeGetter.cs)仅提供静态已知图接缝。计划维护、思考行动和上述注意力机制都尚未实现。

当前 [Kernel](../simulation-kernel.md)负责统一仲裁与提交，[Spatial](../graph-spatial-world.md)负责客观空间。未来角色控制状态如何映射到程序集、事实及提交步骤，由机制与工程设计决定。

现有 Kernel 合同在等待驱动器回答期间不推进模型时间。它与“执行再想想要耗模型时间”描述的是不同阶段。若未来需要世界在驱动器实际回答期间继续运行，应另行裁决；本文不要求引入并发思考。

[旧空间知识备忘](../../research/player-spatial-knowledge.md)保留其 Getter 实现边界及历史消费者说明。本文确立更完整的未来方向；旧文中对当时扩展范围的限制，不代表本轮拒绝系统化笔记与计划。客观空间与角色知识分离的原则继续成立。

下一层机制设计至少应裁决：

| 问题 | 本文保留的边界 |
|---|---|
| 计划如何表达和推进？ | 先比较足以支持具体场景的表达；不预选队列、树、图或通用脚本 |
| 唤醒与执行怎样配合？ | 明确维护机会、暂停和继续的关系；同步维护可作为候选 |
| “再想想”怎样执行？ | 必填笔记、始终可选、正耗时、下次可续思考必须保持；并行、打断、保存时点另定 |
| 其他维护行为是否收费？ | 思考机会、编辑成本、空计划和保持原样的后续节奏需一起说明 |
| 知识、笔记怎样供给？ | 保持来源差异与可取用性；容量、召回、整理与保留策略按场景选择 |
| 计划修改怎样生效？ | 明确哪些未来可编辑及接受边界；再选择版本、协议和提交表达 |

机制比较应先用一个小闭环检验：提交移动计划、自动推进、出现维护机会、修改或保留未来、用“再想想”积累笔记并付出时间、再次维护。它是优先研究的候选切片，不代表同时批准探索迷雾、NPC、购物、通用规划器、存档或异步模型调用。
