# 属性变化速率的可解释模型

状态：2026-10-29 已实施并通过[工程与独立 Console 试玩验收](../experiments/attribute-rate-explanations-acceptance.md)。范围是共享数据与最小重构，不改玩法数值，不限定 decision/classic 的排版。`RateBreakdown` / `RateContribution` 已成为实际 API；三项物理速率与冻结观察共用该形状，数值访问器只读派生。

## 1. 需求账本与证据边界

| 要求 | 来源与地位 |
| --- | --- |
| 说明属性变化速率从何而来；任意 layout 与未来 LLM 使用共同的数据真相 | 本轮用户明确要求；不是给某个布局补字符串 |
| 原型用来探索可复用游戏设计，不将抽象限定于当前温暖规则 | 本轮用户明确要求；示例“白天 +18、暴露 −12”是示意，不要求改变实际算法 |
| 属性旁解释和集中效果栏均应能够从相同材料得到 | 用户提出的两种呈现方向；本方案保留两种投影能力，不要求本片同时新增两种正式布局 |
| 冻结 Opening/Items、角色隔离、完整/增量同源、S/E 恢复不重新感知 | 已实施的 [Context 合同](character-context-model.md) 与相关源码/测试；本文不是另一份独立证据 |
| 当前玩法数值、阈值、昼夜/移动/庇护的先旧后新积分不变 | 本轮是信息披露改进；由现有生存源码和测试约束 |
| 无旧存档或 API 兼容负担；仍须处理同一新修订内的 S/E 恢复 | 会话已定方向与当前仓库协议 |
| 先设计审查，后端到端实施 | 方案审查后用户已授权实施；LLM 端点、通用 Buff 执行系统仍不在本片 |

实际运行由单宿主按模型时间串行提交；等待输入时暂停，Plan 记录具体事实，E/S 发布后消费。当前消费者是物理积分/阈值预测、持久角色观察、两种 layout 和 Console full/delta；没有 GUI、LlmCharacterController 或通用状态效果实例。新设计先落 ResourceCycle，用具体垂直切片检验可复用合同，再决定是否提取程序集。

本方案选择锚点保存已求值贡献、总值派生、同一角色观察内共享来源语义键。裁决依据与可行替代见 §8；无需用户另行裁决玩法。非加法过程和部分可见原因明确延期，不把当前解释结构宣称为任意游戏规则的完整模型。

## 2. 改造前的基线与缺口

- [CycleSurvival](../../src/ResourceCycle/CycleSurvival.cs) 持久化三个整数速率；积分、阈值和补给沿用这些标量。达到 0/100 会夹断实际变化。
- [CycleSurvivalRules](../../src/ResourceCycle/CycleSurvivalRules.cs) 的 `WarmthRate` 按庇护优先、再昼夜选择 +12/+6/−12；`Enrich` 和 `Forecast` 使用它，初始化另有昼夜选择。食水为构造默认 −5/−8。没有当前 Buff 集合。
- `CycleSurvivalObservation` 只保存总速率和 Sheltered 等字段。两种布局显示总速率，[CycleViewSnapshot](../../src/ResourceCycle.Cli/CycleViewSnapshot.cs) 也只投影三个 rate 键；仅加原因字符串无法支持可靠分组或同总值下的来源变更。
- [CycleObservationEquality](../../src/ResourceCycle/CycleObservationEquality.cs)、[CycleVisibleEndpointChanges](../../src/ResourceCycle/CycleVisibleEndpointChanges.cs) 和 [CycleInteractionValidation](../../src/ResourceCycle/CycleInteractionValidation.cs) 都按现有数值材料比较/校验，新增来源必须贯穿这些边界。
- [CycleEnvironmentRules](../../src/ResourceCycle/CycleEnvironment.cs) 的寒风是一次实际扣减；[CycleObservedEvent](../../src/ResourceCycle/CycleObservedEvent.cs) 已保存事件与实际效果。不能把这个瞬时效果再挂成持续负速率。

这里有三个不同问题：现在是多少、为什么以此速率变化、某段时间实际变了多少。当前值、速率解释、历史事件分别回答，不能互相替代。

现有数值合同可对照 [SurvivalValueTests](../../tests/ResourceCycle.Tests/SurvivalValueTests.cs) 的旧段积分、任意 tick 重锚与限幅，以及 [ObservedEventTests](../../tests/ResourceCycle.Tests/ObservedEventTests.cs) 的黄昏先记录旧速率身体变化、再记录新速率；[SurvivalForecastTests](../../tests/ResourceCycle.Tests/SurvivalForecastTests.cs) 约束预测行为。设计审查时只核对源码，实施阶段已运行这些测试，结果见验收。

## 3. 最小可复用模型

以属性为归属单位，保存已求值的贡献；总速率由贡献派生。以下为逻辑形状：

```text
RateBreakdown
  Contributions[]
    SourceKey      // 同一角色观察内跨属性共享的公开原因键；每属性内唯一
    SourceLabel    // 公开来源/生效条件的名称，不含 Markdown 布局
    Amount         // 同一属性约定单位与时间基准的有符号贡献
  Total := sum(Contributions.Amount)
```

当前适配采用整数点/小时，与现有计算精度一致；可复用合同是“同量纲已求值贡献 → 唯一总值”，不是把所有游戏属性统一成小时或整数。量纲/时间基准须由所属属性明确，不能靠解析 SourceLabel 获取。首片保留已具名的三个属性和其固定量纲合同，不新增通用单位换算库、表达式树或动态属性注册表。

分解结构本身不含食物、饮水、庇护或昼夜字段；这些只是产生贡献的首批规则。同一合同可用于生命再生、体力恢复或资源生产等可诚实相加的速率，数值精度与时间基准由接入领域明确。先复用数据语义与生成/消费边界，不要求其他游戏沿用当前三属性对象或生存预测算法。

把三个物理速率标量换为不可变的 RateBreakdown，保留只读计算访问器供现有积分使用。贡献集及总和没有两个独立写入口；观察以同一结果替换原来的三个独立速率字段，其数值访问器也从该结果派生。所有 layout 使用保存材料。这样无需给每次变化额外传递一个只供 UI 使用的原因旁路；物理量与历史观察仍分别承担玩法权威和冻结材料的职责。

同一角色的一份观察中，相同 SourceKey 必须指同一个公开原因，并使用一致的 SourceLabel；例如 `metabolism` 同时产生食物和饮水消耗。属性特定的作用由所属属性与 Amount 说明，不从第一条任意抽取名称或按文案相等猜来源。不同角色不据此合并实例；跨快照可用稳定键比较变化，但它不是 Buff 实例、事件身份或 ToolCallId。

每属性内同键最多一项，重复键拒绝；构造时复制集合并按 SourceKey 的 Ordinal 顺序规范化，提供一份结构比较，物理比较/观察/增量复用。来源键、名称和数值任一变化都参与比较；渲染可自由排序而不回写 Model。这里只规范化无因果先后的加法贡献集合，绝不排序事件、经历或 Context Items。来源名称和数值均冻结；以后条件变化使用新值，不改旧 Context。

### 3.1 条件选择与叠加

当前温暖规则只产生一项：有庇护回暖 +12、白天野外回暖 +6 或夜间野外散热 −12。不为一条分支强行创造“白天 +18、暴露 −12”的实际原因。

如果未来玩法本来就是多项相加，分别保存各实际贡献，例如日照与湿身同时作用；同一数据形状可以表达正负抵消为零。条件是在领域规则求值时判断的，视图不执行条件；不把所有未生效分支放入活动效果栏。

本结构表示已求值的加法分解，不声称支持任意公式。乘法、优先覆盖或非线性规则若以后出现，先由领域定义正确的解释语义；不能为凑总和杜撰贡献，也不因假想需求先实现公式解释器。

### 3.2 单位、限幅与瞬时效果

- 贡献是持续速率；`CycleObservedEffect` 仍记录已发生的实际前后值。不得将一次饮水 +45 或寒风 −10 写成每小时贡献。
- 总速率是边界限幅前的规则结果，当前达到上限时可以显示“回暖 +6/小时，已达上限”；不再持久化第二个有效速率或把贡献全改成 0。
- 上下限作为可见属性材料披露，视图以当前值、速率方向与边界显示限幅提示，不预测未来事件。本片在 `CycleSurvivalObservation` 保存三项共用的 Minimum/Maximum（当前 0/100），由领域定义填入；不为相同范围再建三个独立配置或通用属性元模型。限幅标志不另存，按保存数值派生。
- 同一新数据结构内要求贡献量纲一致、来源键唯一、整数求和不溢出；空列表表示确实没有持续作用，正负抵消的非空列表不能折叠为空。

## 4. 生成、可见性、保存与恢复

规则求值产生一个结果：贡献与它的总值。积分/阈值读取总值，角色投影读取可披露的贡献。初始化、昼夜切换、进入/离开庇护和预测使用同一规则函数，不让工厂、Enrich、布局各维护一个数值分支。

更新时间 t：先按旧锚点速率积分至 t，再安装新贡献；观察冻结新状态与新解释。已经记录的身体变化仍按旧段实际效果叙述，不能拿新速率解释整个过去区间。预测可以求将来各分段的总值，但预测结果不回写当前解释，也不将未知未来条件披露为当前事实。

物理状态与角色观察都在既有 E/S 单根发布内保存；快照重复是历史材料，不是第二个可变玩法权威。`Project/Supply/Warn/Acknowledge/LoseWarmth` 应保留原速率解释，只有规则变化才替换；恢复安装记录结果，不运行布局或重新选规则。

构造和变更速率都必须接收带来源的值，不能保留无来源的可写整数入口并用“未知”或当前环境猜测补齐。现有低层数值测试可以显式构造测试来源，调整夹具不等于新增生产玩法。字段结构、总和与规范顺序需要在持久验证中检查；Fold 可以核对记录的物理结果与观察结果一致，不能为了补解释重做规则选择。

可见性在进入观察前完成，不能把领域来源对象、完整世界引用或隐藏对象 ID 放入角色材料再由 layout 删掉。当前自身食水及昼夜/庇护来源均可公开，因此首片实现完整分解。以后若角色只知总值而不知全部原因，必须显式设计不完全披露，不能删除隐因后还宣称可见贡献之和就是总值；这类玩法在本片延期，不预建权限/遮蔽框架。

## 5. Context、增量与布局

来源集合及内容变化是可见语义变化，即便总速率不变也要更新观察；只改呈现排列不能产生角色新知识。Open 接收者按既有路径追加 Item，Closed 在下一 Opening 冻结当前解释，不重开旧 Context。

增量在属性粒度重绘解释：当前值、范围、总速率或贡献改变，选中该属性当前值与完整速率说明，在尾部各呈现一次。不需新增持久展示块或依赖图；在现有选择器中显式关联 value/rate/解释即可。`body/actor/warmth-rate` 的总值未变、来源变了，仍显示新构成。限幅可附着属性值行，但 rate 方向变化也必须刷新它：温暖 99→100 且速率仍 +6 要增加限幅说明；100→90 且速率仍 +6 要撤除；值仍为 100、+6→−12 也不能留下“增长被上限限制”的旧说明。

不为每条来源新增持久事件或 UI 生命周期；历史事件存在时继续先显示事件/实际效果，之后显示更新的解释。不从“来源消失”推断未经记录的治愈、破坏或物品消耗，也不杜撰数值未变的加减事件。

可在瞬时 `CycleViewSnapshot` 增加以现有 rate key 索引的解释投影；更新选择器同时比较数值与解释，并以同一属性键合并成一次最新值。该投影不是第二套持久属性字典。完整 Context、最新状态预览与增量消费均只读取保存的观察。

同总值变更的贯穿点如下，不能只在 renderer 补比较：

| 入口 | 必须保持的合同 |
| --- | --- |
| `CycleFactApplication.SameSurvival` | 需要身体完全不变的事实不能偷偷替换来源，即便三个总值相同 |
| `CycleObservationEquality.SameSurvival` | 原因变化产生新的可见观察；纯输入排列变化不产生 Item |
| `CycleVisibleEndpointChanges.SameBody` | 原因改变属于必要交付，不能因标量相同漏检 |
| `CycleInteractionValidation.ValidateBodyAndWeather` | 保存的解释与已记录的物理结果一致；不能接受总值相同而来源错误的观察 |
| `CycleViewUpdate.Create` | 比较解释并合并属性级依赖，保证 delta 不漏报原因或限幅变化 |

按属性呈现：温暖 60/100；总速率 +6/小时；原因：白天野外回暖 +6/小时。按来源呈现：基础代谢——食物 −5/小时，饮水 −8/小时。后者是这些贡献的分组视图，不宣称已经存在可驱散、可过期的 Buff 实例；没有作用于速率的状态也不因此被自动纳入。新 layout 可自由决定位置，不能丢总速率或把不完整数据当完整因果。

## 6. 最小实施切片与验证

已按一个端到端垂直切片交付，没有先做通用效果平台。下列三步是同一交付的依赖顺序：

1. 用当前食水/温暖建立贡献结果，统一初始/切换/预测规则；调整物理速率表示与只读数值访问，核对原积分和阈值不变。
2. 持久观察、相等性、端点变化检测及事实验证接通来源；注册模型并更新实际受影响 Schema/GameRevision。允许破坏旧开发存档，不能用旧数据兼容 fallback 掩盖缺失来源。
3. 共用快照/更新选择器与两种 layout 消费解释；提供同材料的按来源分组测试消费者验证可复用性，不必新增正式第三布局。最终串联实际昼夜/移动/补给及 S/E-only 恢复。

实现验收：

- 原 −5/−8 和三种温暖条件的总值、积分、预测/阈值、警告和终局不变；边界更新保留先旧后新顺序。
- 多贡献、零和与同总值换来源的纯数据夹具，不增加新的玩法。必须贯穿 §5 五处入口：产生 Item、不可遗漏必要交付、拒绝伪造的旧解释、full/delta 包含新原因；纯排列变化不制造更新，重复来源键拒绝。同来源跨属性分组不混合不同原因。
- 更新后冷开 S 与 pending E 恢复保留完全相同的数值、来源和历史解释，不重新求因果；旧 Opening 不被最新条件覆盖。
- 两个布局和按来源分组消费者读取同一材料，元命令预览不生成 Item；成功操作和纯拒绝窗口不受影响。
- 覆盖 §5 的三条限幅轨迹，寒风/补给仍是一次性实际效果。观察字段只保存公开键/名称/数值，不持有世界或来源对象；不为验收另造隐藏 Buff 开关，部分可见原因测试随对应玩法重开。
- 测信息与语义，不锁定整屏字符串、章节位置或缩进。代码修改时做适当构建/测试与独立试玩；本次设计审查不算运行验证。

## 7. 延期与重开条件

| 机制 | 何时重开 |
| --- | --- |
| Buff 实例、施加/刷新/驱散/过期及叠层 | 出现真实持续状态生命周期玩法；贡献来源键不能冒充实例 ID |
| 通用运算表达式、乘法/覆盖解释 | 有真实规则无法诚实表达成加法分解，且消费者需要该计算过程 |
| 部分可见原因、未知贡献 | 首个隐藏效果玩法；必须同时定义总值是否可知及可推断的信息边界 |
| 通用属性组件库/动态注册/跨游戏包 | 第二个真实玩法验证相同合同后，按依赖证据提取；当前不动 Kernel/Spatial |
| GUI、LLM 输入优化与解释折叠 | 有相应消费者和测量；不能影响已保存的语义真相 |

## 8. 审查结论

设计阶段按 `dialectical-simplification` 完成需求怀疑者、最小架构师、语义保卫者三路独立审查及一轮交叉质询；主线程核对源码和测试，依据失败轨迹裁决，没有以投票替代证据。该阶段未运行构建/测试；以下保留设计取舍，实施运行证据另见验收。

最强反方是“物理仍存裸速率，Observe 调共享求值器并校验总值，解释只随观察保存”。**在当前固定规则下，该方案可以正确工作；E/S 冻结并不强迫物理锚点保存贡献。** 审查撤回了以恢复协议或可调整的自定义测试 API 证明锚点方案唯一必要的论断。

仍选择锚点贡献，是因为观察已经需要结构化结果，物理直接保存同一不可变结果可减少“当前条件能完全重构锚点原因”的额外前提、重复求值和总值对账路径；同总值换来源也直接进入现有端点比较。代价是修改三个速率字段、复制路径和 Schema；无兼容负担时，这比维持两种可写表示更明确。不是承诺每个游戏都必须采用同样物理存储。

| 裁决 | 内容与理由 |
| --- | --- |
| keep | 保存实际求值贡献、单一总值、先旧后新积分、Context 冻结；删除会丢失原因或使解释与实际区间错配 |
| simplify | 一个 SourceKey 同时用于属性内识别和同角色观察内分组；不加 GroupId、全局注册或 Buff 实例身份 |
| merge | 贡献与总速率归一个不可变结果；积分与观察用派生总值，不维护另一个可写 Total |
| simplify | 贡献构造时规范排序、共用结构比较；限幅从 value/bounds/rate 派生，属性级触发重绘 |
