# 游戏原型与机制实验环境：实践参照及 Playground 定位

2026-11-02。本文整理前述开发经验调查，记录可追溯的来源、对 DramaBoard 的启发及用户已选定的命名方向。外部实践与本项目建议分别陈述；示例工程的当前组织方式，不用于推断引擎最初就是这样开发的。

本文保留命名决策的调查依据；ResourceCycle → Playground 重命名已实施并通过验收，当前入口与持久身份契约见[重命名说明](../implementation/playground-rename.md)。动态执行状态统一见 [PROJECT-STATE](../../PROJECT-STATE.md)。

## 1. 已确定的项目定位

Playground 是 DramaBoard 开发期的可交互游戏原型，用于组合、试验和验证世界模拟机制。它允许真人、通过终端操作 Human Console 的 Coding Agent，以及模型驱动的角色进入同一世界。当前目标不追求商业游戏的游戏性、内容量或平衡，而是从具体情境中发现需求，让值得复用的机制逐步成熟。

命名区分两个层次：

- **Playground** 表达应用的长期用途：机制实验场。它仍承担具体游戏的规则组合、世界发布与宿主接线责任，不自动升级为通用游戏框架。
- **山野镇 / Hillside** 表达当前综合场景的内容身份：小镇与山林中的持续生活。增加其他实验场景时，不需要再次修改整个应用的名称。

Kernel、Spatial、Inventory、Goals、CharacterControl.Completion、CharacterGym 等现有模块继续按明确职责复用。机制先在实际情境中验证，再依据共同需求提取；不因新名称提前建设插件平台、统一世界根或万能事件系统。

## 2. 可核查的外部实践

以下资料在 2026-11-02 的调查中查阅；链接指向官方资料或开发者直接访谈。产品功能随版本变化，本文仅提取所需的组织经验。

### 2.1 《梦见岛》：自由实验逐渐形成正式作品

手塚卓志在直接访谈中回忆，团队成员在日常工作结束后尝试制作掌机上的塞尔达体验，起初未正式获批；做出值得展示的成果后，才向公司申请继续开发。开发过程带有爱好者社团性质，也给打破惯例的人物和情境留下空间。

来源：[Game Informer 对手塚卓志的访谈](https://gameinformer.com/b/features/archive/2016/03/05/looking-back-at-zelda-link-s-awakening?PostPageIndex=1)。

**对本项目的启发**：允许开发者带着好奇心进入可玩的原型，从操作中发现问题。访谈支持“自发实验成长为作品”，没有证明《梦见岛》原本是一套长期积累通用机制的试验平台；后者是我们的工程选择。

### 2.2 Unity 与 GooBall：具体应用提供整合需求

Unity 官方历史介绍记载，创始团队用自建引擎制作并发布 GooBall，同时就有将引擎授权给其他开发者的意图。这是具体游戏与引擎开发相互联系的实例。

来源：[Unity Learn：The Unity Story](https://learn.unity.com/tutorial/what-is-unity?tab=overview)。

**对本项目的启发**：即使最终游戏方向未定，也可以选择一个范围有限的具体世界，让输入、角色、时间、空间、资源和存档必须一起工作。山野镇可以提供这种整合压力，不必承担完整商业产品的制作目标。

### 2.3 Box2D：可操作的机制试验台

Box2D 官方 FAQ 说明，重要新功能配套 samples 代码，用于测试功能并展示预期使用方式；可视化对碰撞和物理调试很重要，因此作者制作了独立的 samples 应用。

来源：[Box2D FAQ](https://box2d.org/documentation/md_questions.html)。

**对本项目的启发**：每项机制可以配一个最小可操作局面，明确初始条件、干预手段和观察结果。叙事世界的“可视化”也可以是结构化文字：谁发出了事件，哪些连接允许传播，哪些角色收到了材料，为什么其他角色没有收到。

### 2.4 Unreal Content Examples：机制展厅

Unreal 的 Content Examples 由多个关卡组成，各自展示引擎的一类技术；关卡内使用编号展台组织示例，支持运行、交互、修改以及在自己的关卡中复用。

来源：[Unreal Content Examples 官方说明](https://dev.epicgames.com/documentation/unreal-engine/content-examples-sample-project-for-unreal-engine?lang=en-US)。

**对本项目的启发**：为机制提供容易找到的演示入口。声音传播、跟随、忙碌响应等可以拥有各自的小场景；不必每次通过长途旅行或复杂前置操作才能观察某项机制。这里借鉴的是入口组织，不要求建设三维展厅或 GUI。

### 2.5 Godot demos：独立样例与版本对应

Godot 官方维护 demo 项目集合，每个带 `project.godot` 的目录可以独立导入；仓库分支与引擎版本对应。官方演示目录既有导航、物理、输入、存档等单项示例，也有平台跳跃、JRPG 等较完整的小型示例。

来源：[Godot 官方 demo 仓库](https://github.com/godotengine/godot-demo-projects)、[官方 Web 演示目录](https://godotengine.github.io/godot-demo-projects/)。

**对本项目的启发**：实验入口应可独立启动，并明确适用的代码版本。积累更多实验不意味着把所有局面塞进同一张地图，也不意味着每个场景都要新建一套领域、CLI 和 Completion 项目。

### 2.6 Unreal Lyra：较完整的参考应用

Lyra 官方定位是模块化示例游戏与学习资源，组合核心系统、插件、多个游戏模式、联网及 Gameplay Ability System 等，并随引擎发展更新。

来源：[Lyra 官方说明](https://dev.epicgames.com/documentation/unreal-engine/lyra-sample-game-in-unreal-engine?lang=en-US)。

**对本项目的启发**：保留一个真实可操作的综合应用，展示机制如何协作。它可以发现单项演示难以暴露的生命周期、所有权、交付和恢复问题；当前无需采用 Lyra 的架构规模。

## 3. 建议的实验环境分工

下表是根据上述实例形成的本项目建议，不是行业统一分类，也不表示四套新框架已经实现。

| 环境 | 要回答的问题 | 本项目例子 | 应保留的结果 |
| --- | --- | --- | --- |
| 自动化测试 | 已明确的规则是否成立？ | 跟随出发的原子性、交易守恒、恢复不重复结算 | 可重复执行的断言 |
| 小型实验场景 | 一个机制实际怎样表现？ | 三个房间、两条语义连接、四个角色的声音传播 | 初始定义、操作方法、观察解释 |
| 持续运行的综合世界 | 多种机制组合后发生什么？ | 山野镇中的生活、生产、探索与协作 | 有界运行记录、交互及恢复证据 |
| 自由试玩 | 还有哪些事先没想到的问题？ | 真人或 Agent 自行安排活动 | 原始输入输出、观察、干预与疑问 |

建议优先复用同一运行时，通过内容定义和初始状态选择场景。已有内容定义和 Human/LLM 接线可作为起点；统一的实验场景目录、启动选择器和专门调试界面尚未由本文要求实施。

自由试玩与验收各有用途：自由试玩允许没有既定路线或测试清单；若要据此证明某项完成条件，仍需明确参与者、版本、预算和实际发生的行为。Agent 操作 Human Console 的记录应如实标注，不能写成真人体验。

## 4. 如何积累而不扩大维护负担

1. **先写出具体疑问。** 例如“声音让生产中的角色获得响应机会后，如何继续原活动”，再选择最小局面。抽象机制的边界由这些问题逐步说明。
2. **初次实验采用有限范围。** 限制地图、角色和运行时长；涉及模型时声明调用与时间预算，区分人工干预和自发行为。
3. **大世界发现，小场景复现。** 在自由生活中遇到异常或交互困惑后，提取必要角色、连接、活动和事件，建立易于重复的实验。
4. **使用实际规则代码。** 场景负责安排条件，宿主提供操作和观察；不另写一套近似实现来制造成功的演示。
5. **把不同价值留在适合的位置。** 正确性问题转为回归；容易理解机制的局面保留为样例；组合行为留在综合场景；体验发现记录为待验证假说。
6. **按共同需求提取模块。** 场景间可以先共享明确的规则和内容构造；是否形成通用 API，要看它是否仍依赖大量具体游戏知识。
7. **允许原型退役。** 被替代的独立应用通过固定 Git tag 保留，主线清理入口和配套维护面。[Microtown 归档](../archive/microtown.md)是本项目已经完成的实例。

一次实验最低限度需要说明：问题、初始条件、运行版本、操作方式、预期关注点、实际结果及证据限制。普通探索无需先填写复杂表格；需要复用或交接时再整理这些信息。

## 5. 给叙事模拟世界的具体建议

这些是后续候选实验，不作为本轮施工清单：

- **语义传播场景**：相同地图分别连接或断开声音能力，核对一跳传播、接收者去重及角色可见材料。
- **活动与响应场景**：两个角色生产或采集，另一个说话或发出报价，观察响应是否保留原有活动及期限。
- **协同行动场景**：跟随、到达、分头工作、大喊集合、重新跟随，观察角色是否能理解当前授权与未完成事项。
- **综合生活场景**：继续用山野镇观察生存、生产、市场和社会交互的组合，必要时再缩小成独立复现局面。

不追求游戏性，仍应让角色处境、可选行动和行动后果容易理解；这决定人类与 LLM 能否有效参与实验。调试视图可提供全局事实，但角色材料必须继续遵守可见性边界。观察和渲染不应偷偷推进世界或消费待交付事件。

## 6. 命名决策与实施交接

用户已选择 `Playground`。以下保留原始项目映射；实施及验收状态见[重命名说明](../implementation/playground-rename.md)：

| 当前项目 | 目标项目 |
| --- | --- |
| `ResourceCycle` | `Playground` |
| `ResourceCycle.Cli` | `Playground.Cli` |
| `ResourceCycle.Completion` | `Playground.Completion` |
| `ResourceCycle.Tests` | `Playground.Tests` |
| `ResourceCycle.Cli.Tests` | `Playground.Cli.Tests` |
| `ResourceCycle.Completion.Tests` | `Playground.Completion.Tests` |

`DramaBoard.ResourceCycle*` 的程序集与 namespace 随项目身份统一。`CycleWorld` → `PlaygroundWorld`、`CycleEngine` → `PlaygroundEngine`、`CycleGameFactory` → `PlaygroundGameFactory` 是代表性类型映射；完整声明符号清单由实施说明记录，避免对 `Cycle` 字样做无差别文本替换。优先使用语义重命名，再逐类处理配置、脚本和字符串。

实施时需分别核对项目/文件路径、CLR 符号、持久类型身份、Schema 历史、游戏身份、内容指纹及日志协议字段。已有“无旧开发存档兼容负担”的范围继续有效；如何处理持久身份及历史 Schema 要明确记录，不能仅凭项目改名就宣称完成。Hillside 仍表示场景内容，不要求跟着改名。

验收至少包括：新 solution/项目引用闭包完整，Release 构建与 Schema Verify 通过，受影响离线回归通过，新入口可启动及冷开恢复，当前文档/脚本同步，历史来源与归档链接保持可追溯。重命名不附带扩展玩法、重开已完成 Goal 或实现上述实验平台候选项。
