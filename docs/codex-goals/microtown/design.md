# 微型小镇：玩法与复用设计草案

状态：实施中。共享 Goals、Completion 调用循环和 Gym 记录/导出已从山林游戏提取；小镇领域切片正在接入，尚未达到完整游戏验收。以下具体玩法允许依据脚本与试玩证据调整，不必把普通配方/数值选择逐项提交用户裁决。

## 1. 世界与居民

最小经济循环为：外界供应原料 → 居民采购/生产 → 消费或出售 → 收入支持下一轮采购。生活需求、耗时生产与有限供需产生取舍；不是无限购买、瞬间加工、无限回购的刷钱循环。

| 项目 | 默认起点，可调整 |
| --- | --- |
| 角色 | 三个独立居民，各有库存、货币、生活状态、Goals、Context；共用模型调用设施，不共享私有语义记忆 |
| 地图 | 市场、工坊、居住区等少量地点，有简单通路与移动时间；设施不必各建完整子系统 |
| 物品 | 少量外购原料；至少两种产出，包含可消费食物与外销制成品。例：谷物→食物、木材→木制品，均为候选内容 |
| 生产 | 固定配方与可见耗时；角色同一时刻只承担一个互斥耗时活动。共享工位容量可后加 |
| 生活 | 先只有食物需求，适当初始储备与经营资金；不强制携带饮水、保暖、逃生规则 |
| 交易 | 外界公开固定报价与有限库存/收购额度；居民间最小显式报价/接受与赠与，不做撮合引擎 |
| 目标 | 初始倾向为各自维持生活并积累储备，允许自主协商；角色能力与禀赋可稍有差异，不固定职业脚本 |
| 实验 | 先定一个有限游戏日长度，并设置宿主调用/同刻操作护栏；脚本调通后接三个真实 LLM 居民 |

“独立行动”是决策和语义状态独立，不要求三个 API 并发调用。沿用世界在请求决策时暂停、按确定性顺序服务的机制；各角色的耗时活动可在世界时间中并存。服务公平性、通知与忙碌期间允许哪些即时操作需明确；不能让一个角色的无限零耗时操作阻止所有人生活。

对话与赠与复用已有经验。居民报价采用接受时重新检查资金/物品、双方变化一次结算的规则，不预留资产，带有限有效期和拒绝/撤回入口，具体合同见第 7 节。交易后角色的自主承诺和世界已验证履约应区分。

## 2. 经济结算与时间

- 生产开始时何时扣料、输入放在哪里、到期何时产出、取消/终局如何处理在同一规则中定义。不得以旧命令重放替代已保存事实应用，或在恢复时再次扣料/产出。
- 交易应原子检查并结算双方货币和货物；余额、数量、容量及整数溢出明确拒绝。外界可作为有限规则对手，不必有 LLM 角色。
- 内部交易的物品与货币转移要守恒；生产按配方转换，生活消费有明确销毁；外界进口、出口与注资若存在则分别记账。不要求不同物品“件数总和”守恒。
- 外界补货、需求更新、生活阈值和生产完成采用现有预测/发生项机制，显式规定同刻顺序。规则不因诊断读取、渲染或冷开产生业务效果。
- 随机性若引入，保存种子/随机坐标或已决定结果；首版可以完全确定性。fork 不因换分支身份而意外换一套外部条件。

先以脚本证明原料可获得、产出有用途、完成生产后仍有生活余地，且能跨至少一次市场周期继续运行。避免为了修复平衡而由宿主暗中给钱或强迫 LLM 选择有利行动。

可选的“下次材料涨价”“某商品需求上升”分为实际外部规则变化和可感知公告两部分。公告固定节奏即可，角色知道的范围以交付记录为准；第一轮不做新闻生成器。

### 首个领域切片的具体选择

`Microtown` 的内存脚本实验采用 48 小时、三居民各 18 钱/一份饭/60 饱食；每小时消耗 3 饱食，饭补 40，上限 100。三地点通路各耗时 15 分钟。2 谷物（每份 2 钱）用 1 小时产 2 饭；2 木材（每份 3 钱）用 2 小时产 1 木器。外售饭 4 钱、木器 12 钱，市场每天提供谷物/木材各 18 份、收购饭 6 份/木器 9 份，补货不记作居民进口。当前库存无限，配方数值属于本游戏内容。

开始生产扣料进入在制品，到期才累计配方消耗和产出；失败退回未完成原料到遗产，实验结束保留在制品。原料、成品、在制品逐项核对，失败居民不移出人口或最差生活统计。同刻顺序明确为饥饿失败、报价到期、市场刷新、空间发生项、活动完成、实验结束、决定；临界饥饿和产出同刻时先失败。

即时成功操作后轮转服务其他空闲或待响应居民，拒绝保留当前服务；新服务先发布 `DecisionOpened`，下一 Step 才调用控制器。生产入口 `CreateControlledKernel` 交付冻结 `TownObservation`，返回原始操作和来源身份；完整世界脚本入口只用于开发测试。同地交流/赠与可唤醒生产或等待中的居民，响应规则见第 6 节。空间到达与接触均须进入同一个 Kernel，不能维护接触预测却漏掉其消费路径。Town 自身的 owner 预测缓存尚待接入；Spatial 已复用增量 Complete/Rebuild。

## 3. 统计与角色信息

开发者可读取世界真相做统计；角色材料只含依法可知的信息。指标不自动进入模型提示词，不隐式成为所有居民共同优化的目标。

当前冻结观察包含本人库存、现金、饱食、Goals、活动、最近操作回执与最近本人活动结果；附近居民只透露同地公开身份和活动类型。地图/配方/价格/市场刷新规律是公共规则，实时库存及收购余额只有市场现场可见，远处明确标未知。`TownTextRenderer` 不查询世界，根据冻结值显示命令、合法整数范围和阻因；局部验证查询不修改状态。

最近一条回执、一条本人经历与有界收发记录共同构成当前角色材料，仍不是完整的 Context 生命周期。交互记录由角色对象持有，高水位在决策 opening 发布时推进，冻结观察只读投影；不能用宿主 Gym 日志填补角色记忆。一次结果再次展示不代表需要重做动作。报价通过独立状态展示当前有效条款与待交付终态，不依赖有限交流历史中的通知。

| 维度 | 首版统计建议 |
| --- | --- |
| 实物 | 各商品生产、消费、进口、出口、期初/期末库存，必要时包括在制品 |
| 资金 | 各居民余额、外部收支、内部转账；给出账实核对，不用单一“GDP”掩盖口径 |
| 生活 | 各居民需求当前值/最低值、未满足需求的持续时间、失败状态；输出最差值和居民身份 |
| 协作 | 已完成交易与赠与的数量/内容，可从记录解释分工；不自动给“合作好坏”打分 |

统计应区分“全局开始到当前”和“本次运行区间”，冷开不丢进度、fork 不混入父未来。可从事实重算或在同根维护必要聚合，选择一种权威，不能把非原子宿主日志作为游戏经济账本。

处境最差不等于钱最少。首版优先直接使用生活需要；死亡/退出居民不能从最差值中被静默删除。不同单位不强行合成总分，不要求跨游戏评分可比。

## 4. 复用与游戏组合

沿用[分层设计](../../design/layering-and-composition.md)。目标不是让一切进入底层，而是让新增游戏主要编写自己的组合和规则。

| 当前源码入口 | 已有依据与提取方向 |
| --- | --- |
| Kernel / Spatial / Host / Inventory | 已有独立项目，优先直接使用；保持单一时间/发布权威 |
| [GoalRules](../../../src/Goals/GoalRules.cs) 与 Goals 模型 | 局部图编辑不读世界；优先提取共享模块，游戏决定何时接受操作、如何发布与呈现 |
| [CharacterContext](../../../src/ResourceCycle/CharacterContext.cs) | 生命周期、冻结材料和回执机制可复用，但保存 CycleObservation/经历/目标；拆分共同生命周期与游戏材料，不能只移动文件或抹掉强类型 |
| [LlmCharacterController](../../../src/ResourceCycle.Completion/LlmCharacterController.cs) | 调用、预算、反馈 Tail 可共享；剥离 CycleDecisionContext 以及生存/交流行动提示，具体游戏提供材料与能力指引 |
| [GymSession](../../../src/ResourceCycle.Cli/Gym/GymSession.cs) / GymJournal / GymTraceExporter | 记录机制与游戏定位分开；由游戏适配解释可恢复边界，保留请求身份、来源截点与只读导出合同 |
| [CycleGameFactory](../../../src/ResourceCycle/CycleGameFactory.cs)、地图、规则、持久化适配 | 山林内容和游戏总根保持归属；小镇有自己的工厂/组合与明确存档选择，不以不断增长的 survival 开关实现 |
| 采集、生存、交流与新制作/交易 | 以实际被两游戏使用的局部能力决定提取；跨模块结算由游戏或明确组合模块负责 |

首片已采用以下物理边界，均不反向引用 ResourceCycle：

- `DramaBoard.Goals`：不可变 Goal/Link/Focus、命令解析与纯编辑规则、自身 DG 注册；游戏负责把结果与回执纳入一次发布。旧 `CycleGoal*` 类型改为 `Goal*`，`CycleGoalInteractionRules` 仍是原游戏的交互组合。
- `DramaBoard.CharacterControl.Completion`：`LlmDecisionLoop` 接收 `LlmDecisionInput(CharacterId, ContextSequence, Material, GameGuidance)`，保留调用预算、反馈保存回执、原生 Tail、请求身份和顺序调用保护；返回未解析的 `CommandSubmission`。它不是持久 Context，更不授权改变世界。原 `LlmCharacterController` 保留强类型观察、能力政策、渲染和操作转换，渲染也受串行保护。
- `DramaBoard.CharacterGym`：哈希串联日志、Completion 消息投影、按角色和祖先切点导出。游戏的完成 S 定位、存档解释、冷开修复以及角色可见材料仍由 `GymSession` 等游戏适配负责。日志新增操作使用状态名称，继续解释格式 1 的数字 Interrupted；构建证据包含新共享程序集。

Context 暂不泛型化：山林的冻结观察、目标回执及经历校验有真实游戏语义。不同游戏可用自己的强类型 Context 投影到调用输入；不强制统一世界根、观察全集、通用命令枚举或结束条件，也不建只为形式分层的同构 DTO。

内容库初期用普通 C# 定义/工厂组织物品、配方、地图片段与文字。共享不可变定义与每局可变状态分开，不能跨游戏/存档意外共享可变对象。不同游戏只装配需要的能力，组件本身不擅自发布世界。

## 5. 初始化、版本与开发入口

需要可识别游戏种类、游戏修订及所需模型注册的加载路径，不能仅因为两游戏恰好有同一 GameRevision 就误开。具体元数据存放和启动命令先做最小方案；不默认统一根 Schema 或引入多模块版本管理器。

首片已将山林/采集游戏的 GameRevision 升到 16，共享 Goals 使用 `DramaBoard.Goals.*` 持久身份，包含这些类型的原游戏 Schema 显式升版。旧开发图没有别名或升级器，可能在 DG 类型还原阶段即拒绝；不宣称修订 15 存档可继续。小镇使用独立 `Microtown` 程序集、`DramaBoard.Microtown.Root/Event` 持久身份，S/E 分别携带 `GameId=microtown` 和 `GameRevision=3`，当前只接受此版本；Character Schema 保持 2；报价切片将 Business/EventKind/Fact/Experience Schema 升到 2，新增 TradeAsset/Offer/State/Status。旧开发存档可能先在 DG 子对象还原时因无升级器拒绝；CLI 将此类数据/Schema 错误明确报告，不提供迁移。

`TownDurableHistory.Open` 检查根/事件身份、修订与相邻 S/E/游标关系，重建就绪世界；不执行 pending、不发布新 E/S。pending 的业务应用及完整验证由正常 Kernel 恢复完成，不能把 Open 当成已完成 pending。`TownFact` 暂用完整不可变 NextBusiness 加 typed SpatialFacts，E 与 S 独立对象图；后续跨版本转换须同时考虑 pending 内的替换业务图。

控制器来源 `TownControllerOperation` 在解析前保存 RawInput/ToolCallId/OperationRecordId；成功和拒绝都把 `TownOperationReceipt` 存入事实及本人状态。拒绝保持 DecisionSequence，递增 OperationSequence 并产生新 S。`CaptureDecisionBoundary` 捕获当前精确完成 S、角色/操作序号、游标和游戏版本；Gym 每次真实模型 Request 都重新捕获，不能按 DecisionSequence 复用旧锚点。

`Fork` 验证源分支历史成员、精确 S 及公开决策窗口，再直接注册子分支；不造新的业务 S，不改变 lineage、时间、随机坐标或累计账。Console 通过 `--branch` 选择运行分支；`--gym-fork` / `--gym-fork-request` 分别按反馈/请求定位原完成 S。子分支证据前缀截至源请求之前，不混入父未来；原生工具 Tail 不作为游戏状态恢复。

现有 E/S 独立修订、完成 S fork、pending 恢复与角色可见性合同保留。旧开发存档不承诺全面兼容；若拆分改变 Schema 或序列化身份，明确拒绝/支持范围，保留旧证据，不隐式改写。当前程序产生的新档须完成冷开与 fork 验收。

已选择独立薄 [Microtown.Cli](../../../src/Microtown.Cli/README.md)，同一个 Console 默认服务三位 Human 居民，`--llm` 绑定三个模型居民，`--human` 可保留一位由人类调试接管。一个 Town 适配器串行调用共享 `LlmDecisionLoop`，每次只接冻结观察，预算跨居民计数，跨决策不保留语义 Tail。`CompletionConnectionBinding` 也被山林宿主使用：恢复后首次真实调用才初始化，目录只解析选中连接的环境变量。

`TownGymSession` 复用共享日志、消息投影及导出。先恢复 pending E，再依据当前分支已完成 E/S 的精确操作回执补录宿主结果；无提交的旧输入标 Interrupted，绝不从日志重放。反馈持久化后才返回工具回执。只读管理不修复日志；写会话也先只读核对游戏身份，不能在拒绝外来日志前修剪尾行。每次运行记录预算、角色绑定、程序集哈希和显式实验指令；运行时实际解析的模型/连接另记 binding，不保存凭据。

共享部分不解释 Town 的世界根、历史边界或经济账。`ReadCommittedOperations` 目前扫描选定分支历史以找待补回执，适合当前有限实验，尚未提供大型长期运行的索引；性能优化须保留精确 E/S 和 fork 前缀语义。当前接线与短局验证不替代完整经济日模型验收；社交/忙碌响应的工程与 Console 证据另见[交互切片](../../experiments/microtown-social-acceptance.md)。

## 6. 首个居民交互切片的规则

本节记录实现契约；验收状态以工作计划为准。同地交流、赠与与忙碌响应构成基础；报价交易复用响应资格，另外维护第 7 节的报价交付状态，不引入通用消息系统。

- `say <resident> <text>` 给同地存活居民发言，禁止对自己发送；双方各存一份带共同消息 ID、各自序号、发送者/收件者和发生时间的记录。原话是居民表达，不成为世界规则或已验证事实。
- `give <resident> <item|money> <count>` 同地赠与；检查完整结果后，一次事实转移双方财产并保存双方记录。内部赠与不计进出口；数量、余额、库存接纳或收件容量不满足时整项拒绝。
- 正在生产/等待的角色收到消息或赠与，获得响应资格；其活动 ID、结束时刻及在制品保持不变。即时操作后轮转其他可服务居民，但该响应资格保留；`continue` 结束响应、继续原活动，`cancel` 结束等待或一次退回生产原料，不产出成品。移动中不新增响应/取消能力。
- 角色自己的历史最多保留 32 条待交付、本次 opening 最多 32 条新记录及此前最近 16 条，共 80 条。opening 发布时记录交付高水位和本窗口的新项下界；纯渲染、重试和冷开不消费。高水位表示已纳入决策材料，不证明人或模型真的阅读。拒绝重试继续使用同一窗口。
- 用户发送超过接收容量时整项拒绝；不能 FIFO 丢弃未读消息。活动到期、失败等系统结果继续使用独立的本人经历字段，不挤入可能已满的用户消息队列。报价终态通过第 7 节的生命周期名额保证保留，不沿用“满了便拒绝”的用户发送规则。
- 展示赠与候选时仅据本人持有数量给上限，明确接收方条件在提交时校验；不通过完整校验的二分查询反推别人的库存、资金或消息队列。实际执行仍由同一领域校验权威决定，不依赖 UI 的估计。
- 任何入库必须同时保证当前接纳、现有生产完成和取消退料可表示；生产开始也检查两个未来分支。可移出的库存不用为尚未实现的锁定功能保留，但不能接受会令已安排的正常系统结算抛异常的变化。

成功即时操作轮转不等于任意控制器下时间必然推进。拒绝保留当前决策，模型/操作预算及同刻护栏会暂停，宿主不暗中代选耗时操作。

## 7. 居民报价与原子交换

本节是交易切片的选定合同，实际验收状态仍由工作计划记录。交易先留在 Microtown 游戏层；不为尚不存在的第二个交易消费者建立通用订单框架。

- `offer <resident> <give-asset> <give-count> <want-asset> <want-count> <hours>` 向同地另一位存活居民提出报价。资产为 `money` 或物品 ID，每边一种；物品每次 1–1000 件，钱为正整数，时效为 1–24 整小时。报价 ID 由发起者身份与操作序号产生。
- 创建时检查发起人当前持有完整支付资产，不要求对方此时持有所求资产；报价不锁定库存或余额。创建成功不代表以后一定能兑现，发起人可以提出多份使用同一资产的报价。
- `accept <offer-id>` 仅由收件人执行，双方必须存活、同地，且当前时间严格小于到期时刻。双方先各自持有并扣除完整支付，再检查收取后的最终余额/库存，以及各自现有生产的完成与取消退料能力。两个支付、两个收取与报价终态进入同一事实；失败不转移任何资产，报价仍有效，直到其他明确终态。
- `reject <offer-id>` 由收件人拒绝，`withdraw <offer-id>` 由发起人撤回；不要求双方仍同地。终态不再接受任何交易操作，重复输入不重复效果。内部交换不计作外界进出口。
- 报价在到期时自动关闭；同刻到期先于决定，不存在“恰好到期但抢先接受”的窗口。参与者失败时相关有效报价关闭，有限实验结束时关闭其余有效报价；终态分别保留原因，不把没有交换的关闭计为成交。

报价生命周期记录与普通交流队列分离。每份报价自身保存双方条款、有效/终态及各方已交付版本和决策序号；有效报价始终出现在参与者材料中，不能因短期交流历史裁剪而消失。另一方的交付标记、库存和钱不进入观察。

保留记录总量最多 24 份，每位发起人最多 8 份，包含尚未回收的终态。新报价占用生命周期名额，已有报价关闭不再申请容量，所以用户消息队列满或报价名额满都不能阻止成交、拒绝、撤回、到期与失败关闭。终态只有在双方此前均已纳入决策材料后，才可在参与者之后的 Opening 回收；本次首次收到终态的材料必须完整保留。失败居民免除后续交付等待，但不伪造已交付证据；幸存方仍需正常 Opening。

Opening 发布时才确认交付，只对新版本推进标记；纯渲染与拒绝重试不消费。新报价/终态变化触发响应资格，存在有效报价本身不会不断唤醒。忙碌居民的即时操作不改变活动截止时刻，`continue` 清响应后保留活动；移动中积累通知，抵达后再服务。实验终点不额外调用控制器。

界面把“自己的条件允许尝试”和“已保证可执行”区分开：接受时仍要核验对方支付及接纳条件；报价构造给参数语法和本人资产域，不枚举居民×双边资产×数量乘积。当前有效报价与终态通知分别呈现，交付仅意味着材料已发布，不意味着角色同意了交易。
