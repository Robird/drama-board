## 合并方式

优先评估以 ResourceCycle 的角色、Context 和探索机制为基础，吸收小镇生产与交易，再形成新的游戏身份。代码规模不是选择依据：应比较需要保留的不变量、领域模型冲突、迁移和验收成本。若另建薄的新游戏组合更简单，可以采用，但避免把两套完整运行时长期包在一起。

实施前做一份简短的符号/职责映射：旧角色、活动、库存、身体、钱、交互、事实、观察、控制器、持久根分别落到哪里。命名迁移和语义变更分开实施，优先使用符号级重命名，避免仓库全局文本替换。最终只保留一套新世界权威，不维持两个互相传送角色快照的游戏实例。

迁移过程中旧原型可作为对照；新入口通过关键回归后再决定归档路径。保留可复现的历史记录，文档明确哪些旧测试已转成新世界合同、哪些旧剧情语义有意删除。新方案无须永远兼容两套旧 CLI。

## 必须先消解的语义冲突

| 冲突 | 首版处理方向 |
| --- | --- |
| 小镇固定实验终点、山林抵达出口即退休 | 实验时长移到宿主停止条件；山口/公路成为可往返地点。明确个体结束、全体不可行动和用户退出的区别。 |
| 两套角色与饥饿/食物表示 | 选一套身体与时间单位，统一物品目录、资金单位、配方输入输出；地区影响条件，不改变角色身份或重置数值。 |
| 山林短时逃生压力与长期生活 | 默认角色有基本生存路径和准备机会，镇内补给/庇护与野外风险一致可解释；避免以暗中补满、取消消耗或无限现金维持运转。具体难度由实际运行调整。 |
| 两套活动与忙碌响应 | 采集、生产、等待、移动共享明确的占用/中断规则；通信与交易能请求响应，不能默默结束原工作。旅行仍有真实耗时。 |
| 不同交互历史模型 | 让生产、买卖、报价和完成结果进入统一角色材料；沿用冻结、局部序号、隐私和原文保真的合同，不要求恢复全部历史或原生工具 Tail。 |
| 静态地图与内容变体 | 明确不可变世界定义与运行状态的边界。普通 C# 内容工厂可以是首版配置入口；外部格式仅在减少实际内容成本时引入。定义身份/指纹或版本须与存档相容性绑定。 |
| 人类/模型的等待 | 首版可保留串行决策和可暂停模拟，公开说明等待语义；改变控制绑定不迁移角色记忆。并发思考和持续墙钟世界按性能/体验证据另立切片。 |

## 一张小地图先形成循环

建议地点为居住区、市场、工坊、山脚、溪流、林地、林屋和山脊中的少量组合。保留语义连接与移动通道独立，不用距离自动推导声音。

首条贯通路径：在镇里准备 → 出发 → 采集或探索 → 补给/休息 → 返回 → 加工/交换 → 再次出发。至少让一种野外资源有真实消费或生产用途，并让镇内产物能改善下一次出行。不是要求所有角色按这条路线行动，而是保证世界中存在可理解、可重复的生活机会。

先使用已有生产、市场、天气和交流能力。若引入资源差异、有限供应或初始偏好，说明它试图改变的选择；不要为演示合作强制职业、锁死单人玩法或给角色隐藏信息。外部市场可提供基本经济边界，但供应无限且覆盖一切的设定可能削弱交往动机，应记录实际观察。

## 软件合同

- 一个世界根拥有角色、空间、资源、经济和个人交互；跨模块效果一次业务结算，E/S 仍是两个发布边界。pending 恢复消费记录，不能重做模型选择或随机结果。
- 保留业务状态与派生预测的分离；冷开 Rebuild，运行中增量维护，以 oracle 验证。不要因融合偷偷引入第二个时钟或直接写世界的后台回调。
- 模型仅收到角色冻结材料；Gym/调试观察可见范围与玩家界面分开。开发者记录不是角色记忆，角色原话不是世界确认。
- 优先复用现有模块；新游戏承担具体规则和组合。不以融合为理由建设万能事件总线、组件注册框架或新存储层。
- 内容修订可拒绝旧开发档，拒绝不应破坏源档；共享依赖的修改范围由实际需要决定，使用本地源码并核对版本，不以发包作为开工前提。

## 建议依赖顺序

1. 明确映射、名称、游戏身份与终止语义，选定一个最小可运行组合。
2. 让一名脚本角色带着连续状态完成镇—山往返与加工消费。
3. 接通交易、生产中的响应、跟随和大喊，以及跨地区个人材料。
4. 完成同版本恢复、内容绑定和 Gym；尽早运行 Human Console，别把 UI 留到最后。
5. 多角色真实模型与自由游玩，根据证据修正最影响体验的问题，再核对所有完成条件。

以上是依赖提示，不是固定轮数或必须全部先设计再编码的瀑布流程。每轮可选择更有价值的纵向切片，并保持可运行、可验证的中间状态。

## 风险处理

长期记忆、事件兴趣/唤醒、模型延迟和内容增长都值得观察。先测出具体重复行为、无价值唤醒、等待或材料增长，再实施最小修复。只有真实问题需要时才引入经历召回、事件过滤或索引；本阶段不承诺完整长期人格和自主社会。

合并前后的性能优劣不能靠代码观感判断。记录模型调用次数、墙钟时间、实际 token/usage（未知则标未知）、游戏时间推进、存档/材料大小和明显重复操作，区分模型等待与模拟/存储成本；不要求未经需求确定的性能数字。
