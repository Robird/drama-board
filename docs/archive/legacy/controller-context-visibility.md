# 历史反馈：角色上下文边界与 Console 诊断输出

状态：2026-10-29 用户反馈整理与源码核对，基线 `0912377`。**这是临时工作单，不是已批准的实施方案，也不表示下述能力已经实现。** 本轮只记录问题；后续逐项裁决、实施、验收后，把稳定合同合入正式设计，本文归档。

归档：角色上下文 Model 已实施，现行合同与证据见[方案](../../design/character-context-model.md)及[验收记录](../../experiments/character-context-model-acceptance.md)。以下保留基线问题与候选比较供追溯，不作为当前实现事实或待办。

## 1. 目标与范围

继续打磨 Human Console，使它既能供真人玩游戏，也能帮助开发者检查未来 LLM CharacterController 实际获得的信息。两者共用角色观察、可感知事件及继承结果的基础真相；Console 可额外提供管理和诊断信息，但不能让这些附加信息混入角色上下文。

用户已明确的方向：

- 将单一“回合边界”升级为可辨识的“LLM 上下文开始 / LLM 上下文结束”。目前没有 LLM 接入，这两个标记表达拟模拟的信息范围。
- 存档路径、保存/恢复说明、元命令提示等放在上下文外；开场处放在开始标记之前。
- “你在山林中迷途……寻找人类社会”等角色背景与目标属于上下文内。
- 放行模拟后不再给旧上下文追加行动执行结果或结算过程；沿用 handoff 和下一回合继承，不恢复动作后收尾阶段或引入 `:end`。
- 下一回合如何交付上次行动及其影响，应与现有“上次推进的结果”统一设计，避免重复两套讲述。
- 区分角色可感知信息与开发者诊断信息，尤其考虑世界推进和其他角色活动。狼人杀中狼人夜间的私有活动不能因调试方便进入警察或村民的上下文。

本轮不实现 LLM 适配器、通用权限框架或完整轨迹日志。本文中的 Human / LLM CharacterController 是职责称呼；当前具体 Human 类型仍为 `PlayConsole.ConsoleCharacterController`，不意味着已经重命名或新增了对应类型。

## 2. 已核对的实现与错位

| 入口 | 当前事实 | 对问题的影响 |
| --- | --- | --- |
| [PlayConsole](../../../src/ResourceCycle.Cli/PlayConsole.cs) `RunAsync` | `StartupText` 将存档、恢复说明与迷途背景拼成同一字符串 | 目前无法直接按角色/宿主内容划界；需要拆分语义来源，不能只整体搬到标记外 |
| [PlayPresentationSession](../../../src/ResourceCycle.Cli/PlayPresentationSession.cs) `ShowFull / Write` | 先写回合分隔，再写 StartupText、ConsoleHint、layout 和阶段提示；没有结束标记 | 管理提示与角色正文共同落入两条边界之间 |
| 同文件 `BeginAdvancing / Commit / EnterInput` | 所有合法返回领域操作都会先进入 Advancing，包含 `use`；ContextSequence 未变时提交输出仍接在原画面上，下一次输入才按身份重画 | “正在结算”不等于旧决策上下文已经结束；仅靠阶段或模型时间判断会误分零耗时操作 |
| 基线 `0912377` 的 `CycleContinuityRules.Enrich / OpenContext`（已替换） | 合法 go/wait/gather，以及确认后恢复模拟的 continue，记录 Pending；下次可决策时才增加 ContextSequence 并封存 Incoming | 旧回合结束和新回合开始是两个时点；不能等编号改变才结束旧显示范围 |
| `PlayConsole.RenderCommitted` | 生存模式从已提交事实提取匹配 ObserverId 的事件，并构造该角色观察；忽略纯 DecisionContextOpened；当前选用 `world.Characters[0]` | 已有单角色投影，不能笼统称为全世界日志；也不能直接当成未来多角色分发机制 |
| [CycleObservedEvents](../../../src/ResourceCycle/CycleObservedEvents.cs) / [验证](../../../src/ResourceCycle/CycleObservedEventValidation.cs) | 记录身体过程、自身效果及有限公开/同地资源事件，带 ObserverId；[CycleViewUpdate](../../../src/ResourceCycle.Cli/CycleViewUpdate.cs) 再过滤观察者 | 可复用结构化材料，但当前规则只服务既有玩法，不是任意游戏可见性的完成证明 |
| [CycleObservation](../../../src/ResourceCycle/CycleObservation.cs) `Create` | 按角色筛选当前地点资源/通路、同地其他角色、个人历史观察等 | 全量与增量应沿用同一观察权威；布局不能直接从全世界补齐隐藏原因 |
| 基线 `0912377` 的 `ContinuityPlayView`（已替换） | 从冻结 Incoming 展示行动、区间净变化、唤醒原因、过程计数与 handoff | 当时已有自足、可恢复的跨回合摘要，但不是完整事件序列 |
| `RenderCommitted` 非 survival 分支 | `--play` 仍直接输出操作结果及 `RenderPublicChange`，没有多角色增量分发 | 多角色 Console 验收需单独核对，不能用生存单角色结论替代 |

用户实录中的 `use item.water` 留在同一决策回合，但也显示 Advancing → ControllerInput；`go trail-1` 的开始、身体消耗、抵达、警告则在旧画面之后陆续输出，最后才出现下一回合分隔线。这与[已有继承合同](../../design/decision-context-handoff.md)的“放行后结束旧控制会话”在呈现上不一致，不要求重新设计三阶段领域流程来修补。

## 3. 待处理问题

### P1：定义上下文生命周期与标记的精确含义

**要产出的裁决**：明确开始、结束、暂停显示与宿主退出各自依据，以及标记是否代表可机械提取的上下文内容。

- 开始应绑定角色身份与决策 ContextSequence，不等于一次 `ChooseCommandAsync` 调用、一次模型请求、模型时间增加或一次全量重绘。
- 正常结束应依据已成功提交的“放行模拟”语义；不能仅因解析出 go 就宣布执行成功，也不能把所有 BeginAdvancing 当结束。非法命令、use、handoff、cancel，以及只确认空闲警告的 continue 不应误结束。
- 新开始前，宿主提示在外；正文背景、角色知识、继承信息、当前观察与可用行动在内。沿用背景 → 历史 → 当前 → 行动的组织原则，不预定“书接上文”必须挤到规则之前。
- 终局不会再开可行动回合：冻结终局结果放在哪种只读上下文、如何标结束，需要明确。
- EOF、`:exit`、取消和进程故障不能伪造领域回合完成。正常退出若闭合显示标记，应区分“展示会话关闭”与“已放行模拟”；异常截断不承诺完整配对。
- 冷开同一决策回合可能重新展示一次上下文；区分持久回合身份与本次展示身份，不因重启额外递增领域编号。

**特别需澄清**：用户说“最后的耗时动作及其结果不放入前一回合上下文”。动作指令毕竟由旧控制器产生。应分清终端输入回显、模型输出的 tool-call、游戏接受回执、执行效果和下一轮继承材料。可以规定旧会话不接收执行反馈，却不能声称模型从未生成那次调用。下一轮究竟使用历史叙述还是重放 call/result 配对，也不能只靠移动文本决定。既有 ToolCallId 原样保存及结果配对合同继续成立；是否再次送给模型是另一问题，端点格式仍归 Completion。

### P2：分离角色材料、Console 管理内容与开发者诊断

**要产出的裁决**：三类内容的来源、接收者及输出方式；名称与具体接口留待设计，不先搭通用消息总线。

| 内容 | 建议归属 | 需处理的细节 |
| --- | --- | --- |
| 存档路径、自动保存、恢复/截断修复说明 | 宿主/Console | 开始标记之前；不进入共享角色材料 |
| 迷途背景、逃离目标、角色已知规则 | 角色上下文 | 从混合 StartupText 拆出；新上下文应自足，不能只在进程首次启动出现；续局/终局措辞避免再次宣称刚醒来 |
| “等待输入世界暂停”“正在处理结算”、提示符 | 宿主交互状态，具体文案需拆分 | 当前开场句也混有这些内容；角色必需的行动规则与宿主状态分别处理 |
| 元命令提示、帮助中的管理部分、切模式/布局回执 | Console | 回合中途也可能出现，不是只前移首次提示即可 |
| 当前观察、个人经历、角色行动拒绝原因、零耗时实际效果 | 角色材料 | 使用与未来 LLM 相同的可见性投影；仍需区分历史与当前 |
| 全世界提交、隐藏行动、恢复与交付排查 | 开发者诊断 | 与角色输出分流；颜色或“诊断”标签本身不构成信息隔离 |

`:help` 目前混合管理帮助与游戏规则；`:layout ... once`、`:look` 则是宿主触发的角色观察展示。需要决定这些临时查看是否属于“模拟 LLM 阅读流”，还是只供人检查同一投影。若允许在开始/结束之间穿插 Console 专属内容，那么这对标记就不能同时承诺“截取之间所有字节便是 LLM 上下文”。可考虑独立输出流、明确的带外块或专用上下文预览，**本工作单不选定方案**。

基础真相共用不要求 Console 的提示符、ANSI 颜色、调试注解与 LLM 消息逐字相同，也不允许为 LLM 维护另一份角色状态。未来消费者应从结构化角色材料构造上下文，不解析 Console 文本来恢复真相。

### P3：统一上次行动结果与首次获知的事件

**要产出的裁决**：下一回合继承什么、保留到哪里、如何避免与 Incoming 和最近事件历史重复。

| 候选 | 收益 | 成本与限制 |
| --- | --- | --- |
| 继续只交付冻结 Incoming 摘要 | 已持久化、体积有界、冷开自足，改动较小 | 丢失逐事件因果与净零过程细节，无法直接复用 A 的完整事件体验 |
| 下一回合交付可感知事件及效果，整合现有摘要 | 保留因果，复用 A 的结构化材料与部分渲染，衔接 B | 要定义收集窗口、首次获知、持久来源/裁剪，并收敛重复信息 |
| 直接搬运上一段 Console 增量文本 | 表面改动少 | 带旧基线、临时“当前”值、宿主状态；恢复与角色隔离困难，不宜成为数据真相 |

初步建议是先评估第二种的最小范围，但不把它写成已采纳方案。若复用，优先复用 `CycleObservedEvent / CycleObservedEffect` 及事件/效果渲染，不拼接整段旧 `RenderUpdate` 文本。旧更新中每次“当前”尾部属于当时基线；新回合应有自己的完整当前观察。

需要一起回答：

1. 上轮放行操作 → 接受 → 模拟期间可感知事件 → 本次唤醒，采用何种顺序与分组？“发生时间”和“首次交给控制器的上下文”分别如何保存？
2. 行动摘要保留哪些独有价值：命令身份、区间、唤醒原因、活动仍在进行、handoff；逐项净变化与详细效果重复时如何收敛？
3. 身体随时间变化不能归因于恰巧推动此次提交的其他角色秘密动作；发现地点资源不等于资源刚生成。文本、效果键、事件种类及来源信息都需保持可见性。
4. 本轮不耗时操作已给旧上下文看过，下一轮的“最近历史”与首次获知的放行结果如何区分？这两类不能混称“上一轮已看到的事件”。
5. 需要冷开保留的材料进入何种角色状态/历史读取路径？不能仅靠 Console 内存缓存；仍不恢复旧模型会话。

与[增量 UI B](../../design/incremental-ui-milestone.md)有直接重叠：该文已提出首次获知、领域经历、稳定来源和窗口裁剪。本项应补全 B 的前置裁决，不能另造平行历史系统，也不暗中把有界继承升级成无限上下文。

### P4：按角色分发可感知信息，另保留诊断证据

**要产出的裁决**：先针对当前玩法列出事件接收规则、交付时机与诊断来源，再以隐藏行动用例检查边界。

- 至少区分：世界事实发生、角色获得可感知经历、控制器首次获得该经历、真人/模型实际读取。四者不必同刻；写入终端不证明 LLM 已接收。
- 当前 ObserverId 筛选是基础，仍需核对事件产生端、摘要、状态差分、错误文字、风险提示和来源元数据；不能只在最终渲染删他人姓名。
- 世界时间推进造成自己的身体变化可以可见，但触发提交的隐藏行为及其私有对象不能因此可见；诊断关联键可供开发者追踪，不必暴露给角色。
- 狼人杀只是隔离反例，不要求本片实现该游戏。测试可用两个角色的私有操作与同地公开效果表达同一约束。
- 现有 E/S 是世界提交/恢复材料；`operations.jsonl` 是操作及配对结果记录，并非完整模型输入或全世界可读调试日志。若要新增开发者日志，明确记录范围、来源关联、存储及失败策略，不宣称已有完整 trace。
- `--play` 的同一 Console 轮流扮演多角色，不等于这些角色共享记忆；当前 full-only 回退应保留明确范围，未实施多角色分发前不能宣称已具备 LLM 多角色隔离验收。

## 4. 建议处理顺序与交付物

1. **先裁决 P1/P2**：写出事件时序及内容归属表，明确标记是逻辑范围还是可提取范围，处理元命令中途出现与终局。
2. **再收敛 P3/P4**：选择跨回合材料方案，给出角色可见性矩阵、恢复/身份规则，以及与增量 B 的共用数据入口。可先保留 Incoming 达成边界正确，再独立补事件历史；是否分片待裁决。
3. **形成有限实施方案**：列出更改入口、领域与呈现职责、是否涉及持久化修订、延期项。不能预设仅修改 UI 或完全不改 Schema。
4. **实施与验收**：实际运行 full/delta、decision/classic，对比同一角色获得的语义材料；按下列场景检查，再合并正式文档、归档工作单。

本轮不修改已实施设计的历史正文，也不把上述候选改成新的现行合同。

## 5. 后续验收场景

| 场景 | 必须能证明的结果 |
| --- | --- |
| 新游戏、存档冷开 | 管理信息在外，角色背景/目标在内；每个新上下文自足，恢复说明不冒充角色经历 |
| 实录复现：use water → go trail-1 → 抵达与食物警告 | use 的效果仍在同一上下文；放行后旧上下文不接收结算；下一上下文有足够上文理解抵达/警告，且不重复成两套历史 |
| 非法行动、handoff、cancel、两类 continue | 拒绝与零耗时操作不误结束；恢复模拟才闭合旧上下文；保留原活动期限 |
| 查看帮助、look、layout/once、模式切换 | 不改变领域回合；管理内容不混入角色材料；预览不污染增量基线；明确是否计入上下文阅读流 |
| 中途警告返回、天气、净零变化 | 保留必要因果与实际效果；持续活动与完成不混淆；历史值不冒充当前值 |
| A 私有行动、B 同时等待 | B 的观察、摘要、历史、更新、错误及元数据不泄漏 A 私有行为；开发者能够沿诊断来源追踪 |
| 冷开、pending E 恢复、交付中断 | 不重复执行、不重复追加经历、不重编号操作；不依赖上次终端文本恢复信息 |
| 死亡/逃离、EOF、exit、取消 | 冻结终局与宿主退出明确区分；不产生虚假的可行动回合或领域提交 |

测试重点是内容归属、顺序语义、角色隔离、身份/恢复和效果一致性，不固定具体章节位置、整屏文本或缩进宽度。上下文开始/结束关系是语义合同，可以验证。至少保留一份真实 Console 实录；接入 LLM 之前不声称已证明端点消息序列、prompt-cache 或模型决策效果。

## 6. 收尾与归档条件

裁决完成后，将生命周期与继承规则合入[信息继承方案](../../design/decision-context-handoff.md)，Console 带外组合合入[Console 边界](../../design/console-command-boundary.md)和[布局合同](../../design/console-layouts.md)，事件保留/可见性合入[增量 UI 阶段目标](../../design/incremental-ui-milestone.md)。新增稳定概念时更新[术语表](../../glossary.md)，不为工作单预先声明不存在的 API。

验收证据放 experiments 或测试；替换 PROJECT-STATE 中本工作单入口，再按[文档归档入口](../README.md)归档。不要长期并行维护两份当前待办。
